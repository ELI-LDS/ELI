# 브랜치·커밋·PR 컨벤션

ELI의 개발자와 AI 에이전트는 브랜치 생성, 커밋, PR 작성 전에 이 문서를 확인해요.
브랜치 이름은 [Conventional Branch 1.1.0](https://conventionalbranch.org/), 커밋은 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)을 바탕으로 해요.
아래의 언어, 작업 흐름, PR 규칙은 ELI의 프로젝트 규칙이에요. GitHub 보호 규칙과 CI를 실제로 설정했다는 의미는 아니며, 추후 확정하는 GitHub 운영 전략에 맞춰 갱신해요.

## 1. 브랜치 이름

형식: `<type>/<description>`

| 접두사 | 용도 | 예시 |
| --- | --- | --- |
| `feat/` | 새 기능·컴포넌트 | `feat/button-component` |
| `fix/` | 버그 수정 | `fix/input-focus-ring` |
| `hotfix/` | 배포된 버전의 긴급 수정 | `hotfix/button-click-error` |
| `release/` | 릴리스 준비 | `release/v1.0.0` |
| `chore/` | 문서·설정·의존성·유지보수 | `chore/branch-conventions` |

- `feature/`, `bugfix/`는 사용하지 않고 각각 `feat/`, `fix/`로 통일해요.
- AI 에이전트도 작업 목적에 따른 접두사를 사용해요. `codex/`, `ai/`를 추가하지 않아요.
- 설명은 영문 소문자, 숫자, 단어 사이 하이픈으로 작성해요. 공백·밑줄·한글·대문자는 사용하지 않아요.
- 점은 릴리스 버전에만 사용해요. 하이픈이나 점을 연속으로 쓰거나 설명의 처음·끝에 두지 않아요.
- 연결할 이슈가 있으면 `feat/issue-12-button-component`처럼 번호를 포함할 수 있어요.
- `main` 같은 기본 브랜치에는 접두사를 붙이지 않아요.
- 문서·테스트·리팩터링만 수행하는 브랜치는 `chore/`를 사용하고, 커밋에서는 세부 타입으로 구분해요.

## 2. 작업 흐름

별도 운영 전략이 정해지기 전에는 `main`을 통합 브랜치로 사용해요.

1. 작업 전 현재 브랜치와 변경 사항을 확인해요. 기존 작업을 임의로 덮어쓰거나 다른 작업에 포함하지 않아요.
2. 새 작업은 최신 `main`에서 목적에 맞는 브랜치를 만들어요. 이미 해당 작업 브랜치에 있다면 이어서 사용해요.
3. 한 브랜치와 PR은 하나의 목적을 다루고, 커밋은 검토 가능한 변경 단위로 나눠요.
4. 변경에 필요한 검증을 수행한 뒤 `main`을 대상으로 PR을 작성해요. `main`에 직접 커밋하거나 푸시하지 않아요.
5. 리뷰와 설정된 필수 검사를 통과한 뒤 병합해요. 기본 병합 방식은 Squash merge로 하고, 최종 커밋에도 아래 규칙을 적용해요.

`release/`는 릴리스 준비가 필요할 때만 사용해요. `hotfix/`의 기준은 수정 대상 배포 버전이며, 배포 태그가 `main`과 다르면 해당 태그에서 분기하고 수정 사항을 `main`에도 반영해요. 장기 유지보수 브랜치·승인 인원·배포 자동화는 추후 GitHub 운영 전략에서 정해요.

## 3. 커밋 컨벤션

```text
<type>[(scope)][!]: <요약>

[변경 이유와 필요한 설명]

[footer]
```

대괄호는 선택 항목을 뜻하며 실제 메시지에 쓰지 않아요.

| 타입 | 용도 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 오류 수정 |
| `docs` | 문서 변경 |
| `style` | 동작에 영향 없는 코드 포맷 변경 |
| `refactor` | 기능 변경 없는 내부 구조 개선 |
| `perf` | 성능 개선 |
| `test` | 테스트 추가·수정 |
| `build` | 빌드·패키징·의존성 변경 |
| `ci` | CI 설정 변경 |
| `chore` | 그 외 유지보수 |
| `revert` | 기존 변경 되돌리기 |

- 타입과 scope는 영문 소문자, 요약과 본문은 한국어를 기본으로 해요. 코드 식별자는 원문을 유지해요.
- scope는 `button`, `input`, `tokens`, `storybook`처럼 변경 대상을 나타내며 생략할 수 있어요.
- 요약은 변경 결과를 간결하게 표현하고 끝에 마침표를 붙이지 않아요.
- CSS 변경도 사용자에게 보이는 기능 추가라면 `feat`, 오류 수정이라면 `fix`예요. CSS 파일이라는 이유만으로 `style`을 쓰지 않아요.
- 호환성이 깨지면 `!`를 붙이고 `BREAKING CHANGE:` footer에 영향과 이전 방법을 기록해요.
- 공개 props뿐 아니라 CSS 변수·커스터마이징용 클래스·내부 요소 선택자·CSS import 경로도 호환성 검토 대상이에요.

```text
feat(button): 크기 옵션 추가
fix(input): 포커스 테두리 잘림 수정
docs: 브랜치 및 PR 컨벤션 정리
build: 패키지 CSS 배포 설정 추가
```

호환성이 깨지는 변경 예시:

```text
feat(tokens)!: 기본 색상 변수 이름 변경

BREAKING CHANGE: --eli-primary를 --eli-color-primary로 변경해요. 소비 프로젝트의 CSS 재정의도 새 이름으로 수정해야 해요.
```

브랜치와 개별 커밋의 타입은 일치할 필요가 없어요. 예를 들어 `feat/button-component` 안에 `feat`, `test`, `docs` 커밋을 함께 작성할 수 있어요. `hotfix/`의 오류 수정 커밋 타입은 `fix`를 사용해요.

## 4. PR 컨벤션

### 제목

커밋과 동일한 `<type>[(scope)][!]: <요약>` 형식을 사용하고, PR 전체의 최종 변경을 표현해요.

```text
feat(button): 버튼 컴포넌트와 CSS 커스터마이징 지원
```

### 본문

문제와 변경 후 동작을 먼저 설명해요. 아래 항목을 변경 규모에 맞게 작성하며, 해당하지 않는 항목은 생략할 수 있어요.

```markdown
## 변경 내용

- 해결하려는 문제와 변경 후 동작
- 공개 API 또는 스타일 커스터마이징 규약의 변경

## 검증

- 실행한 검사와 결과
- 실행하지 못한 검증과 이유

## UI 확인

- 시각적 변경이 있으면 전후 스크린샷 또는 Storybook 링크
- 관련 상태와 CSS 재정의 예시의 확인 결과

## 용량과 버전

- `pnpm size`의 압축 크기·압축 해제 크기·포함 파일 수
- 예상 버전 변경 유형과 이유

## 호환성

- 기존 사용 코드에 미치는 영향과 필요한 이전 방법

## 관련 이슈

Closes #이슈번호
```

- 실제 수행한 검증만 기록해요. 아직 검사 도구가 없다면 그 사실을 적어요.
- 관련 이슈가 없으면 이슈 항목을 생략해요. PR 병합으로 해결되는 이슈만 `Closes #번호`로 연결하고, 단순 참조는 `Refs #번호`를 사용해요.
- 구현 중인 PR은 Draft로 표시하고, 검토 가능한 상태가 되면 리뷰를 요청해요.
- 범위가 바뀌면 제목과 본문을 최종 변경 내용에 맞춰 갱신해요.
- Squash merge 시 PR 제목을 최종 커밋 제목으로 사용해요. 호환성이 깨지는 변경의 `!`와 `BREAKING CHANGE:` 설명도 최종 커밋에 보존해요.

## 5. 에이전트 확인 사항

- Codex PR 리뷰 기준은 루트의 [AGENTS.md](../AGENTS.md), 구현 검증은 [testing.md](testing.md)를 따라요. 자동 리뷰 연결은 아직 설정하지 않았어요.
- 브랜치 생성·커밋·PR 작성 시 이 문서의 규칙을 따라요.
- 커밋 전에 diff와 스테이징 목록을 확인하고 해당 작업의 파일만 포함해요.
- 비밀 값, 로컬 환경 파일, 불필요한 생성물을 커밋하지 않아요.
- 문서 작성 요청을 커밋·푸시·PR 생성 요청으로 확대 해석하지 않아요.
- 이 문서는 컨벤션이며 GitHub 설정, 자동 검증, npm 배포를 직접 활성화하지 않아요.

배포에 영향을 주는 PR은 [검증 기준](testing.md)의 용량 결과와 [버전 규칙](versioning.md)의 변경 유형을 반드시 기록해요.
