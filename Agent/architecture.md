# 프로젝트 구조

## 소스 설치와 기존 전체 패키지를 구분해요

`packages/ui/src`는 선택 설치와 기존 전체 패키지가 공유하는 UI 원본이에요. npm의 `eli-design` 설치 도구는 GitHub Release의 UI·하네스 콘텐츠를 각각 선택해 받아요. 기존 `@eli-design/ui` 전체 패키지에는 공통 토큰과 하네스를 포함해요. `apps/storybook`과 `apps/docs`는 비공개 앱이에요. npm 배포 단계와 공식 홍보 시점의 버전 전환은 [버전 규칙](versioning.md)에서 관리해요.

현재는 외부 사용자가 없는 실험 단계예요. 기존 전체 패키지는 종료 예정이며 이 패키지 구성은 현재 내부 구현 상태를 설명해요. 소스 배포에 맞춰 패키지명·역할·공개 경로를 바꿀 수 있어요. 하네스 배포 구조가 달라지면 담당 개발자와 연결 계약을 먼저 맞춰요.

공개 컴포넌트는 `packages/ui/src/{그룹}/{컴포넌트}/`에서 관리하고 그룹의 `index.ts`로 내보내요. 현재 실험 패키지는 `@eli-design/ui/{그룹}`에서 가져와요. 실제 공개 경로는 `packages/ui/package.json`의 `exports`를 기준으로 확인해요.

하나의 그룹에 역할이 가까운 컴포넌트를 함께 둘 수 있어요. 각 컴포넌트의 타입·구조·스타일·Hook은 PascalCase 컴포넌트 폴더 안에서 관리하고, 그룹 진입점에서는 외부에 필요한 심벌만 공개해요.

`Agent/` 문서에는 현재 컴포넌트 명단이나 개별 props를 반복해서 기록하지 않아요. 여러 컴포넌트에 적용되는 구조 규칙과 별도 공개 여부처럼 예외적인 결정만 기록해요. 구현 현황은 루트 README와 Storybook에서 확인해요.

`packages/ui/src/dim`은 Modal 같은 오버레이 컴포넌트가 내부에서 공유해요. 공개 사용 사례가 확정되기 전까지 별도의 패키지 진입점을 만들지 않아요.

`packages/ui/src/icon`은 컴포넌트 내부에서 재사용하는 아이콘을 관리해요. 아이콘 자체를 공개하기 전까지 별도의 패키지 진입점을 만들지 않아요.

컴포넌트 Storybook 예제는 `apps/storybook/stories`에서 관리하고 개발용 `@/` 경로로 UI 소스를 연결해요. 이를 통해 `packages/ui`에 Storybook 의존성을 추가하지 않아요.

## 소스 설치를 기본으로 사용해요

ELI의 기본 소비 방식은 shadcn/ui처럼 필요한 컴포넌트 소스를 소비 프로젝트에 추가하는 방식이에요. 전체를 원하면 같은 소스 설치 흐름에서 모든 공개 컴포넌트를 명시적으로 선택할 수 있어야 해요. UI 원본은 `packages/ui/src` 한 곳에서 관리하고 배포 방식별로 구현을 복제하지 않아요.

- **소스 방식 — 기본:** 필요한 컴포넌트 하나·여러 개 또는 전체와 공통 토큰·실제 의존 파일을 소비 프로젝트에 추가해요. 설치된 로컬 파일에서 import하고 사용자가 직접 수정해요. `packages/registry`는 배포 JSON을 생성하고 `packages/cli`는 npm의 `eli-design`으로 실행해요. CLI·UI 콘텐츠·하네스의 게시 상태와 실제 검증 범위는 [릴리스 기록](../handbook/releases/0.2.0.md)에서 구분해요. 데이터와 연동 계약은 [레지스트리 지침](registry.md)에서 관리해요.
- **패키지 방식 — 종료 예정:** 기존 npm `@eli-design/ui`는 종료하고 사용자 배포는 `eli-design` 소스 설치로 통일해요. 신규 설치 대안으로 안내하지 않아요. 현재 원본·내부 workspace·호환 검사에 남은 이름과 연결은 구조 변경 작업에서 별도로 정리하며 npm 삭제가 완료된 것으로 표현하지 않아요.

`@eli-design/ui/button` 같은 하위 경로 import는 소비 앱의 번들 분리에 도움을 줄 수 있지만, npm tarball에서 Button 파일만 다운로드한다는 뜻은 아니에요. 실제로 한 컴포넌트만 내려받으려면 shadcn/ui처럼 CLI가 레지스트리 항목의 소스와 필요한 파일을 소비 프로젝트에 복사하는 별도 배포 경로가 필요해요.

예를 들어 Button을 선택하면 공통 `tokens/`와 `Button/` 폴더 안의 컴포넌트·스타일·타입·Hook만 추가해요. Button이 내부 아이콘처럼 다른 파일을 실제로 참조한다면 그 파일만 명시적인 레지스트리 의존성으로 함께 추가하고, 관계없는 컴포넌트는 내려받지 않아요.

공통 `tokens/`는 첫 컴포넌트를 추가할 때 한 번만 설치해요. 다음 컴포넌트를 추가할 때 이미 같은 토큰이 있으면 중복 복사하지 않아요. 같은 컴포넌트를 다시 추가해도 불필요한 파일이 늘어나지 않아야 해요. 레지스트리는 원본 소스를 참조해 `.artifacts/registry`에 생성하고 전체 npm 패키지에는 포함하지 않아요. 하네스는 같은 CLI의 별도 선택 명령으로 독립 콘텐츠를 설치해요. 파일·버전·설정 병합은 [하네스 구조](harness.md#하네스-배포-데이터와-설치-기록)를 따라요.

CLI는 파일을 쓰기 전에 변경 대상과 충돌을 보여주고, 사용자가 수정한 기존 파일을 확인 없이 덮어쓰지 않아야 해요. 복사된 소스는 소비 프로젝트가 직접 소유하고 수정할 수 있으므로, 패키지 방식의 자동 버전 업데이트와 다른 업데이트·마이그레이션 정책을 별도로 정의해요.

기본 설치 진입점은 `eli-design`이에요. 실행 형태와 구현 상태는 [패키지 매니저 지침](package-managers.md#소스-추가를-기본-소비-방식으로-사용해요)에서 관리해요. 설치 도구에는 UI 전체 소스와 하네스를 묶어 내려받게 하지 않아요. 하네스가 소비 방식과 실제 설치 경로를 구분하도록 전달할 기준은 [레지스트리 연동 계약](registry.md#하네스가-소비-방식을-구분하게-해요)에서 관리해요.

## 참고 모델을 ELI에 맞게 적용해요

아래는 외부 시스템의 복제가 아니라 ELI가 선택한 설계 기준이에요. 같은 기준을 다른 지침에 다시 정의하지 않아요.

| 참고 대상 | 가져올 원칙 | ELI의 적용 |
| --- | --- | --- |
| [shadcn 레지스트리](https://ui.shadcn.com/docs/registry/registry-item-json) | 파일·의존성을 단위로 하는 소스 배포 | 개별·다중 추가가 기본이고 전체는 명시적으로 선택해요. 사용자가 복사한 소스를 소유하고 수정해요. |
| [SEED 사용 가이드](https://seed-design.io/react/components/action-button) | 목적·variant 선택 기준·사용 예시 | 디자이너와 합의한 선택 기준을 문서 원본에서 관리하고 JSDoc·Storybook·MCP가 같은 의미를 전달하게 해요. |
| [SEED CLI](https://seed-design.io/react/getting-started/cli/commands) | 설정·호환성 검사·기존 파일 충돌 처리 | 설치 버전과 경로를 기록하고, 사용자 수정 파일을 보호하며 설치 결과와 호환성을 확인하게 해요. |

SEED의 ActionButton 스니펫은 `@seed-design/react`를 참조해요. ELI는 이 기반 패키지 의존 구조를 채택하지 않고, 선택한 소스가 전체 ELI UI 패키지를 다시 요구하지 않게 해요. shadcn을 참고한다는 이유로 Tailwind나 shadcn CLI를 필수로 도입하지 않아요. 두 시스템 중 하나가 항상 더 작다고 단정하지 않고 [실제 다운로드량](testing.md#소스-설치의-전체-다운로드량을-확인해요)으로 확인해요.

## 코드와 스타일을 함께 연결해요

TypeScript는 ESM과 타입 선언을 만들고 `scripts/build-ui.mjs`는 CSS를 같은 상대 경로로 복사해요. 컴포넌트는 자신의 CSS를 import하고, 그 CSS는 필요한 공통 토큰을 연결해요. `sideEffects`에는 CSS를 등록해요.

그룹 진입점에서 여러 CSS 의존성이 연결되면 사용하지 않는 형제 컴포넌트의 CSS도 포함될 수 있어요. JS 트리 셰이킹과 CSS 제거를 같은 것으로 설명하지 않아요. 실제 소비 번들로 확인해요.

## 폰트 로딩을 분리해요

`@eli-design/ui`는 `--eli-font-family-sans`와 fallback만 제공해요. 폰트 파일을 패키지에 넣거나 CDN에서 자동으로 불러오지 않아요. 이를 통해 컴포넌트 패키지 용량과 소비 앱의 폰트 로딩 정책을 분리해요.

현재 CLI는 폰트를 자동 설치하지 않으므로 소비 앱이 Pretendard를 직접 연결해요. 추후 폰트 초기 설정 도구를 구현한다면 프레임워크를 확인하고 전역 진입점에 한 번 연결해요. 이미 같은 폰트가 설정되어 있으면 다시 추가하지 않아요. MCP는 이 과정을 안내할 수 있지만 재현 가능한 설치와 파일 변경은 초기 설정 도구가 담당해요.

## 실행 의존성을 검토해요

UI 원본과 기존 전체 UI 패키지에는 실행 `dependencies`가 없어요. CLI는 semver 하나를 실행 의존성으로 사용하며 UI 실행 의존성을 포함하지 않아요. React 19.3 계열을 개발·검증 기준으로 삼고 peer 범위는 `^19.3.0`이에요. React DOM은 SSR 검증용 개발 의존성으로만 사용하며 배포 패키지에는 포함하지 않아요. 포털 같은 런타임 기능을 구현할 때 peer dependency 필요성을 별도로 검토해요. 지원 범위를 넓힐 때 해당 버전의 소비 테스트를 추가해요.

새 실행 의존성을 추가하면 목적·직접 구현 비용·용량·라이선스를 검토하고 패키징 검사의 기준을 함께 갱신해요. 개발 도구와 실행 의존성을 구분해요.

## 현재 상태와 예정된 기능

색상·타이포그래피·레이아웃 토큰을 패키지에 포함하고 실제 tarball의 Vite 소비와 서버 렌더링을 검증해요. Next.js App Router에서는 프로덕션 빌드·Server Component의 직접 import·Client Component의 이벤트 연결·프로덕션 서버 HTML·CSS 자동 연결·브라우저 hydration을 별도로 검증해요. 같은 tarball의 npm·pnpm·Yarn Classic·Yarn Modern·Bun 소비 행렬도 자동 검사해요. 구현된 컴포넌트와 확정되지 않은 디자인은 루트 README에서 구분해요. Storybook은 Cloudflare Worker에 정적 파일로 배포하며 사용자 지정 도메인에서 확인해요. `apps/docs`는 문서·랜딩 페이지용 Next.js App Router 앱의 초기 셋업만 있고 아직 내용과 배포는 없어요. 문서 원본·API·MCP 구조는 [문서 앱 지침](docs.md)에서 관리해요. UI·하네스 선택 설치와 소비 검사는 구현되어 있어요. 실제 공개 상태는 릴리스 기록을 확인해요. 폰트 초기 설정 도구, 원격 MCP 구현과 npm 배포 자동화는 아직 없어요.
