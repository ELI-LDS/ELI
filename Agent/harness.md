# 하네스 구조

하네스는 ELI를 쓰는 프로젝트에서 Claude Code·Codex 같은 에이전트가 `/eli-...` 명령으로 디자인 작업을 하도록 돕는 도구예요. 스킬과 SessionStart 훅 스크립트는 `packages/harness`에 있어요. 원격 MCP의 도구와 배포 경로가 아직 없어서 실제 에이전트에 설치해 쓸 수는 없어요.

## 로컬과 원격으로 나눠요

| 구분 | 담는 내용 | 위치 |
| --- | --- | --- |
| 로컬 하네스 | 명령별 절차, 판단 규칙, 원격 MCP 연결 방법 | `packages/harness` |
| 원격 MCP | 컴포넌트 사용법, 언제 써야 하는지, props, 토큰, 가이드 | `apps/docs`의 `/mcp` |

- 로컬 하네스는 뼈대만 담아요. 분량은 [SEED Design 스킬](https://seed-design.io/ai-integration/skill) 정도로 유지해요.
- 로컬 하네스에 컴포넌트 이름, props, 토큰 값, 버전 표를 적지 않아요. 이런 내용은 원격 MCP에서 조회해요. 로컬에 복사하면 문서와 어긋나요.
- 로컬 하네스는 원격 MCP에 연결하는 방법을 안내해요. 연결되지 않았으면 추측해서 작업하지 않고 연결 방법을 먼저 알려줘요.
- 원격 MCP의 도구와 데이터 구조는 [문서 앱 지침](docs.md)에서 관리해요.
- 하네스를 `@eli/ui` 배포 결과물에 포함하지 않아요.

## 로컬 하네스의 기능

| 명령 | 하는 일 |
| --- | --- |
| 기본 동작 | 사용자가 디자인 수정이나 변경을 요청하면 원격 MCP에서 ELI 문서를 읽은 뒤 작업해요. 명령을 입력하지 않아도 적용돼요. |
| `/eli-setup` | 처음 셋업할 때 써요. 기획과 레퍼런스를 묻고, 문서 세 개와 디자인 시스템을 만들고, 피드백으로 다듬어요. |
| `/eli-doctor` | 설치·버전·폰트·토큰 파일·원격 연결을 점검하고 다음에 쓸 명령을 안내해요. 코드를 바꾸지 않아요. |
| `/eli-design-md` | 사용자에게 질문해서 `DESIGN.md`를 만들어요. 서비스 기획, 사용자 예시, 지향하는 제품(당근, 토스 등)을 물어요. |
| `/eli-design-system` | ELI로 디자인 시스템을 구축하고, 디자인 시스템 페이지를 만들어 로컬에서 띄워 보여줘요. |
| `/eli-verify` | 프론트엔드 코드 전체에서 디자인 시스템을 따르지 않는 코드와 모바일 웹에서 깨지기 쉬운 화면을 찾아 보고하고 고쳐요. |
| `/eli-ux-writing` | 사용자에게 질문해서 문구 규칙을 `UX-WRITING.md`로 정하고, 그 규칙에 맞게 화면의 문구를 다듬어요. |
| `/eli-icon` | `ICON.md`에 아이콘 스타일을 정하고, 화면에 크게 보이는 커스텀 아이콘을 같은 톤으로 만들어요. 작은 UI 아이콘은 `@eli/ui`의 아이콘을 써요. |

명령마다 `packages/harness/skills/<명령 이름>/SKILL.md` 파일 하나를 둬요. 기본 동작과 원격 연결 방법은 `skills/eli/SKILL.md`에 있어요.

- 원격 MCP의 주소는 `skills/eli/SKILL.md` 한 곳에만 적어요. 다른 스킬은 서버 이름 `eli-docs`로만 가리켜요.
- 스킬은 [문서 앱 지침](docs.md)의 도구 이름, 섹션 키, 가이드 주제를 그대로 써요. 한쪽을 바꾸면 다른 쪽도 함께 고쳐요.
- 스킬이나 훅을 고치면 `pnpm test:harness`를 실행해요. 이 검사는 훅의 출력과 스킬의 형식만 확인해요. 에이전트가 스킬을 실제로 잘 따르는지는 확인하지 않아요.

### 처음 셋업은 세 단계로 해요

1. **묻기:** 서비스의 간략한 기획과 디자인 레퍼런스로 삼을 제품만 물어요.
2. **만들기:** 답을 바탕으로 `DESIGN.md`, `ICON.md`, `UX-WRITING.md`를 만들고 디자인 시스템을 개발해 로컬에서 띄워요.
3. **다듬기:** 디자인 시스템을 본 사용자의 피드백으로 2단계에서 만든 것을 고치고 발전시켜요. 사용자가 됐다고 할 때까지 반복해요.

- `/eli-setup`은 문서의 구성과 규칙을 각 명령의 스킬에서 가져와요. 같은 내용을 `eli-setup`에 다시 적지 않아요.
- 사용자가 답하지 않아 추정한 내용에는 `(초안)`을 붙이고, 3단계에서 확인받으면 지워요.
- 피드백은 페이지만 고치지 않고 문서나 토큰 파일을 먼저 고쳐요.
- 훅은 `DESIGN.md`가 없는 프로젝트에서 UI 작업을 요청받으면 `/eli-setup`을 먼저 제안하게 해요.
- `/eli-design-md`, `/eli-ux-writing`, `/eli-design-system`은 셋업 뒤에 한 부분만 다시 만들거나 자세히 정할 때 써요.

### 화면 코드의 기준은 eli 스킬의 references에 둬요

- `skills/eli/references/`에 CSS(`css.md`), 마크업·접근성·React(`code.md`), 화면 디자인(`design.md`) 기준을 둬요. 어느 서비스에나 적용되는 일반 기준이에요.
- `skills/eli/SKILL.md`에는 항상 지킬 핵심 규칙과 어느 문서를 언제 읽는지만 적어요.
- 이 문서들에는 ELI의 컴포넌트 이름, props, 토큰 값을 적지 않아요. ELI 자체의 정보는 원격 MCP가 가져요.
- 기준은 MDN, web.dev, WCAG 2.2, react.dev 같은 1차 자료로 확인한 내용만 적고, 문서 끝에 출처를 남겨요. 실무 관행은 관행이라고 구분해요.
- 브라우저 지원 현황은 시간이 지나면 달라져요. `css.md`의 "써도 되는 기능" 표는 기준 날짜를 적고, 고칠 때 다시 확인해요.
- `/eli-verify`의 화면 품질 점검은 이 문서들을 기준으로 써요.

### 문서 세 개는 초안을 가져와 맞춰 써요

- `DESIGN.md`, `ICON.md`, `UX-WRITING.md`의 상세한 초안을 각 스킬 폴더의 `template.md`에 둬요. 스킬은 문서를 처음부터 새로 쓰지 않고, 초안을 가져와 사용자의 서비스에 맞게 고쳐요.
- 초안의 `{중괄호}`는 채울 자리이고, `<!-- 맞춤: ... -->` 주석은 어떻게 고칠지 알려주는 지시예요. 저장한 문서에는 둘 다 남기지 않아요.
- 초안에는 여러 서비스에 공통으로 맞는 기본 내용만 적어요. ELI의 컴포넌트 이름, props, 토큰 값은 적지 않아요.
- 문서의 구성을 바꿀 때는 `template.md`를 고쳐요. 스킬에는 구성을 다시 적지 않아요.
- `ICON.md` 초안의 형태 값(캔버스, 선 굵기, 모서리 반경)은 임시 기본값이에요. 디자이너의 규칙을 원격 `icon` 가이드에 적으면 그 값이 먼저 적용돼요.

### 기본 동작

- `hooks/session-start.mjs`는 세션을 시작할 때 프로젝트가 `@eli/ui`를 쓰는지 확인하고, 쓰는 경우에만 짧은 지침을 출력해요. [ponytail](https://github.com/DietrichGebert/ponytail)의 SessionStart 훅 방식을 참고해요.
- 주입하는 지침은 "UI를 수정하기 전에 원격 MCP에서 해당 컴포넌트 문서를 읽어요" 수준으로 짧게 유지해요.

### 프로젝트 토큰을 반드시 만들고 전역에서 써요

- `/eli-design-system`은 소비 프로젝트의 토큰 파일을 반드시 만들어요. 이 단계는 건너뛸 수 없어요.
- 프로젝트 토큰은 역할로 이름을 짓고 ELI 토큰을 가리켜요. 값을 직접 쓰는 곳은 토큰 파일 하나뿐이에요.
- 기본 동작과 훅은 모든 스타일 작업에서 프로젝트 토큰만 쓰게 해요. 필요한 토큰이 없으면 값을 직접 쓰지 않고 토큰 파일에 먼저 추가해요.
- `/eli-verify`는 토큰 파일 밖의 값과 화면 코드의 `--eli-` 변수를 위반으로 보고해요.
- `hooks/post-edit.mjs`는 에이전트가 화면 파일을 고칠 때마다 직접 쓴 색상 값을 찾아 바로 알려요. 간격과 글자 값은 오탐이 많아서 `/eli-verify`가 맡아요.
- 사람이 직접 쓴 코드는 `/eli-verify`를 실행해야 잡혀요. 린트 규칙처럼 빌드를 막는 장치는 아직 없어요.

### DESIGN.md에 CSS 단위 기준을 반드시 적어요

- `/eli-design-md`와 `/eli-setup`은 `DESIGN.md`에 `## 단위` 표를 항상 적어요. 글자는 `rem`, 레이아웃은 `%`와 `fr`, 화면 높이는 `dvh`, 테두리는 `px`처럼 용도별로 무엇을 쓰는지와 그 이유를 적어요.
- 기본 표는 `skills/eli-design-md/template.md`에서 관리해요.
- 기본 동작은 CSS 값을 쓸 때 이 표에서 단위를 고르게 하고, `/eli-verify`는 표와 다른 단위를 보고해요.
- 글자 크기, 간격, 모서리는 토큰으로 쓰므로, 이 표는 새 토큰을 정할 때와 토큰이 다루지 않는 레이아웃 크기에 적용해요.

### 문구는 UX-WRITING.md를 만들고 그 문서대로 써요

- `/eli-ux-writing`은 첫 문구를 다듬기 전에 소비 프로젝트의 루트에 `UX-WRITING.md`를 만들어요. 말투, 호칭, 톤, 문구 형식, 용어, 표기를 좋은 예와 나쁜 예로 적어요.
- 기본 동작과 훅은 화면에 보이는 모든 문구를 `UX-WRITING.md`대로 쓰게 해요. 문서가 없으면 먼저 만들자고 안내해요.
- `/eli-verify`는 규칙과 다른 문구를 보고하고, `/eli-doctor`는 문서가 있는지 확인해요.
- 문구를 다듬을 때 뜻, 숫자, 조건은 바꾸지 않아요. 약관 같은 법적 문서는 다듬지 않아요.
- 이 규칙은 소비 프로젝트의 화면 문구에 적용해요. ELI 저장소의 문서는 [글쓰기 지침](writing.md)을 따라요.

### 디자인 시스템 페이지는 로컬에서만 띄워요

- 사용자의 프로젝트가 쓰는 프레임워크나 라이브러리 위에 페이지를 만들고, 그 프로젝트의 개발 서버로 띄워요.
- 프로젝트에서 쓸 라이브러리가 아직 정해지지 않았으면 HTML 파일로 만들어 로컬에서 띄워요.
- 외부에 배포하지 않아요. 배포 명령을 실행하거나 배포 설정을 추가하지 않아요.

### verify는 보고한 뒤 고쳐요

- 먼저 코드를 바꾸지 않고 위반 목록을 보고해요.
- 판단 기준이 되는 토큰과 컴포넌트 목록은 원격 MCP에서 조회해요.
- 원격에서 확인하지 못한 항목은 통과로 적지 않고 "확인하지 못했어요"로 구분해요.

### 아이콘은 ICON.md를 만들고 그 문서대로 만들어요

- 커스텀 아이콘을 남발하지 않아요. 기본은 ELI의 선 아이콘이에요. 커스텀 아이콘과 선 아이콘을 고르는 판단표는 `skills/eli-icon/SKILL.md`에서 관리하고, 빈 화면·온보딩처럼 화면의 메시지를 대표하는 자리에만 한 화면에 하나씩 써요.
- 첫 아이콘을 만들기 전에 소비 프로젝트의 루트에 `ICON.md`를 만들어요. 톤, 형태, 색, 파일 규칙, 만든 아이콘 목록을 적어요.
- 이후의 모든 아이콘은 `ICON.md`를 읽고 따라요. 프로젝트 전체의 아이콘이 같은 톤으로 나오게 하기 위해서예요.
- 스타일을 바꿀 때는 아이콘 하나만 고치지 않고 `ICON.md`를 먼저 고쳐요.
- `ICON.md`의 기본값이 되는 그리드, 선 굵기, 색 규칙은 원격 `icon` 가이드에서 조회해요. 디자이너에게 전달받지 않은 규칙을 임의로 만들지 않아요.

## 정하지 않은 것

- **업그레이드 안내:** 버전을 올릴 때 바뀐 API를 찾아 주는 기능은 만들지 않았어요. 원격 MCP가 버전별 변경 내역을 제공해야 하고, 첫 배포 뒤에 검토해요.
- **훅 등록:** 훅 스크립트를 에이전트에 등록하는 설정 파일은 배포 경로에 따라 달라서 아직 만들지 않았어요.
- **하네스 배포 경로:** 아직 정하지 않았어요. 플러그인 마켓플레이스, `npx skills add`, npm 패키지 중 어느 것으로 배포할지와 저장소 공개 범위가 정해지면 이 문서에 기록해요. 정해지기 전에는 설치 명령을 README나 문서에 적지 않고, 특정 배포 경로에만 맞는 구조를 먼저 만들지 않아요.
- **지원 에이전트별 호출 방식:** Claude Code와 Codex를 목표로 해요. 에이전트별 명령 이름 형식은 배포 경로와 함께 확인해요.
- **아이콘 규칙:** 디자이너에게 전달받아야 해요.
