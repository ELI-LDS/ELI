# 하네스 구조

하네스는 ELI를 쓰는 프로젝트에서 Claude Code·Codex 같은 에이전트가 `/eli-...` 명령으로 디자인 작업을 하도록 돕는 도구예요. 스킬과 훅 스크립트의 원본은 `packages/harness`에 있고, 빌드할 때 npm에 게시하는 `@eli-design/ui` 패키지에 함께 들어가요. 에이전트는 설치된 패키지 안의 `harness/INSTALL.md`를 따라 스킬과 훅을 사용자의 프로젝트에 복사해요. 원격 MCP는 아직 준비 중이므로 원격 조회가 필요한 단계의 동작 여부는 따로 구분해요. npm 설치만으로 원격 기능까지 사용할 수 있다고 안내하지 않아요.

## 로컬과 원격으로 나눠요

| 구분 | 담는 내용 | 위치 |
| --- | --- | --- |
| 로컬 하네스 | 명령별 절차, 판단 규칙, 원격 MCP 연결 방법 | `packages/harness` |
| 원격 MCP | 컴포넌트 사용법, 언제 써야 하는지, props, 토큰, 가이드 | `apps/docs`의 `/mcp` |

- 로컬 하네스는 뼈대만 담아요. 분량은 [SEED Design 스킬](https://seed-design.io/ai-integration/skill) 정도로 유지해요.
- 로컬 하네스에 컴포넌트 이름, props, 토큰 값, 버전 표를 적지 않아요. 이런 내용은 원격 MCP에서 조회해요. 로컬에 복사하면 문서와 어긋나요.
- 로컬 하네스는 원격 MCP에 연결하는 방법을 안내해요. 연결되지 않았으면 추측해서 작업하지 않고 연결 방법을 먼저 알려줘요.
- 원격 MCP의 도구, 응답 형식, 가이드 주제는 [원격 MCP 규격](mcp-spec.md)에서 관리해요.

## 현재 실험 패키지는 하네스를 함께 담아요

이 절과 아래 설치·버전 안내는 현재 구현 기준이에요. UI 소스 배포가 이 구조를 계속 사용해야 한다는 뜻은 아니에요. 소스 선택 설치에 하네스가 자동으로 따라오는 것으로 해석하지 않아요.

- `pnpm build`가 `packages/harness`를 `packages/ui/harness`로 복사해요. 이 폴더는 빌드 결과물이라 Git에 올리지 않아요. 고칠 때는 `packages/harness`의 원본을 고쳐요.
- 패키지에는 `harness/INSTALL.md`, `harness/skills/`, `harness/hooks/`가 들어가요. 현재 빌드에서는 컴포넌트와 스킬이 같은 버전이에요.
- 현재 버전 원본은 하나예요. 빌드가 `packages/ui/package.json`의 `version`을 `harness/skills/eli/VERSION`에 적어요. 원본 폴더에는 `VERSION` 파일을 두지 않아요.
- 하네스의 파일은 실행 코드에서 import하지 않아요. `exports`에 넣지 않고, 번들 크기에 영향을 주지 않아요.
- 하네스를 고치면 패키지의 내용이 달라져요. `pnpm size`로 용량을 확인하고 PR에 적어요.

## 설치는 INSTALL.md의 안내를 따라요

- 설치 절차의 기준은 `packages/harness/INSTALL.md`예요. 루트 README에는 이 문서를 읽으라는 안내만 두고 절차를 다시 적지 않아요.
- 에이전트는 먼저 프로젝트의 패키지 매니저로 `@eli-design/ui`를 설치하고, `node_modules/@eli-design/ui/harness/INSTALL.md`를 읽어요.
- npm에서 설치할 수 없을 때만 저장소를 임시 폴더에 받아 `packages/harness/INSTALL.md`를 따라요.
- 스킬 폴더는 통째로 복사해요. 스킬끼리 서로의 `template.md`와 `references/`를 읽어요.
- 훅은 `node_modules` 안의 파일을 직접 가리키지 않고 프로젝트에 복사해서 등록해요. 의존성을 다시 설치하는 동안에도 깨지지 않아요.
- Claude Code는 `.claude/skills/`와 `.claude/settings.json`, Codex는 `.agents/skills/`와 `.codex/hooks.json`을 써요.
- 훅을 등록하기 전에 무엇을 등록하는지 사용자에게 알리고, 기존 설정 파일을 덮어쓰지 않고 합쳐요.
- 스킬 폴더의 이름, 훅 파일의 이름이나 위치를 바꾸면 `INSTALL.md`와 세션 시작 훅의 `VERSION` 경로를 함께 고쳐요.
- 프로젝트 안에 설치한 세션 시작 훅은 `@eli-design/ui`가 아직 설치되지 않았어도 지침을 출력해요.

## 소스 배포와의 연결을 준비해요

목표 UI 설치 진입점은 [패키지 매니저 지침](package-managers.md#소스-추가를-기본-소비-방식으로-준비해요), 설치 데이터와 하네스 호출의 완료 기준은 [레지스트리 지침](registry.md#하네스가-설치-도구를-호출할-수-있게-준비해요)에서 관리해요. 이 절은 후속 연결 계약이며 현재 스킬·훅·설치 안내가 이를 구현했다고 표현하지 않아요.

UI가 소스로 설치된 프로젝트는 실제 설치 기록·파일을 확인해요. 전체 npm 패키지가 없다는 이유만으로 UI가 없다고 판단하거나 자동으로 전체 패키지를 추가하지 않아요. 사용 의미는 MCP와 같은 문서 원본에서 읽고 실제 import 경로는 설치 도구의 결과·기록에서 확인해요.

UI 콘텐츠·설치 도구·하네스의 버전은 [버전 기준](versioning.md#설치-도구와-콘텐츠-버전을-구분해요)에 따라 구분해요. 하네스 독립 설치, 훅 병합과 기존 스킬의 소스 설치 지원은 담당 개발자가 구현해요. 그때 아래의 패키지 버전 점검과 업데이트 절차도 실제 구조에 맞춰 함께 바꿔요.

## 로컬 하네스의 기능

| 명령 | 하는 일 |
| --- | --- |
| 기본 동작 | 사용자가 디자인 수정이나 변경을 요청하면 원격 MCP에서 ELI 문서를 읽은 뒤 작업해요. 명령을 입력하지 않아도 적용돼요. |
| `/eli-setup` | 처음 셋업할 때 써요. 기획과 레퍼런스를 묻고, 문서 세 개와 디자인 시스템을 만들고, 피드백으로 다듬어요. |
| `/eli-doctor` | 설치·버전·폰트·토큰 파일·원격 연결을 점검하고 다음에 쓸 명령을 안내해요. 코드를 바꾸지 않아요. |
| `/eli-design-md` | 사용자에게 질문해서 `DESIGN.md`를 만들어요. 서비스 기획, 사용자 예시, 지향하는 제품(당근, 토스 등)을 물어요. |
| `/eli-design-system` | ELI로 디자인 시스템을 구축하고, 디자인 시스템 페이지를 만들어 로컬에서 띄워 보여줘요. |
| `/eli-verify` | 프론트엔드 코드 전체에서 디자인 시스템을 따르지 않는 코드와 모바일 웹에서 깨지기 쉬운 화면을 찾아 보고하고 고쳐요. |
| `/eli-update` | 프로젝트가 쓰는 `@eli-design/ui`의 버전을 원격으로 확인하고, 새 버전이 있으면 알린 뒤 올려요. 패키지 안의 스킬과 훅도 다시 복사해요. |
| `/eli-ux-writing` | 사용자에게 질문해서 문구 규칙을 `UX-WRITING.md`로 정하고, 그 규칙에 맞게 화면의 문구를 다듬어요. |
| `/eli-icon` | `ICON.md`에 아이콘 스타일을 정하고, 화면에 크게 보이는 커스텀 아이콘을 같은 톤으로 만들어요. 작은 UI 아이콘은 `@eli-design/ui`의 아이콘을 써요. |

명령마다 `packages/harness/skills/<명령 이름>/SKILL.md` 파일 하나를 둬요. 기본 동작과 원격 연결 방법은 `skills/eli/SKILL.md`에 있어요.

- 원격 MCP의 주소는 `skills/eli/SKILL.md` 한 곳에만 적어요. 다른 스킬은 서버 이름 `eli-docs`로만 가리켜요.
- 스킬은 [원격 MCP 규격](mcp-spec.md)의 도구 이름, 섹션 키, 가이드 주제를 그대로 써요. 한쪽을 바꾸면 다른 쪽도 함께 고쳐요.
- 스킬이나 훅을 고치면 `pnpm test:harness`를 실행해요. 이 검사는 훅의 출력과 스킬의 형식만 확인해요. 에이전트가 스킬을 실제로 잘 따르는지는 확인하지 않아요.

### 처음 셋업은 단계로 나눠서 해요

1. **묻기:** 서비스의 간략한 기획과 디자인 레퍼런스로 삼을 제품만 물어요.
2. **만들기:** 답을 바탕으로 `DESIGN.md`, `ICON.md`, `UX-WRITING.md`를 만들고, Pretendard를 연결하고, 토큰과 디자인 시스템 페이지를 만들어 로컬에서 띄워요.
3. **다듬기:** 디자인 시스템을 본 사용자의 피드백으로 2단계에서 만든 것을 고치고 발전시켜요. 사용자가 됐다고 할 때까지 반복해요.

4. **옮기기:** 이미 화면 코드가 있는 프로젝트면 이어서 기존 화면 전체를 새 기준으로 리팩토링해요.

- 4단계는 새 브랜치에서 토큰, 단위, 컴포넌트, 문구, 화면 품질 순서의 묶음으로 나눠 고치고, 묶음마다 프로젝트의 검사를 실행해요. 기능과 로직은 바꾸지 않아요.
- 4단계는 조사 결과를 보고한 뒤 승인을 기다리지 않고 고쳐요. 모양이 눈에 띄게 달라지는 변경, 새 토큰이 필요한 값, 뜻이 바뀔 수 있는 문구만 모아서 물어요.
- `/eli-setup`은 문서의 구성과 규칙을 각 명령의 스킬에서 가져와요. 같은 내용을 `eli-setup`에 다시 적지 않아요.
- 사용자가 답하지 않아 추정한 내용에는 `(초안)`을 붙이고, 3단계에서 확인받으면 지워요.
- 피드백은 페이지만 고치지 않고 문서나 토큰 파일을 먼저 고쳐요.
- 훅은 `DESIGN.md`가 없는 프로젝트에서 UI 작업을 요청받으면 `/eli-setup`을 먼저 제안하게 해요.
- `/eli-design-md`, `/eli-ux-writing`, `/eli-design-system`은 셋업 뒤에 한 부분만 다시 만들거나 자세히 정할 때 써요.

### 화면 코드의 기준은 eli 스킬의 references에 둬요

- `skills/eli/references/`에 CSS(`css.md`), 마크업·접근성·React(`code.md`), 화면 디자인(`design.md`) 기준을 둬요. 어느 서비스에나 적용되는 일반 기준이에요.
- `skills/eli/SKILL.md`에는 항상 지킬 핵심 규칙과 어느 문서를 언제 읽는지만 적어요.
- 이 문서들에는 ELI의 컴포넌트 이름, props, 토큰 값을 적지 않아요. ELI 자체의 정보는 원격 MCP가 가져요.
- 기준은 MDN, web.dev, WCAG 2.2, react.dev 같은 1차 자료로 확인한 내용만 적고, 문서 끝에 출처를 남겨요. 실무 관행은 관행이라고 구분해요.
- 브라우저 지원 현황은 시간이 지나면 달라져요. `css.md`의 "써도 되는 기능" 표는 기준 날짜를 적고, 고칠 때 다시 확인해요.
- `/eli-verify`의 화면 품질 점검은 이 문서들을 기준으로 써요.

### 현재 실험 구조의 버전 점검

아래는 현재 UI·스킬이 같은 패키지에 담기는 구조의 동작이에요. 후속 소스 배포의 버전 의미는 앞의 연결 계약을 따라요.

- 소비 프로젝트의 `DESIGN.md`에 `## 버전`을 둬요. 쓰는 `@eli-design/ui`의 버전, 프로젝트에 복사한 스킬의 버전, 마지막으로 확인한 날짜를 적어요.
- 세션 시작 훅은 두 가지를 알려요. 날짜가 14일이 지났으면 `/eli-update`로 확인하라고 알리고, 설치된 패키지와 복사한 스킬의 버전이 다르면 다시 복사하라고 알려요. 훅은 파일만 읽고 네트워크를 쓰지 않아요.
- 새 버전이 있는지는 `/eli-update`가 원격 MCP의 `get_versions`로 확인해요. 원격에 연결할 수 없으면 추측하지 않고 날짜도 갱신하지 않아요.
- 새 버전이 있으면 무엇이 바뀌는지 보여주고 한 번 확인받은 뒤 올려요. 의존성과 훅을 말없이 바꾸지 않아요.
- 스킬과 훅은 설치된 패키지 안의 파일을 복사해서 올려요. 원격 서버가 알려준 주소나 저장소에서 받지 않아요. 서버가 뚫려도 사용자의 컴퓨터에서 코드가 실행되는 통로가 되지 않게 하기 위해서예요.
- 스킬을 다시 복사할 때 사용자가 고친 파일은 덮어쓰기 전에 물어요. `DESIGN.md`, `UX-WRITING.md`, `ICON.md`와 토큰 파일은 건드리지 않아요.

### 문서 세 개는 초안을 가져와 맞춰 써요

- `DESIGN.md`, `ICON.md`, `UX-WRITING.md`의 상세한 초안을 각 스킬 폴더의 `template.md`에 둬요. 스킬은 문서를 처음부터 새로 쓰지 않고, 초안을 가져와 사용자의 서비스에 맞게 고쳐요.
- 초안의 `{중괄호}`는 채울 자리이고, `<!-- 맞춤: ... -->` 주석은 어떻게 고칠지 알려주는 지시예요. 저장한 문서에는 둘 다 남기지 않아요.
- 초안에는 여러 서비스에 공통으로 맞는 기본 내용만 적어요. ELI의 컴포넌트 이름, props, 토큰 값은 적지 않아요.
- 문서의 구성을 바꿀 때는 `template.md`를 고쳐요. 스킬에는 구성을 다시 적지 않아요.
- `ICON.md` 초안의 형태 값(캔버스, 선 굵기, 모서리 반경)은 임시 기본값이에요. 디자이너의 규칙을 원격 `icon` 가이드에 적으면 그 값이 먼저 적용돼요.

### 기본 동작

- `hooks/session-start.mjs`는 세션을 시작할 때 프로젝트가 `@eli-design/ui`를 쓰는지 확인하고, 쓰는 경우에만 짧은 지침을 출력해요. [ponytail](https://github.com/DietrichGebert/ponytail)의 SessionStart 훅 방식을 참고해요.
- 주입하는 지침은 "UI를 수정하기 전에 원격 MCP에서 해당 컴포넌트 문서를 읽어요" 수준으로 짧게 유지해요.

### 글꼴은 Pretendard로 고정해요

- 소비 프로젝트의 전역 글꼴은 Pretendard예요. 하네스는 다른 글꼴을 제안하거나 고르게 하지 않아요.
- ELI의 타이포그래피 토큰은 글자 크기, 굵기, 줄 높이, 자간이 Pretendard에 맞춰져 있어요. 글꼴을 바꾸면 자간과 정렬이 깨져요.
- 하네스는 `--eli-font-family-sans`를 다시 정하지 않고, 화면 코드에 `font-family`나 `letter-spacing`을 따로 쓰지 않게 해요.
- `/eli-design-system`은 Pretendard Variable을 전역 진입점에서 한 번 불러오게 해요. 방법은 `skills/eli-design-system/fonts.md`와 원격 `font` 가이드에서 관리해요.
- 사용자가 다른 글꼴을 원하면 고정인 이유를 알리고 굵기, 크기, 색, 여백으로 조절하자고 제안해요.
- 글꼴 자체를 바꿀 수 있게 하려면 `@eli-design/ui`의 타이포그래피 토큰부터 바꿔야 해요. 하네스에서 먼저 풀지 않아요.

### 프로젝트 토큰을 반드시 만들고 전역에서 써요

- `/eli-design-system`은 소비 프로젝트의 토큰 파일을 반드시 만들어요. 이 단계는 건너뛸 수 없어요.
- 프로젝트 토큰은 역할로 이름을 짓고 ELI 토큰을 가리켜요. 값을 직접 쓰는 곳은 토큰 파일 하나뿐이에요.
- 기본 동작과 훅은 모든 스타일 작업에서 프로젝트 토큰만 쓰게 해요. 필요한 토큰이 없으면 값을 직접 쓰지 않고 토큰 파일에 먼저 추가해요.
- `/eli-verify`는 토큰 파일 밖의 값과 화면 코드의 `--eli-` 변수를 위반으로 보고해요.
- `hooks/post-edit.mjs`는 에이전트가 화면 파일을 고칠 때마다 직접 쓴 색상 값을 찾아 바로 알려요. 간격과 글자 값은 오탐이 많아서 `/eli-verify`가 맡아요.
- 사람이 직접 쓴 코드는 `/eli-verify`를 실행해야 잡혀요. 린트 규칙처럼 빌드를 막는 장치는 아직 없어요.

### DESIGN.md에 CSS 단위 기준을 반드시 적어요

- `/eli-design-md`와 `/eli-setup`은 `DESIGN.md`에 `## 단위` 표를 항상 적어요. 글자는 `rem`, 레이아웃은 `%`와 `fr`, 화면 높이는 `dvh`, 테두리는 `px`처럼 용도별로 무엇을 쓰는지와 그 이유를 적어요.
- 기본 표는 `skills/eli-design-md/template.md`에서 관리해요.
- 기본 동작은 CSS 값을 쓸 때 이 표에서 단위를 고르게 하고, `/eli-verify`는 표와 다른 단위를 보고해요.
- 글자 크기, 간격, 모서리는 토큰으로 쓰므로, 이 표는 새 토큰을 정할 때와 토큰이 다루지 않는 레이아웃 크기에 적용해요.

### 문구는 UX-WRITING.md를 만들고 그 문서대로 써요

- `/eli-ux-writing`은 첫 문구를 다듬기 전에 소비 프로젝트의 루트에 `UX-WRITING.md`를 만들어요. 말투, 호칭, 톤, 문구 형식, 용어, 표기를 좋은 예와 나쁜 예로 적어요.
- 기본 동작과 훅은 화면에 보이는 모든 문구를 `UX-WRITING.md`대로 쓰게 해요. 문서가 없으면 먼저 만들자고 안내해요.
- `/eli-verify`는 규칙과 다른 문구를 보고하고, `/eli-doctor`는 문서가 있는지 확인해요.
- 문구를 다듬을 때 뜻, 숫자, 조건은 바꾸지 않아요. 약관 같은 법적 문서는 다듬지 않아요.
- 이 규칙은 소비 프로젝트의 화면 문구에 적용해요. ELI 저장소의 문서는 [글쓰기 지침](writing.md)을 따라요.

### 디자인 시스템은 @eli-design/ui로 만들어요

- 엘리가 만드는 디자인 시스템의 컴포넌트는 `@eli-design/ui`예요. 버튼이나 입력창을 직접 새로 만들지 않고, 다른 UI 라이브러리를 추가하지 않아요.
- 프로젝트 토큰은 ELI 토큰을 가리켜요. 글꼴은 Pretendard로 고정이고 `--eli-font-family-sans`를 그대로 써요.
- ELI에 없는 컴포넌트만 ELI 컴포넌트와 프로젝트 토큰을 조합해 직접 만들고, 디자인 시스템 페이지에서 구분해서 보여줘요.
- 프레임워크가 정해지지 않아 HTML로 만들 때는 React 컴포넌트를 실행할 수 없어요. 이때는 토큰과 방향만 보여주고, 실제 컴포넌트가 아니라고 페이지에 적어요.

### 디자인 시스템 페이지는 로컬에서만 띄워요

- 사용자의 프로젝트가 쓰는 프레임워크나 라이브러리 위에 페이지를 만들고, 그 프로젝트의 개발 서버로 띄워요.
- 프로젝트에서 쓸 라이브러리가 아직 정해지지 않았으면 HTML 파일로 만들어 로컬에서 띄워요.
- 외부에 배포하지 않아요. 배포 명령을 실행하거나 배포 설정을 추가하지 않아요.

### verify는 보고한 뒤 고쳐요

- 먼저 코드를 바꾸지 않고 위반 목록을 보고해요.
- 판단 기준이 되는 토큰과 컴포넌트 목록은 원격 MCP에서 조회해요.
- 원격에서 확인하지 못한 항목은 통과로 적지 않고 "확인하지 못했어요"로 구분해요.

### 아이콘은 ICON.md를 만들고 그 문서대로 만들어요

- 커스텀 아이콘을 남발하지 않아요. 기본은 ELI의 선 아이콘이에요. 커스텀 아이콘과 선 아이콘을 고르는 판단표는 `skills/eli-icon/SKILL.md`에서 관리하고, 빈 화면·온보딩처럼 화면의 메시지를 대표하는 자리에만 한 화면에 하나씩 써요.
- 첫 아이콘을 만들기 전에 소비 프로젝트의 루트에 `ICON.md`를 만들어요. 톤, 형태, 색, 파일 규칙, 만든 아이콘 목록을 적어요.
- 이후의 모든 아이콘은 `ICON.md`를 읽고 따라요. 프로젝트 전체의 아이콘이 같은 톤으로 나오게 하기 위해서예요.
- 스타일을 바꿀 때는 아이콘 하나만 고치지 않고 `ICON.md`를 먼저 고쳐요.
- `ICON.md`의 기본값이 되는 그리드, 선 굵기, 색 규칙은 원격 `icon` 가이드에서 조회해요. 디자이너에게 전달받지 않은 규칙을 임의로 만들지 않아요.

## 정하지 않은 것

- **업그레이드 안내:** npm 배포는 시작했지만 버전을 올릴 때 바뀐 API를 찾아 주는 기능은 만들지 않았어요. 원격 MCP의 버전별 변경 내역 제공과 함께 검토해요.
- **하네스 설치 명령:** 현재는 에이전트가 `INSTALL.md`를 읽고 파일을 복사해요. UI의 목표 진입점은 정했지만 하네스 독립 설치의 명령과 연결은 담당자와 정해야 해요.
- **Codex의 편집 훅:** `post-edit.mjs`는 Claude Code의 입력 형식(`tool_input.file_path`)만 읽어요. Codex는 `apply_patch`의 입력 형식이 달라서 아직 지원하지 않아요.
- **아이콘 규칙:** 디자이너에게 전달받아야 해요.
