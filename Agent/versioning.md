# 버전 규칙

`@eli-design/ui` 안의 모든 컴포넌트와 토큰은 하나의 버전을 사용해요. [SemVer](https://semver.org/lang/ko/)의 `MAJOR.MINOR.PATCH` 형식을 따라요.

| 변경 | 버전 | 예시 |
| --- | --- | --- |
| 기존 사용법과 호환되지 않아요 | MAJOR | 공개 props·경로·CSS 변수 삭제 또는 이름 변경 |
| 기존 사용법을 유지하며 기능을 추가해요 | MINOR | 새 컴포넌트·선택적 prop·variant |
| 기존 계약을 유지하며 오류를 고쳐요 | PATCH | 명세와 다른 스타일·동작·접근성 오류 수정 |

## 초기 버전을 관리해요

npm scope는 `@eli-design`이에요. 패키지 이름은 `@eli-design/ui`예요. 라이선스는 MIT예요. 루트 `LICENSE`를 고치면 tarball에 들어가는 `packages/ui/LICENSE`도 같게 맞춰요. 이름, 로고, 마스코트의 사용 기준은 루트 `TRADEMARKS.md`에서 관리해요. 첫 게시 버전은 `0.0.0`이에요. 아직 게시하지 않았어요. 소비 프로젝트의 `^0.0.0`은 `0.0.0`만 뜻하므로, 실제로 쓰기 시작하는 버전은 `0.1.0`부터 올려요. `0.x`에서는 호환성 변경과 기능 추가에 MINOR, 호환되는 오류 수정에 PATCH를 올려요. 이는 ELI의 개발 단계 운영 규칙이에요.

안정된 공개 API와 사용 규칙을 지원하는 첫 정식 버전을 `1.0.0`으로 정해요. 사전 배포는 `1.0.0-beta.1`처럼 쓰고 npm `next` 태그를 사용해요. 정식 배포는 `latest`를 사용해요.

## 변경 영향을 기록해요

공개 props·import 경로·CSS 변수·기본 동작·문서로 약속한 디자인을 호환성 판단에 포함해요. 명세대로 고치는 스타일 수정과 새 디자인으로 바꾸는 변경을 구분해요.

README·JSDoc·지침·Storybook 설명만 바뀌고 공개 계약과 동작이 달라지지 않으면 버전을 올리지 않아요. 패키지 파일이 달라지면 버전을 올리지 않더라도 용량은 다시 측정해요. 여러 변경을 묶을 때는 가장 큰 변경 유형을 적용해요. PR에는 예상 유형을 기록하고 릴리스 준비 때 패키지 버전을 한 번 올려요.

릴리스 때 루트 `CHANGELOG.md`에 사용자에게 달라지는 점과 이전 방법을 기록해요. 패키지 버전·lockfile·태그(`v0.0.0` 형식)를 일치시켜요. 이미 배포한 버전은 재사용하지 않아요. npm 게시와 Git 태그 생성은 실제 릴리스 작업에서 진행해요.

## 선택 설치 데이터의 버전

레지스트리는 UI와 같은 릴리스 버전을 사용해요. JSON 형식의 호환성은 별도 `schemaVersion`으로 구분해요. 실제 파일 구성과 설치 경로도 소비자의 사용 계약이므로 변경 시 이전 방법을 안내해요. 로컬 생성만으로 npm 게시나 GitHub Release가 완료되지는 않아요. 상세 계약과 CLI·하네스 담당자의 경계는 [레지스트리 지침](registry.md)을 따라요.

## 하네스의 버전

- 하네스는 `@eli-design/ui` 패키지에 함께 들어가요. 버전은 `packages/ui/package.json`의 `version` 하나예요. 하네스의 버전을 따로 두지 않아요.
- 스킬, 훅, 초안, 참고 문서, `INSTALL.md`를 바꾸는 것도 패키지의 변경이에요. 릴리스할 때 변경 내역에 함께 적어요.
- 설치 방법이 달라지거나 사용자가 다시 확인해야 하는 훅 변경은 MINOR, 스킬의 문구와 규칙만 고친 변경은 PATCH를 올려요.
- 원격 MCP와 호환되지 않게 바뀌면 [원격 MCP 규격](mcp-spec.md)의 `harness.minimum`을 함께 올려요.
- 소비 프로젝트는 쓰는 버전과 마지막으로 확인한 날짜를 `DESIGN.md`의 `## 버전`에 적어요. 확인과 올리기는 `/eli-update`가 맡아요.
