# 버전 규칙

현재 실험 패키지 `@eli-design/ui`의 컴포넌트·토큰·함께 배포하는 하네스는 `packages/ui/package.json`의 버전 하나를 사용해요. 이는 현재 빌드 구조이며 미래의 설치 도구까지 같은 버전이어야 한다는 규칙은 아니에요. [SemVer](https://semver.org/lang/ko/)의 `MAJOR.MINOR.PATCH` 형식을 따라요. 이 문서는 정책, [릴리스 절차](../handbook/releasing.md)는 실행 순서와 결과 기록을 관리해요.

## npm 배포와 공식 홍보를 구분해요

`@eli-design/ui`는 npm에 게시되어 있어요. 공식 홍보 전에는 `0.x.y`를 사용하고, 팀이 공식 홍보를 시작하기로 결정한 릴리스를 `1.0.0`으로 정해요. npm 게시나 PR 병합만으로 홍보 시작을 판단하지 않아요.

현재는 외부 사용자가 없는 실험 단계예요. npm 게시 사실만으로 기존 패키지명·API·배포 방식을 계속 지원해야 한다고 판단하지 않아요. 사용성을 위한 구조 변경을 허용하고, 패키지 역할과 이름도 다시 정할 수 있어요. 바뀐 계약과 공개 범위는 아래 변경 유형과 기록 규칙에 따라 남겨요. 이미 게시한 버전의 재사용 제한은 실험 단계에도 적용해요.

| 단계 | 호환성이 깨지는 변경 | 호환되는 기능 추가 | 호환되는 오류 수정 |
| --- | --- | --- | --- |
| 공식 홍보 전 `0.x` | MINOR | MINOR | PATCH |
| 공식 홍보 시작 | `1.0.0`으로 전환해요 | `1.0.0`으로 전환해요 | `1.0.0`으로 전환해요 |
| 공식 홍보 후 `1.0.0` 이상 | MAJOR | MINOR | PATCH |

예를 들어 `0.2.3`의 기능 추가나 호환성 변경은 `0.3.0`, 오류 수정은 `0.2.4`예요. `1.2.3`의 호환성 변경은 `2.0.0`, 기능 추가는 `1.3.0`, 오류 수정은 `1.2.4`예요. MINOR를 올리면 PATCH를, MAJOR를 올리면 MINOR와 PATCH를 0으로 초기화해요.

`0.x`의 MINOR 규칙은 ELI의 초기 운영 정책이에요. 이 단계에서도 호환성이 깨지면 커밋·PR에 `!`와 `BREAKING CHANGE`, 이전 방법을 적어요. `1.x` 유지가 필요하다는 이유로 호환성 변경을 MINOR나 PATCH로 배포하지 않아요.

`0.0.0`도 이미 게시한 버전이므로 재사용하지 않아요. `^0.0.0`은 다음 버전으로 자동 갱신되지 않으며, 일반적인 `^0.x.y` 범위도 다음 MINOR를 포함하지 않아요. 소비 프로젝트의 의존성 범위와 lockfile을 함께 확인해요.

## 공개 계약과 변경 유형을 판단해요

공개 props·타입·import 경로·CSS 변수·커스터마이징 경로·기본 동작·문서로 약속한 디자인을 호환성 판단에 포함해요. 받은 명세대로 고치는 오류 수정과 새 디자인으로 바꾸는 변경을 구분해요. 지원 React 범위를 줄이거나 설치 조건을 강화하는 변경도 호환성 검토 대상이에요.

- 저장소의 README·지침·Storybook만 바뀌고 npm 배포 파일이 바뀌지 않으면 UI 버전을 올리지 않아요.
- 패키지에 포함된 README·타입 선언의 JSDoc·하네스 같은 파일을 바꾸어 **다시 게시하려면 새 버전이 반드시 필요해요**. 설명만 고친 배포는 PATCH가 기본이고 기능·호환성이 달라지면 더 큰 변경 유형을 적용해요.
- 내부 도구·문서 앱의 의존성만 바뀌면 UI 실행 코드·타입·배포물에 영향이 있는지 먼저 확인해요. 개발 도구 버전과 UI 버전을 기계적으로 함께 올리지 않아요.
- 여러 변경을 묶으면 가장 큰 변경 유형을 적용해요. 최종 번호는 실제 npm 게시 버전과 전체 미배포 변경을 비교한 뒤 정해요.

라이선스는 MIT예요. 루트 `LICENSE`를 바꾸면 tarball의 `packages/ui/LICENSE`도 맞춰요. 이름·로고·마스코트는 루트 `TRADEMARKS.md`를 기준으로 확인해요.

## 미배포 변경을 기록해요

사용자에게 영향을 주는 변경은 해당 PR에서 루트 `CHANGELOG.md`의 `Unreleased`에 적어요. 추가·변경·수정·이전 방법을 구분하고 관련 PR을 연결해요. 코드에서 확인한 변경만 기록하며, CLI·MCP·레지스트리의 준비 상태와 실제 제공 여부를 구분해요.

PR마다 패키지 버전을 올리지는 않아요. `main`에 게시 이후 변경이 쌓여도 다음 릴리스 준비 전까지 버전 숫자가 그대로일 수 있어요. 이것을 현재 `main`의 내용이 이미 npm에 올라갔다는 뜻으로 설명하지 않아요.

릴리스 준비 PR에서 미배포 변경을 묶고 버전을 한 번 올려요. `Unreleased`의 해당 내용을 확정 버전 구역으로 옮기며, 게시 예정 날짜는 예정으로 표시하고 게시 후 실제 날짜를 확인해요. GitHub Release 본문은 같은 변경 기록을 사용해요. 자동 CHANGELOG·버전 증가·npm 게시 도구는 현재 없어요.

기존 `0.0.0`의 기록은 npm 메타데이터로 확인한 게시 사실만 남겨요. 게시 원본 커밋과 검증 기록이 확인되지 않으면 미확인으로 적고 최신 `main`에 과거 태그를 임의로 붙이지 않아요.

## 버전과 배포 태그를 구분해요

일반 사용자가 받는 버전은 npm `latest`가 가리켜요. 공식 홍보 전의 `0.x`도 일반 배포할 수 있어요. `0.3.0-beta.1`, `1.0.0-beta.1` 같은 시험 버전은 `next`를 사용하고 `latest`에 연결하지 않아요.

일반 배포 후보도 먼저 `next`로 게시해 실제 설치를 확인한 다음 `latest`로 승격해요. 이는 npm에 공개되는 실제 버전이며 비공개 임시 배포나 npm의 별도 staged publishing 기능을 뜻하지 않아요. 동시에 여러 릴리스를 진행하지 않고 기존 태그 값을 기록한 뒤 변경해요.

사전 배포와 일반 버전은 다른 번호예요. beta 파일의 이름만 바꾸거나 태그만 옮겨 정식 버전으로 만들지 않아요. 일반 버전으로 다시 패키징하고 검증해요. npm 배포 태그 변경과 Git 태그 `v{version}` 생성은 서로 다른 작업이에요.

## 같은 배포 후보를 검증하고 게시해요

아래는 현재 npm UI 패키지를 게시할 때의 기준이에요. 목표 소스 배포에서 설치 도구·콘텐츠·하네스의 버전을 한 숫자로 강제하지 않아요. 실제 릴리스 대상의 버전·원본·검증 파일을 각각 확인해요.

릴리스 PR 병합 후의 깨끗한 `main` 커밋을 배포 기준 SHA로 고정해요. 패키지 버전, lockfile에 있는 관련 참조, CHANGELOG와 레지스트리 버전이 일치해야 해요.

검사 후 만든 최종 tarball의 파일명·integrity·SHA·크기를 기록하고 **그 파일을 검증하고 게시해요**. 검증 뒤 소스·의존성·빌드 결과를 바꾸거나 다시 패키징하면 후보를 새로 검증해요. 각 검사 도구가 자체 생성한 tarball의 통과 결과만으로 최종 게시 파일까지 검증했다고 표현하지 않아요.

npm 게시 완료 후 명시적 버전의 격리 설치와 integrity를 확인해요. Git 태그·GitHub Release는 고정한 같은 커밋을 가리키고 레지스트리 JSON도 그 커밋에서 만든 파일을 사용해요. 외부에 보이는 문서의 버전도 실제 게시 버전과 맞춰요. 구체적인 순서와 실패 시 처리는 [릴리스 절차](../handbook/releasing.md)를 따라요.

공식 홍보용 `1.0.0`도 검사 예외가 아니에요. 공개 계약·이전 안내·지원 환경·실제 수행한 검증과 미검증 범위를 검토해요. npm 게시를 접근성·실기기·문서·MCP 검증 완료로 대신하지 않아요.

## 설치 도구와 콘텐츠 버전을 구분해요

목표 소스 배포에서는 아래 버전을 별도로 식별해요. 새 패키지나 버전 파일을 이번 문서 변경만으로 만들지 않아요.

설치 도구와 UI 콘텐츠에도 공식 홍보 전 `0.x` 원칙을 적용하되 같은 번호로 강제하지 않아요. 정수인 `schemaVersion`은 JSON 규격을 위한 별도 번호예요.

| 대상 | 뜻 |
| --- | --- |
| 설치 도구 버전 | `eli-design` 실행 파일의 버전. `@latest`는 이 도구를 선택해요 |
| UI 콘텐츠 버전 | 레지스트리가 제공하는 컴포넌트·토큰·공유 파일의 릴리스 버전 |
| 규격 버전 | 목록·항목 JSON을 해석하는 `schemaVersion` |
| 하네스·MCP 호환 범위 | 담당자가 합의한 설치 기록·사용 가이드·응답 계약의 지원 범위 |

최신 설치 도구 실행만으로 복사한 UI가 최신이 되거나 같은 버전의 하네스가 설치됐다고 판단하지 않아요. 설치 기록에 UI 콘텐츠 버전과 실제 파일 상태를 남기고, UI 갱신은 별도 변경 계획과 사용자 수정 파일 확인을 거쳐요. 한 프로젝트의 공통 파일과 설치 항목은 같은 콘텐츠 릴리스를 사용해요.

현재 콘텐츠 버전은 생성기가 `packages/ui/package.json`에서 읽어요. 향후 버전 원본이나 배포물 구성을 바꾸면 생성기·검사·릴리스 기록을 함께 갱신해요. 실제 공개 시 설치 도구가 지원하는 규격·콘텐츠 범위를 명시하고, MCP·하네스의 버전 필드 의미는 담당자와 함께 변경해요.

## 선택 설치 데이터의 버전

레지스트리의 `version`은 UI 콘텐츠 릴리스 버전이고 JSON 형식의 호환성은 별도 `schemaVersion`으로 구분해요. 현재는 UI 패키지 manifest와 같은 번호를 읽지만 전체 UI 패키지를 npm에 먼저 게시해야 한다는 조건은 아니에요. 파일 구성과 설치 경로도 소비 계약이므로 변경 시 이전 방법을 안내해요. 로컬 생성은 npm 게시나 GitHub Release 완료를 뜻하지 않아요. 상세 계약과 담당 경계는 [레지스트리 지침](registry.md)을 따라요.

## 하네스의 버전

현재 하네스는 `@eli-design/ui`에 포함되므로 같은 버전을 사용해요. 스킬·훅·초안·참고 문서·설치 안내 변경도 실제 배포물에 반영된다면 위의 변경 유형과 재게시 규칙을 적용해요. 하네스가 별도 배포물로 분리될 때 버전·호환성 정책은 담당 개발자와 합의해 갱신해요.

원격 MCP와 호환되지 않게 바뀌면 [원격 MCP 규격](mcp-spec.md)의 `harness.minimum`도 함께 검토해요. 소비 프로젝트는 쓰는 버전과 확인 날짜를 `DESIGN.md`에 남겨요. 하네스 설치·훅·업데이트의 상세 구현은 담당자의 범위예요.

기준 자료는 [SemVer](https://semver.org/lang/ko/), [npm 배포 태그](https://docs.npmjs.com/adding-dist-tags-to-packages/), [npm publish](https://docs.npmjs.com/cli/commands/npm-publish/)예요.
