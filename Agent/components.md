# 컴포넌트 구현 규칙

## 받은 디자인을 구현해요

디자이너가 제공한 색상·타이포그래피·상태·크기·반응형 기준을 확인해요. 누락된 명세는 확정된 사실처럼 채우지 않아요. 검증용 임시 값을 배포 소스에 추가하지 않아요.

## 선택 기준을 함께 제공해요

컴포넌트는 사용할 수 있는 props만 나열하지 않고, 개발자가 상황에 맞는 값을 고를 수 있도록 선택 기준을 함께 제공해요. `color`, `variant`, `size`처럼 의미 있는 선택지가 둘 이상이라면 구현 전에 [디자이너 협업 가이드](../handbook/designer-guide.md#선택-기준을-합의해요)에 따라 사용 원칙을 합의해요.

합의되지 않은 기준은 개발자가 디자인만 보고 추측하지 않아요. 협업 가이드에 `미정`으로 남기고, 확정된 범위만 JSDoc과 Storybook에 반영해요.

허용 값과 기본값은 prop 설명에서 확인할 수 있게 하고, 선택 이유는 컴포넌트 JSDoc의 `선택 가이드`와 Storybook에서 확인할 수 있게 해요. 선택지가 없는 컴포넌트에는 형식만 맞추기 위한 빈 가이드를 만들지 않아요. 초보 개발자가 소스 코드를 읽지 않고도 어떤 값을 왜 골라야 하는지 설명할 수 있어야 완료된 것으로 봐요.

## 색상 토큰의 역할을 구분해요

디자이너가 전달한 Color Variables 91개를 구현해요. 원시 색상 52개는 `tokens/colors.css`, 사용 목적과 상태를 나타내는 의미 색상과 효과 39개는 `tokens/semantic-colors.css`에서 관리해요. `tokens/index.css`는 두 파일을 연결해요.

- 단계가 있는 원시 색상은 `--eli-color-{색상}-{단계}` 형식으로 작성하고, 고정된 흰색과 검은색은 `--eli-color-static-{색상}` 형식으로 작성해요.
- 의미 색상은 Figma의 `{Category}/{Group?}/{Role 또는 강도}/{State?}` 계층을 순서대로 kebab-case로 바꾸고 `--eli-` 접두사를 붙여요.
- Category는 `foreground`, `background`, `border`, `effect`를 사용해요. `interaction` Group은 Hover·Pressed 같은 상태가 있는 Background와 Border에만 사용해요.
- 강조 강도는 `strong`, `default`, `subtle` 순서로 구분해요. 상호작용 상태는 Figma에 정의된 `default`, `hover`, `pressed`, `disabled`, `focused`를 사용해요.
- 반투명 변형은 이름 끝에 `-alpha`를 붙여요. 화면을 덮는 Dim과 그림자는 각각 `--eli-effect-dim`, `--eli-effect-shadow`를 사용해요.
- 컴포넌트에서는 원시 색상보다 의미 색상 토큰을 우선 사용해요. 원시 색상은 의미 색상을 연결할 때 사용해요.
- 투명도는 `rgb(from var(--eli-color-...) r g b / 30%)` 형식으로 한 줄에 작성해요.
- 같은 의미 토큰을 중복 선언하지 않아요. 같은 원시 색상을 참조하더라도 Foreground와 Background처럼 역할이 다르면 의미 토큰을 각각 유지해요.
- 디자이너가 확정하지 않은 색상이나 상태 토큰은 임의로 추가하지 않아요.

## 타이포그래피 기준을 지켜요

기본 글꼴은 `Pretendard Variable`이에요. 컴포넌트에서는 `--eli-font-family-sans`를 사용하고 소비 앱 전체의 `font-family`를 강제로 바꾸지 않아요. 시스템에 Variable 글꼴이 없으면 `Pretendard`와 시스템 글꼴 순서로 대체해요.

`@eli-design/ui`에는 폰트 파일, 원격 CDN import, 폰트 패키지 의존성을 포함하지 않아요. 초기 설정 도구가 소비 프로젝트에 Pretendard를 한 번 설치하고 로딩 설정을 추가해요. 소비 프로젝트가 이미 Pretendard를 불러오고 있다면 같은 설정을 중복으로 추가하지 않아요.

초기 설정 도구를 구현할 때는 Pretendard Variable의 동적 서브셋을 기본안으로 검증해요. 설치할 패키지와 정확한 버전, 프레임워크별 연결 방식은 구현 시점에 고정하고 다운로드 용량을 기록해요. 글자 크기·행간·굵기 같은 세부 타이포그래피 토큰은 디자이너가 확정한 값만 추가해요.

## 타이포그래피 크기 토큰을 재사용해요

타이포그래피의 기본 크기는 `tokens/typography.css`에서 `--eli-size-{기준 픽셀값}` 형식으로 관리하고 값은 `rem`으로 작성해요. 디자인 환산 기준은 `1rem = 16px`이며 라이브러리가 소비 앱의 루트 글자 크기를 강제로 설정하지 않아요. 모바일과 데스크탑 값이 같으면 하나의 토큰만 선언해요. 값이 달라지는 토큰은 디자이너가 확정한 반응형 기준을 받은 뒤 의미 토큰에서 재정의해요.

기본 굵기도 `tokens/typography.css`에서 `--eli-font-weight-{이름}` 형식으로 관리해요. 모바일과 데스크탑 값이 같으면 하나의 토큰을 함께 사용해요. Pretendard Variable에서 제공하는 연속적인 굵기 값은 정수 그대로 유지해요.

역할별 글자 크기는 `--eli-font-size-{종류}-{단계}` 형식으로 기본 크기 토큰을 참조해요. 데스크탑 값을 기본으로 선언하고 모바일 구간에서 같은 토큰을 덮어써요. Heading의 모바일 재정의는 관련 H1~H4 클래스 바로 다음에 배치해 두 값을 한 번에 확인할 수 있게 해요. 별도의 `-mobile`, `-desktop` 토큰을 중복으로 공개하지 않아요.

여러 컴포넌트가 같은 타이포그래피 조합을 사용하면 `tokens/typography.css`에 `.eli-typo-{이름}` 공통 클래스로 관리해요. Heading은 `.eli-typo-heading-h1`부터 `.eli-typo-heading-h4`, Body는 `.eli-typo-body-medium`과 `.eli-typo-body-small`, Label은 `.eli-typo-label-large`·`.eli-typo-label-medium`·`.eli-typo-label-small`을 사용해요. 별도 토큰이 필요하지 않은 고정 속성은 클래스에 값을 직접 작성해요.

## 레이아웃 기준을 재사용해요

레이아웃 값은 `tokens/layout.css`에서 관리해요. 크기 단계는 `--eli-layout-scale-{단계}` 형식으로 작성하고 디자이너가 전달한 픽셀값을 유지해요. 모바일의 375px은 기준 화면 너비로 기록하고, Tablet 768px과 Desktop 1024px을 반응형 전환 기준으로 사용해요.

CSS 미디어 쿼리 조건에서는 `var()`를 사용할 수 없으므로 `@media`에는 확정된 전환 값을 직접 작성해요. 데스크탑 스타일을 기본으로 두고 `1023px` 이하에서 Tablet, `767px` 이하에서 Mobile 스타일을 덮어써요. 기준이 변경되면 `layout.css`, 미디어 쿼리와 Storybook 반응형 검증을 함께 수정해요.

## 한 번 import하면 스타일이 적용돼요

컴포넌트 파일에서 자신의 CSS를 import해요. 컴포넌트 CSS에서는 공통 토큰 CSS를 상대 경로로 연결해요. 실제 `TextField`를 구현할 때의 예시예요.

```tsx
// src/text/TextField/TextField.tsx
import './TextField.css';
```

```css
/* src/text/TextField/TextField.css */
@import '../../tokens/index.css';
```

소비 코드에는 `import { TextField } from '@eli-design/ui/text'`만 필요해야 해요. JS로 style 태그를 삽입하거나 전용 CSS 프레임워크를 요구하지 않아요.

## 필요한 곳만 바꿀 수 있어요

공통 토큰은 `--eli-` 접두사를 써요. 컴포넌트 변수는 `--eli-text-field-`처럼 대상을 구분해요. 클래스도 `.eli-text-field`처럼 충돌을 줄여요. 전역 reset과 일반 HTML 태그 선택자로 소비 앱의 스타일을 바꾸지 않아요.

컴포넌트 변수는 사용 위치에서 재정의할 수 있도록 공통 토큰 fallback으로 연결해요. 사용자 `className`과 `style`을 전달하고, 한 인스턴스 변경이 다른 인스턴스에 번지지 않는지 확인해요. 공개하는 CSS 변수는 문서로 남겨요.

스타일 도구와 관계없이 생성된 클래스를 `className`으로 전달할 수 있게 해요. ELI의 실행 의존성이나 필수 설정에 Tailwind CSS, Emotion, vanilla-extract 같은 외부 스타일 도구를 추가하지 않아요. 공개 컴포넌트 함수의 JSDoc은 `빠른 사용`, `주요 설정`, 필요한 경우 `선택 가이드`, `내용과 동작`, `스타일 변경` 순서로 짧게 구성해 컴포넌트 hover만으로 사용법을 훑을 수 있게 해요. 허용 값과 기본값은 한 줄로 표시하고, 각 prop의 자세한 설명과 적용 대상은 props 타입에 작성해 prop hover에서 확인하게 해요. 컴포넌트 함수는 `props: {컴포넌트명}Props`로 받은 뒤 본문에서 구조 분해해 hover 시그니처가 불필요하게 길어지지 않게 해요.

모든 공개 컴포넌트의 `className` prop은 타입 파일에 직접 선언하고 실제 적용 대상을 적어요. `className`과 `style`이 바깥 래퍼에 적용되는 컴포넌트에서는 내부 input이나 콘텐츠에도 적용된다고 설명하지 않아요. 내부 영역을 바꾸는 요구가 확인되면 해당 영역만 별도 className prop으로 공개해요.

ELI의 컴포넌트 규칙과 공통 타이포그래피 클래스는 CSS `components` 레이어에서 관리해 소비 앱의 일반 CSS, CSS Modules, CSS-in-JS와 Tailwind utility가 별도의 ELI 토큰이나 `!important` 없이 덮어쓸 수 있게 해요. 색상·크기 같은 토큰 선언은 레이어 밖에 유지해요. 상태 스타일을 바꿀 때는 Default만 바꾸고 Hover·Pressed·Disabled를 놓치지 않도록 각 상태의 예시를 함께 제공해요.

새 컴포넌트를 추가하거나 기존 컴포넌트를 수정할 때는 컴포넌트 hover 설명, prop별 설명, CSS 레이어와 외부 클래스 전달을 함께 확인해요. 패키징 검증에서는 모든 공개 컴포넌트의 설명과 CSS 레이어가 배포 결과에도 남는지 확인해요.

## 접근성과 상태를 확인해요

가능하면 기본 HTML 요소를 사용해요. label, 키보드 조작, focus, disabled, error 상태를 해당 컴포넌트에 맞게 검증해요. 라이브 리전·포커스 이동 같은 복잡한 동작은 실제 명세와 접근성 기준을 확인한 뒤 구현해요.

## 여러 브라우저와 입력 방식을 지원해요

Chrome·Edge의 Chromium, Safari 계열의 WebKit과 Firefox에서 같은 공개 API와 핵심 동작을 유지해요. 마우스 Hover만으로 정보나 기능을 제공하지 않고 키보드와 터치에서도 같은 작업을 완료할 수 있게 해요. 특정 브라우저 전용 API나 아직 널리 지원되지 않는 CSS를 사용할 때는 지원 행렬을 확인하고 필요한 대체 동작을 함께 제공해요.

모바일에서는 좁은 화면, 터치 입력, 가상 키보드와 화면 확대를 고려해요. `hover`가 없거나 포인터가 정밀하지 않은 환경에서도 선택·열기·닫기·입력이 가능해야 해요. 브라우저별 자동 검사와 실제 Android·iOS 확인 범위는 [검증 기준](testing.md#브라우저와-모바일-환경을-구분해-확인해요)을 따라요.

## 빠른 동작을 기본값으로 제공해요

컴포넌트는 작은 예시뿐 아니라 합의한 현실적인 사용 범위에서도 빠르게 반응해야 해요. 긴 목록, 반복 렌더링, 잦은 DOM 탐색과 다수 요소의 동시 애니메이션이 메인 스레드에 주는 비용을 고려해요. 패키지 다운로드 용량이 작다는 사실을 상호작용 성능이 빠르다는 근거로 사용하지 않아요.

성능 문제가 의심되면 먼저 같은 조건에서 측정하고 병목을 확인해요. 측정 전에 가상화, 메모이제이션이나 컴포넌트 구조 변경을 임의로 적용하지 않아요. 긴 목록의 지원 범위와 대체 패턴, 가상화 허용 여부는 [디자이너 협업 가이드](../handbook/designer-guide.md#성능-범위를-합의해요)에 따라 먼저 합의해요.

모션은 가능하면 레이아웃과 페인트 부담이 적은 `transform`과 `opacity`를 우선 검토해요. 다만 전달받은 디자인을 성능을 이유로 임의 변경하지 않고, 측정 결과와 사용자 경험을 근거로 디자이너와 조정해요. 구체적인 측정 조건과 결과 해석은 [검증 기준](testing.md#상호작용-성능을-별도로-확인해요)을 따라요.

## 상태와 상호작용을 Hook으로 분리해요

컴포넌트에서 상태 관리, 제어·비제어 값 처리, 키보드 조작, 포커스 이동, Effect처럼 화면 구조와 분리할 수 있는 동작은 같은 컴포넌트 폴더의 `use{컴포넌트명}.ts`로 분리해요. 새 컴포넌트뿐 아니라 기존 컴포넌트를 수정할 때도 분리할 수 있는 로직이 있는지 확인해요.

Hook은 하나의 동작 책임만 맡도록 구성해요. 화면 마크업·스타일·Storybook 전용 코드를 Hook에 넣지 않고, 시맨틱 HTML과 `aria-*` 연결은 구조를 한눈에 확인할 수 있도록 컴포넌트 파일에 남겨요. 단순히 값을 다시 전달하기만 하는 Hook이나 실제 재사용·가독성 개선이 없는 빈 추상화는 만들지 않아요.

Hook에는 상태, 접근성 ID, 참조, 이벤트 처리처럼 코드의 역할이 드러나는 한국어 주석을 작성해요. 모든 줄을 반복해서 설명하기보다 동작의 목적과 포커스 이동 같은 중요한 이유를 남겨요. 공개 props 타입은 컴포넌트 타입 파일에서 관리하고 Hook 내부에서만 사용하는 타입은 Hook 파일 안에 둬요.

## 클라이언트 경계를 명시해요

State·Effect·Ref 같은 React Hook, 사용자 이벤트 또는 `window`·`document` 같은 브라우저 API를 사용하는 컴포넌트는 파일 맨 위에 `'use client';`를 작성해요. 지시문은 import보다 앞에 두고, 타입·순수 표현 컴포넌트·CSS처럼 클라이언트 기능을 사용하지 않는 파일에는 추가하지 않아요.

클라이언트 컴포넌트가 내부에서 가져오는 `use{컴포넌트명}.ts`는 같은 클라이언트 모듈 그래프에 포함되므로 지시문을 중복 작성하지 않아요. 빌드 결과에서도 클라이언트 컴포넌트 파일의 지시문이 첫 줄에 남아야 해요.

## 서버 렌더링을 지원해요

모든 공개 컴포넌트는 `window`, `document`, `navigator`, `localStorage`, `requestAnimationFrame` 같은 브라우저 전역이 없는 환경에서도 처음 렌더링할 수 있어야 해요. 브라우저 API가 필요한 동작은 모듈 최상위나 렌더링 중에 실행하지 않고 이벤트 처리나 Effect 안에서만 실행해요. 서버와 브라우저의 첫 마크업이 달라지는 값은 렌더링 중에 임의로 만들지 않아요.

Hook과 이벤트를 사용하는 컴포넌트도 서버에서 초기 HTML을 만들 수 있어야 해요. `pnpm test:packaging`은 실제 tarball을 서버용으로 번들한 뒤 모든 공개 컴포넌트를 `react-dom/server`로 렌더링하고, 클라이언트 경계 지시문이 배포 결과에 남는지 확인해요. Next.js 같은 프레임워크 고유 동작은 해당 소비 예제를 추가할 때 별도로 검증해요.

## Storybook을 함께 확인해요

Storybook은 개발자와 디자이너가 같은 컴포넌트를 확인하는 문서로 사용해요. 왼쪽 메뉴의 그룹과 사용자 설명은 한글로 작성하고, 컴포넌트 이름은 `Button`, `TextField`처럼 공개된 영문 이름을 그대로 사용해요.

- Story는 원칙적으로 `한눈에 보기`, `직접 바꿔보기` 두 화면으로 구성해요. 같은 목적의 Story를 상태나 조합마다 나누지 않아요.
- 모바일 배치가 명확한 하단 내비게이션·관련 Item·FAB Menu만 `StoryDeviceFrame`의 `375×640` 모바일 프레임을 사용해요. 웹 컴포넌트는 가상 페이지나 디바이스 프레임으로 감싸지 않아요.
- 모바일 프레임 안에는 검수 대상 컴포넌트만 배치하고 제목·설명·상태명이나 가짜 서비스 화면을 넣지 않아요. 하단 내비게이션은 하단, FAB는 우측 하단처럼 실제 배치 위치를 반영해요.
- `한눈에 보기`의 안내 문구와 조합 이름은 `StoryOverview`와 `StoryCase`를 사용해 컴포넌트 미리보기 밖에 표시해요. Story마다 설명 타이포·간격·구분선을 임의로 만들지 않아요.
- `한눈에 보기`는 크기·형태·색상·상태처럼 디자이너가 검수할 주요 UI를 한 화면에 보여주고 Controls를 숨겨요.
- `직접 바꿔보기`는 공개 props를 Controls에서 조작할 수 있게 하고 컴포넌트 하나만 보여줘요.
- 변경할 공개 prop이 없는 컴포넌트는 형식을 맞추기 위한 `직접 바꿔보기`를 만들지 않아도 돼요.
- 정말 별도 목적이 필요한 Story만 예외로 추가하고, 이름에서 확인 목적을 바로 알 수 있게 해요.
- 전체 조합 화면에는 color, variant, size처럼 비교 기준을 표시해 디자이너가 코드를 보지 않고도 차이를 알 수 있게 해요.
- 선택지가 있는 컴포넌트는 각 값의 이름만 보여주지 않고 합의된 권장 상황과 구분 기준도 확인할 수 있게 해요. 기준이 미정이면 임의로 작성하지 않고 미정 상태를 표시해요.
- Hover와 Pressed는 실제 컴포넌트 상호작용으로 확인하고 확인 방법을 화면에 안내해요. Storybook 전용 스타일로 컴포넌트 상태 디자인을 복제하지 않아요.
- Disabled처럼 상호작용으로 확인하기 어려운 상태는 실제 prop과 전체 조합을 사용해 보여줘요.
- Storybook Controls는 공개 props를 기준으로 제공하고 각 항목의 이름과 설명을 한글로 작성해요.
- `argTypes.name`으로 표시 이름을 바꾼 항목을 `controls.include`나 `controls.exclude`로 필터링할 때는 내부 prop 키가 아니라 Storybook에 표시되는 이름을 사용해요. 가능하면 불필요한 항목을 `argTypes`에서 숨겨 필터 의존성을 줄여요.
- `직접 바꿔보기`를 수정한 뒤에는 Controls가 비어 있지 않은지와 값을 바꿨을 때 실제 컴포넌트에 반영되는지를 실행 중인 Storybook에서 확인해요.
- 배열이나 객체처럼 기본 Object Control에서 한 번에 편집하기 어려운 prop은 `직접 바꿔보기` 안에 항목 추가·수정·삭제 UI를 제공할 수 있어요. 공개 컴포넌트 API를 바꾸지 않고 Storybook 전용 편집 상태로 실제 prop에 연결해요.
- 별도 편집 UI가 필요하면 `StoryPreviewLayout`을 사용해 추가·수정·삭제 영역은 왼쪽, 실제 컴포넌트 미리보기는 오른쪽에 배치해요. 기기 종류와 Canvas 너비에 따라 상하 배치로 바꾸지 않고, 공간이 부족하면 가로로 스크롤해 두 영역의 관계를 유지해요.
- `aria-label`은 Controls에서 `버튼 설명`, `체크박스 설명`, `토글 설명`, `선택 영역 설명`처럼 컴포넌트의 역할이 드러나는 이름으로 표시해요. 화면 낭독기가 언제 읽는 값인지도 설명해요.
- 디자인이나 공개 props가 바뀌면 관련 Story도 같은 작업에서 갱신해요.

Storybook과 패키징의 실행 검증 책임은 [검증 기준](testing.md#소비자-입장에서-확인해요)에서 관리해요.
