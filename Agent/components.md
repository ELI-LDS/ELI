# 컴포넌트 구현 규칙

## 받은 디자인을 구현해요

디자이너가 제공한 색상·타이포그래피·상태·크기·반응형 기준을 확인해요. 누락된 명세는 확정된 사실처럼 채우지 않아요. 검증용 임시 값을 배포 소스에 추가하지 않아요.

## 색상 토큰의 역할을 구분해요

디자이너가 전달한 Color Variables 91개를 구현해요. 원시 색상 52개는 `tokens/colors.css`, 사용 목적과 상태를 나타내는 의미 색상과 효과 39개는 `tokens/semantic-colors.css`에서 관리해요. `tokens/index.css`는 두 파일을 연결해요.

- 단계가 있는 원시 색상은 `--eli-color-{색상}-{단계}` 형식으로 작성하고, 고정된 흰색과 검은색은 `--eli-color-static-{색상}` 형식으로 작성해요.
- 의미 색상은 Figma의 `{Category}/{Group?}/{Role 또는 강도}/{State?}` 계층을 순서대로 kebab-case로 바꾸고 `--eli-` 접두사를 붙여요.
- Category는 `foreground`, `background`, `border`, `effect`를 사용해요. `interaction` Group은 Hover·Pressed 같은 상태가 있는 Background와 Border에만 사용해요.
- 강조 강도는 `strong`, `default`, `subtle` 순서로 구분해요. 상호작용 상태는 Figma에 정의된 `default`, `hover`, `pressed`, `disabled`, `focused`를 사용해요.
- 반투명 변형은 이름 끝에 `-alpha`를 붙여요. 화면을 덮는 Dim과 그림자는 각각 `--eli-effect-dim`, `--eli-effect-shadow`를 사용해요.
- 컴포넌트에서는 원시 색상보다 의미 색상 토큰을 우선 사용해요. 원시 색상은 의미 색상을 연결할 때 사용해요.
- 투명도는 `rgb(from var(--eli-color-...) r g b / 30%)` 형식으로 한 줄에 작성해요.
- 같은 의미 토큰을 중복 선언하지 않아요. 같은 원시 색상을 참조하더라도 Foreground와 Background처럼 역할이 다르면 의미 토큰을 각각 유지해요.
- 디자이너가 확정하지 않은 색상이나 상태 토큰은 임의로 추가하지 않아요.

## 타이포그래피 기준을 지켜요

기본 글꼴은 `Pretendard Variable`이에요. 컴포넌트에서는 `--eli-font-family-sans`를 사용하고 소비 앱 전체의 `font-family`를 강제로 바꾸지 않아요. 시스템에 Variable 글꼴이 없으면 `Pretendard`와 시스템 글꼴 순서로 대체해요.

`@eli/ui`에는 폰트 파일, 원격 CDN import, 폰트 패키지 의존성을 포함하지 않아요. 초기 설정 도구가 소비 프로젝트에 Pretendard를 한 번 설치하고 로딩 설정을 추가해요. 소비 프로젝트가 이미 Pretendard를 불러오고 있다면 같은 설정을 중복으로 추가하지 않아요.

초기 설정 도구를 구현할 때는 Pretendard Variable의 동적 서브셋을 기본안으로 검증해요. 설치할 패키지와 정확한 버전, 프레임워크별 연결 방식은 구현 시점에 고정하고 다운로드 용량을 기록해요. 글자 크기·행간·굵기 같은 세부 타이포그래피 토큰은 디자이너가 확정한 값만 추가해요.

## 타이포그래피 크기 토큰을 재사용해요

타이포그래피의 기본 크기는 `tokens/typography.css`에서 `--eli-size-{기준 픽셀값}` 형식으로 관리하고 값은 `rem`으로 작성해요. 디자인 환산 기준은 `1rem = 16px`이며 라이브러리가 소비 앱의 루트 글자 크기를 강제로 설정하지 않아요. 모바일과 데스크탑 값이 같으면 하나의 토큰만 선언해요. 값이 달라지는 토큰은 디자이너가 확정한 반응형 기준을 받은 뒤 의미 토큰에서 재정의해요.

기본 굵기도 `tokens/typography.css`에서 `--eli-font-weight-{이름}` 형식으로 관리해요. 모바일과 데스크탑 값이 같으면 하나의 토큰을 함께 사용해요. Pretendard Variable에서 제공하는 연속적인 굵기 값은 정수 그대로 유지해요.

역할별 글자 크기는 `--eli-font-size-{종류}-{단계}` 형식으로 기본 크기 토큰을 참조해요. 데스크탑 값을 기본으로 선언하고 모바일 구간에서 같은 토큰을 덮어써요. Heading의 모바일 재정의는 관련 H1~H4 클래스 바로 다음에 배치해 두 값을 한 번에 확인할 수 있게 해요. 별도의 `-mobile`, `-desktop` 토큰을 중복으로 공개하지 않아요.

여러 컴포넌트가 같은 타이포그래피 조합을 사용하면 `tokens/typography.css`에 `.eli-typo-{이름}` 공통 클래스로 관리해요. Heading은 `.eli-typo-heading-h1`부터 `.eli-typo-heading-h4`, Body는 `.eli-typo-body-large`와 `.eli-typo-body-medium`, Label은 `.eli-typo-label-large`·`.eli-typo-label-medium`·`.eli-typo-label-small`을 사용해요. 별도 토큰이 필요하지 않은 고정 속성은 클래스에 값을 직접 작성해요.

## 레이아웃 기준을 재사용해요

레이아웃 값은 `tokens/layout.css`에서 관리해요. 크기 단계는 `--eli-layout-scale-{단계}` 형식으로 작성하고 디자이너가 전달한 픽셀값을 유지해요. 모바일의 375px은 기준 화면 너비로 기록하고, Tablet 768px과 Desktop 1024px을 반응형 전환 기준으로 사용해요.

CSS 미디어 쿼리 조건에서는 `var()`를 사용할 수 없으므로 `@media`에는 확정된 전환 값을 직접 작성해요. 데스크탑 스타일을 기본으로 두고 `1023px` 이하에서 Tablet, `767px` 이하에서 Mobile 스타일을 덮어써요. 기준이 변경되면 `layout.css`, 미디어 쿼리와 Storybook 반응형 검증을 함께 수정해요.

## 한 번 import하면 스타일이 적용돼요

컴포넌트 파일에서 자신의 CSS를 import해요. 컴포넌트 CSS에서는 공통 토큰 CSS를 상대 경로로 연결해요. 실제 `TextField`를 구현할 때의 예시예요.

```tsx
// src/text/TextField/TextField.tsx
import './TextField.css';
```

```css
/* src/text/TextField/TextField.css */
@import '../../tokens/index.css';
```

소비 코드에는 `import { TextField } from '@eli/ui/text'`만 필요해야 해요. JS로 style 태그를 삽입하거나 전용 CSS 프레임워크를 요구하지 않아요.

## 필요한 곳만 바꿀 수 있어요

공통 토큰은 `--eli-` 접두사를 써요. 컴포넌트 변수는 `--eli-text-field-`처럼 대상을 구분해요. 클래스도 `.eli-text-field`처럼 충돌을 줄여요. 전역 reset과 일반 HTML 태그 선택자로 소비 앱의 스타일을 바꾸지 않아요.

컴포넌트 변수는 사용 위치에서 재정의할 수 있도록 공통 토큰 fallback으로 연결해요. 사용자 `className`과 `style`을 전달하고, 한 인스턴스 변경이 다른 인스턴스에 번지지 않는지 확인해요. 공개하는 CSS 변수는 문서로 남겨요.

## 접근성과 상태를 확인해요

가능하면 기본 HTML 요소를 사용해요. label, 키보드 조작, focus, disabled, error 상태를 해당 컴포넌트에 맞게 검증해요. 라이브 리전·포커스 이동 같은 복잡한 동작은 실제 명세와 접근성 기준을 확인한 뒤 구현해요.

## 상태와 상호작용을 Hook으로 분리해요

컴포넌트에서 상태 관리, 제어·비제어 값 처리, 키보드 조작, 포커스 이동, Effect처럼 화면 구조와 분리할 수 있는 동작은 같은 컴포넌트 폴더의 `use{컴포넌트명}.ts`로 분리해요. 새 컴포넌트뿐 아니라 기존 컴포넌트를 수정할 때도 분리할 수 있는 로직이 있는지 확인해요.

Hook은 하나의 동작 책임만 맡도록 구성해요. 화면 마크업·스타일·Storybook 전용 코드를 Hook에 넣지 않고, 시맨틱 HTML과 `aria-*` 연결은 구조를 한눈에 확인할 수 있도록 컴포넌트 파일에 남겨요. 단순히 값을 다시 전달하기만 하는 Hook이나 실제 재사용·가독성 개선이 없는 빈 추상화는 만들지 않아요.

Hook에는 상태, 접근성 ID, 참조, 이벤트 처리처럼 코드의 역할이 드러나는 한국어 주석을 작성해요. 모든 줄을 반복해서 설명하기보다 동작의 목적과 포커스 이동 같은 중요한 이유를 남겨요. 공개 props 타입은 컴포넌트 타입 파일에서 관리하고 Hook 내부에서만 사용하는 타입은 Hook 파일 안에 둬요.

## 클라이언트 경계를 명시해요

State·Effect·Ref 같은 React Hook, 사용자 이벤트 또는 `window`·`document` 같은 브라우저 API를 사용하는 컴포넌트는 파일 맨 위에 `'use client';`를 작성해요. 지시문은 import보다 앞에 두고, 타입·순수 표현 컴포넌트·CSS처럼 클라이언트 기능을 사용하지 않는 파일에는 추가하지 않아요.

클라이언트 컴포넌트가 내부에서 가져오는 `use{컴포넌트명}.ts`는 같은 클라이언트 모듈 그래프에 포함되므로 지시문을 중복 작성하지 않아요. 배포 결과에 지시문이 남는지, SSR과 hydration이 동작하는지는 Next.js 지원을 추가할 때 별도로 검증해요.

## Storybook을 함께 확인해요

Storybook은 개발자와 디자이너가 같은 컴포넌트를 확인하는 문서로 사용해요. 왼쪽 메뉴의 그룹과 사용자 설명은 한글로 작성하고, 컴포넌트 이름은 `Button`, `TextField`처럼 공개된 영문 이름을 그대로 사용해요. Story 표시 이름은 `한눈에 보기`, `상태별 보기`, `직접 바꿔보기`처럼 한글로 작성해요.

- 주요 디자인 조합을 비교할 필요가 있으면 `한눈에 보기`를 기본 표시 이름으로 사용해요.
- 여러 상태가 있으면 `상태별 보기`를 사용하거나 `오류 상태`, `비활성화`, `로딩 상태`처럼 실제 내용이 드러나는 이름으로 나눠요.
- Controls에서 속성을 조작하는 화면은 `직접 바꿔보기`로 표시하고 컴포넌트 하나만 보여줘요.
- 컴포넌트에 해당하지 않는 화면은 만들지 않아요. 필요한 Story의 수와 상태 구분은 컴포넌트 특성에 맞춰 정해요.
- 전체 조합 화면에는 color, variant, size처럼 비교 기준을 표시해 디자이너가 코드를 보지 않고도 차이를 알 수 있게 해요.
- Hover와 Pressed는 실제 컴포넌트 상호작용으로 확인하고 확인 방법을 화면에 안내해요. Storybook 전용 스타일로 컴포넌트 상태 디자인을 복제하지 않아요.
- Disabled처럼 상호작용으로 확인하기 어려운 상태는 실제 prop과 전체 조합을 사용해 보여줘요.
- Storybook Controls는 공개 props를 기준으로 제공하고 각 항목의 이름과 설명을 한글로 작성해요.
- 디자인이나 공개 props가 바뀌면 관련 Story도 같은 작업에서 갱신해요.
