# 독스 페이지 작성과 공통 UI

사용자는 독스 안에서 설치·선택·실제 동작·API를 확인할 수 있어야 해요. 이 공통 구성은 컴포넌트 상세 문서에 적용하며, Foundation에 컴포넌트 설치나 Props 구역을 억지로 추가하지 않아요. Storybook은 제작자 검수용으로 두고 사용법을 대신 설명하는 링크로 사용하지 않아요. 폴더 책임과 SSR은 [프론트엔드 구조](docs-frontend.md), 한국어 문장은 [글쓰기](writing.md), 검증은 [검증 기준](testing.md#문서-웹페이지를-확인해요)을 따라요.

## 읽는 순서와 필수 구역을 맞춰요

1. 영문 컴포넌트 이름과 역할을 설명하는 짧은 문장
2. 기본 UI 하나와 핵심 사용 코드
3. 해당 컴포넌트의 설치 명령
4. 목적별 사용 예시
5. 실제 타입에서 조회한 전체 속성

선택 기준·주의사항·접근성은 전달할 내용이 있을 때 붙여요. 같은 정보를 반복하거나 내용이 없는 구역을 만들지 않아요. 컴포넌트가 지원하지 않는 상태·옵션을 문서 형식을 맞추기 위해 추가하지 않아요. 추가 예시가 필요 없는 문서에는 빈 예시 구역을 만들지 않아요. 본문은 한국어로 쓰고 이름에 한글을 병기하지 않아요. 검색용 한글 별칭과 화면 표시 이름은 구분해요.

## 공통 블록으로 조립해요

- `DocIntro`: 이름과 짧은 설명
- `DocSection`: 제목 계층·앵커·간격
- `DocExample`: 설명·실제 미리보기·핵심 코드·필요한 전체 실행 예시
- `InstallationSection`: 패키지 매니저 탭과 컴포넌트 추가 명령
- `PropsReference`: 조회한 속성·타입·기본값·설명
- `DocPreviewCase`: 비교 UI마다 해당 허용 값을 함께 표시
- `DocToc`: 같은 섹션 정의로 만든 목차
- `DocGuidance`: 권장·피할 상황과 상황별 속성 조합
- `DocComposition`: 조립 부품과 직접 배치·자동 구성 관계를 보여주는 시각적 구성도

모든 컴포넌트 상세 페이지는 같은 블록을 조립해요. 일부 페이지에 이전의 일곱 구역·API 표·별도 설치 UI를 남기지 않아요. 개별 예시는 자기 폴더에서 상태·이벤트를 관리해요. 페이지마다 제목·표·코드의 전역 스타일을 다시 정의하지 않아요. 컴포넌트 전용 블록은 해당 페이지의 `sections`에 둬요. 컴포넌트·Foundation이 함께 쓰는 목차는 `features/docs-toc`에서 표시·앵커·활성 상태·CSS를 관리하며 페이지의 구역 정의를 전달받아요.

웹 출력용 섹션·예시 데이터는 페이지 가까이에 둬요. 승인된 가이드와 실제 Props를 기존 조회 함수로 읽고, 웹 배치 정보나 전체 Props를 가이드 JSON에 복제하지 않아요. 같은 페이지에서 소개하는 하위 컴포넌트의 API·사용 기준도 같은 조회 결과로 표시해요. 형태가 다르거나 공개 API가 있다는 이유만으로 별도 페이지를 만들지 않아요. 함께 조립하는 Item 등 구성 요소의 API는 사용하는 상위 문서에 모아요. 별도 설치·사용 선택이 필요한 공개 컴포넌트는 독립 페이지로 안내할 수 있으며 같은 계열이라는 이유로 무조건 합치지 않아요. 페이지 상단 관련 컴포넌트 링크는 추가하지 않아요. 구성 요소마다 권장·피할 상황을 반복하지 않아요. 상위 컴포넌트의 선택 기준을 한 번 설명하고 구성 요소는 역할 요약·API·조립 시 주의사항과 동작으로 안내해요. 고유 값·이벤트 취소·선택과 펼침 구분 등 제약은 API 옆에 유지하고, 독립적으로 고르는 형태의 선택 기준은 남겨요. 모바일 전용 컴포넌트에만 이름 옆에 `Mobile` pill을 표시해요. 별도의 플랫폼 설명 문장이나 `Web` 표시는 넣지 않아요. 화면 낭독기에는 모바일 전용임을 설명하며 데스크톱에서 미리보기가 보인다는 이유로 웹용으로 안내하지 않아요. 예시가 별도 소스를 요구하면 그 예시의 설치 명령에 필요한 항목만 명시하고 기본 설치에 관계없는 항목을 포함하지 않아요. 하나의 Markdown 문자열에 모든 화면 구역을 강제로 합치지 않아요.

## Foundation은 개념·사용법·실제 기준을 연결해요

Foundation도 본문 최대 너비·제목 위계·간격·강조·목차는 공통 문서 기준을 따라요. 컴포넌트 설치나 Props 구역은 추가하지 않아요. 개념 소개는 짧게 쓰고 역할이 다른 개념은 나눠 보여줘요. 바로 사용할 수 있는 핵심 CSS 토큰·클래스 예시 뒤에 실제 미리보기와 기준값을 제공해요.

색상 샘플은 역할과 값을 함께 읽을 수 있게 배치하며 설명을 색상 면 위에 겹쳐 가독성을 떨어뜨리지 않아요. 타이포그래피는 스타일 이름·실제 클래스·미리보기·크기·굵기·행간·자간을 같은 묶음에서 확인하게 해요. Layout은 Scale·padding·gap·Radius 비교와 전체 토큰 조회를 구분해요. 실제 토큰·클래스를 재사용하고 가독성 정리를 이유로 토큰 값·반응형 기준·폰트 설정을 바꾸지 않아요.

목차와 본문 앵커는 같은 구역 정의에서 만들어요. Color 탭을 바꾸면 해당 패널의 목차로 함께 갱신하고 이전 패널의 앵커는 URL에서 정리해요. 모바일에는 별도 목차를 표시하지 않으며 긴 표의 헤더와 행은 하나의 컨테이너 안에서 함께 스크롤해요.

## 조립 관계는 시각적인 구성도로 보여줘요

여러 컴포넌트를 조립하는 문서에는 기본 예시 다음에 선택적인 `구성` 구역을 제공해요. 공통 `DocComposition`의 프레임·부품 카드·역할 미니어처로 관계를 표현하고 ASCII 도식이나 긴 본문으로 대체하지 않아요. 단일 컴포넌트에 형식을 맞추려고 구성도를 추가하지 않아요.

사용자가 직접 배치하는 부품과 props에서 자동 생성되는 부품을 구분하고 선택·반복 여부는 짧은 표시로 전달해요. 구성도는 웹 전용 메타데이터와 실제 공개 이름을 조합해 만들며, 가이드 JSON·공개 API·설치 의존 관계를 변경하지 않아요. 내부 전용 요소는 직접 import하거나 설치할 대상으로 안내하지 않아요. 실제 DOM 계층이나 전체 설치가 자동으로 따라온다는 의미로 표현하지 않아요.

부품 카드는 누르는 컨트롤처럼 만들지 않고 장식 도형은 화면 낭독기에서 제외해요. 이름·역할·구성 방식은 서버 HTML에서도 읽을 수 있어야 하며 좁은 화면에서는 카드가 순서대로 재배치돼요. 전체 화면의 가로 스크롤이나 추가 애니메이션·의존성 없이 제공해요.

## 예시는 한 가지 사용 목적을 설명해요

각 예시에는 고유한 ID, 제목, 짧은 설명, 핵심 코드와 대응하는 실제 미리보기를 연결해요. 미리보기와 코드의 속성·문구·동작이 일치해야 해요. 열고 닫는 예시는 트리거의 포커스와 닫힌 뒤 복귀까지 연결해요. 기본 예시는 조합 전체보다 첫 사용에 필요한 하나를 보여줘요.

상태·이벤트 연결이 필요하면 전체 실행 예시를 제공하고 import·상태·함수를 완결되게 작성해요. 기본 코드의 불필요한 Fragment·로그·출력용 UI는 제거하되 구조적으로 필요한 코드는 유지해요. 일반 React 예시에는 프레임워크 전용 `'use client'`를 넣지 않아요. Next.js App Router에서 상태·이벤트가 필요한 경우의 선언은 별도 안내로 제공해요. 실제 구현 파일의 Client Component 경계는 프론트엔드 지침대로 유지해요. 전체 코드가 새 정보를 주지 않으면 같은 예시를 반복하지 않아요. 공통 블록이 서로 다른 예시의 상태를 대신 소유하지 않아요.

짧은 코드는 바로 읽을 수 있게 해요. 긴 코드는 기존 줄 수 제한과 내부 스크롤을 유지하고 전체 원문을 복사할 수 있게 해요. 코드 영역의 스크롤바는 숨기되 가로·세로 스크롤과 키보드 조작은 유지해요. 마지막 줄이 가려지지 않도록 코드 영역 바깥의 하단 여백을 확보해 표시 줄 수에 영향을 주지 않게 해요. 복사할 때 줄 번호를 포함하지 않으며 복사 실패도 사용자에게 알려줘요. 복사 버튼의 아이콘 전환은 [후속 작업](../handbook/improvements.md#독스-복사-버튼을-아이콘으로-변경해요)이며 현재 텍스트 버튼을 유지해요.

선택 기준은 권장 상황·피할 상황을 위아래로 배치하고 속성 조합은 별도 구역으로 구분해요. 선택 항목마다 역할과 사용 상황을 먼저 읽고 해당 속성을 따로 확인할 수 있게 해요. 카드 외곽 테두리는 사용하지 않고 기존 가로 구분선·항목 사이 여백·제목의 굵기·설명의 색상으로 항목을 구분해요. 선택 기준 제목 위에는 구분선을 두지 않고 제목 아래의 첫 구분선·각 선택 항목 사이의 선과 기존 여백은 유지해요. 외곽 테두리 제거와 항목 사이 구분선 제거를 같은 변경으로 취급하지 않아요. 승인된 문구·조합은 그대로 유지하고, 해석할 수 없는 형식은 원문으로 표시해 누락하지 않아요.

## Properties는 선택을 먼저 돕고 전체 속성을 분리해요

시각적인 선택을 설명하는 문서는 `Properties`에서 기존 크기·형태·색상·콘텐츠 예시를 조합해요. 같은 예시를 별도 예시 구역에 다시 표시하지 않아요. 실제 UI와 해당 허용 값을 함께 보여주고 설명은 선택에 필요한 차이를 짧게 전달해요. Properties와 상태·이벤트의 소제목·목차는 `size`, `variant`, `disabled`, `onClick`처럼 실제 prop 이름으로 표시하고 한글 별칭을 제목으로 사용하지 않아요. 두 구역의 소제목은 동일한 20px 토큰으로 설명보다 한 단계 크게 표시해요. 연결할 속성과 기본값·필수 여부는 실제 조회 결과를 사용하며 소제목 아래에 같은 prop 이름을 반복하지 않아요.

상태·이벤트를 연결하는 예시는 별도 `상태와 이벤트`에 묶어요. 필요한 정보가 없는 묶음은 만들지 않아요. 정확한 타입과 전체 설명은 하단의 `전체 속성`에 항상 표시하고 내용·설정·상태와 이벤트·스타일 등 찾는 목적별로 분류해요. 전체 속성을 열기 위한 접이식 컨트롤을 두지 않아요. 속성마다 구분선을 반복하지 않고 그룹 사이에만 구분선을 두며 그룹 안은 제목·타이포 위계·여백으로 구분해요. 속성·제약을 삭제하거나 필수 값을 숨겨 사용 예시가 불완전해지지 않게 해요. 기존 `#api` 앵커는 유지하고 각 묶음의 필수 항목을 먼저, `className`은 전체의 마지막에 표시해요.

전체 컴포넌트 문서에서 같은 공통 블록·구역 메타데이터를 사용해요. 설명할 속성이나 동작이 없으면 해당 구역을 생략하며 명세에 없는 예시를 억지로 만들지 않아요. 소비 앱이 구성하는 트리거·패널 등은 `조합 예시`에 두고 ELI가 제공하는 prop이나 동작으로 잘못 소개하지 않아요. 함께 연결하는 실제 props는 `value · onValueChange`처럼 묶고 다른 구성 컴포넌트의 예시는 그 컴포넌트 이름과 실제 조회 결과를 연결해요. 구현·검증 현황은 프론트엔드 README에서 관리해요. SEED의 [디자인 속성 비교](https://seed-design.io/components/badge#size)와 [React Props 조회](https://seed-design.io/react/components/badge#props)의 역할 분리를 참고하되 ELI에서는 한 문서 안에서 사용 선택과 정확한 속성 조회를 함께 제공해요.

## 강조의 용도를 구분해요

백틱은 속성명·허용 값·명령어·짧은 코드처럼 실제 식별자에 사용해요. 중요한 선택 기준이나 주의 문장은 굵게 표시해요. 일반 단어를 모두 코드로 만들거나 문단 전체를 강조하지 않아요. 공통 인라인 렌더러와 스타일을 사용하고 예시 설명에서도 같은 기준을 적용해요.

## 설치·API·탐색을 정확하게 안내해요

상세 페이지의 설치 영역은 패키지 매니저 탭과 해당 컴포넌트의 `add` 명령만 표시해요. 명령은 밝은 중립 배경의 터미널 형태로 표시해요. 줄 번호·문법 강조·펼침·`$` 프롬프트 없이 명령 원문만 표시하고 복사해요. 긴 명령은 내부에서 가로 스크롤하며 복사 성공·실패와 키보드 포커스를 지원해요. 초기 설정 접이식 영역이나 명령 위아래의 별도 설명을 넣지 않아요. 사용자가 후속 설치 동작에 맞춘 선반영을 명시적으로 요청한 경우에만 웹 전용 메타데이터에 예정 상태를 기록해요. 현재 설치와의 차이·미완료 소비 검사는 내부 인계와 테스트에 남기고, 실제 지원·공개 배포 검증이 끝났다고 표현하지 않아요. 구현 후 예정 상태와 알려진 누락·TODO를 함께 해제해요. 탭에는 `yarn`으로 표시해요. 패키지 매니저별 명령과 Yarn Classic·Modern 차이의 기술 기준은 [패키지 매니저 지침](package-managers.md#cli-실행-행렬도-구분해요)에서 관리해요. 화면 단순화와 CLI의 초기 설정 필요 여부를 구분하고, CLI 자동 초기화는 [후속 작업](../handbook/improvements.md#컴포넌트-추가-시-자동-초기화를-별도-브랜치에서-구현해요)으로 관리해요.

API는 기존 조회 결과에서 읽고 기본값·필수 여부·이벤트를 임의로 작성하지 않아요. 좁은 열에 모든 정보를 압축하지 않아요. 속성명은 굵은 코드로, 타입·기본값은 작은 보조 정보로, 설명은 본문으로 구분해요. 정확한 타입과 설명은 전체 속성에서 바로 읽을 수 있게 두고 속성마다 반복되는 상세 펼침을 만들지 않아요. 문자열 리터럴의 허용 값은 배경 없이 따옴표·`|` 구분자·대비가 충분한 코드 색상으로 표시해 일반 `string` 타입과 구분해요. 허용 값을 pill처럼 만들지 않으며 속성명 행과 타입 사이 여백을 확보해요. 필수·선택 여부는 실제 조회 결과를 기준으로 pill에 표시해요. 필수는 Primary 계열, 선택은 중립색으로 구분하고 색뿐 아니라 문구로도 알 수 있게 해요. 필수 항목을 먼저 보여주고 각 묶음 안에서는 콘텐츠 → 주요 설정 → 상태 → 기타 설정 → 이벤트 → 접근성·ref → 크기·스타일 순서를 사용해요. `className`은 필수 여부와 관계없이 항상 마지막에 둬요. 미지정 속성은 같은 분류 안에서 원래 순서를 유지하고, 이 정렬은 웹 표시 계층에만 적용해 원본 선언이나 MCP 응답 순서를 재작성하지 않아요. 객체 배열의 필드가 긴 한 줄 타입으로 펼쳐지면 배열·읽기 전용 여부를 짧게 표시하고 항목 필드·타입·필수 여부를 펼쳐 확인하게 해요. 원본에서 안전하게 분리할 수 없는 복잡한 타입은 그대로 표시해요. 표시용 요약을 위해 원본 API나 제약을 삭제하지 않아요. 중요한 제약과 소비 앱이 연결해야 하는 동작은 해당 예시 가까이에서 안내해요.

목차는 여러 구역을 오갈 필요가 있는 문서에 제공해요. 특정 컴포넌트 이름을 이유로 목차에서 제외하지 않아요. 섹션 ID와 제목을 목차에 따로 복제하지 않아요. 오른쪽 목차는 1280px 이상에서 제공하고 모바일·좁은 화면에는 별도 목차를 두지 않아요. 현재 읽는 구역·Hover·키보드 포커스는 ELI Brand(Primary) 토큰으로 구분하고 Hover·선택 상태에는 배경색을 넣지 않아요. 텍스트 크기와 굵기는 고정하고 현재 구역은 Primary 글자색·표시선으로 구분해요. 현재 구역에는 `aria-current`를 함께 제공하며 키보드 포커스 외곽선은 유지해요. 스크롤·본문 높이 변화에 맞춰 활성 구역을 갱신하고 모션 줄이기 설정을 존중해요. 우측 목차의 컴포넌트 이름은 한 줄로 표시하고 가장 긴 항목에 맞춰 목차 열의 너비를 확보해요. 줄바꿈·이름 생략·가로 스크롤로 처리하지 않으며 본문은 남은 폭에 맞춰 표시해요. 앵커 이동 후 제목이 고정 헤더에 가려지지 않게 해요. 목차의 부드러운 이동이 페이지 전환에 적용되지 않게 해요. 다른 문서로 이동하면 새 본문은 즉시 맨 위에서 표시하고 상단으로 올라가는 애니메이션을 재생하지 않아요.

## 추가한 페이지를 확인해요

페이지 등록·필수 구역·고유 앵커·실제 미리보기·전체 코드의 타입과 동작을 확인해요. 코드 복사·설치 명령·목차·키보드·SSR과 모바일 화면은 [검증 지침](testing.md#문서-웹페이지를-확인해요)에 따라 확인해요. 구현 현황과 확인한 범위는 프론트엔드 README에서 관리하고, 새 문서를 추가할 때마다 이 지침에 컴포넌트 목록을 늘리지 않아요.
