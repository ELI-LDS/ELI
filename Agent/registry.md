# 선택 설치용 레지스트리

필요한 컴포넌트 소스만 추가하는 기본 소비 방식과 전체 소스 추가를 지원하기 위한 배포 규격이에요. 기존 npm `@eli-design/ui`는 npm에서 삭제됐으며 신규 설치는 `eli-design` 소스 추가 방식으로 통일해요. 생성기·설치 도구·소비 검사는 구현되어 있어요. 기본 설치 도구 `eli-design`과 UI·하네스 콘텐츠는 공개됐어요. 실제 버전·게시 상태와 검증 범위는 [릴리스 기록](../handbook/releases/0.2.0.md)을 확인해요.

## 개별 소스 추가를 기본으로 사용해요

- 기본 선택 범위는 사용자가 요청한 공개 컴포넌트 하나 또는 여러 개예요. 전체 소스 추가는 명시적인 선택으로 제공해요.
- 전체 소스 추가도 같은 레지스트리의 모든 `component` 항목과 필요한 의존 항목을 해석해요. 공통 파일은 한 번만 추가하고 하네스는 자동으로 포함하지 않아요.
- `add --all`은 목록의 공개 컴포넌트를 선택해요. 전체 소스를 묶은 중복 집계 항목은 만들지 않아요.
- 소스 설치를 위해 `@eli-design/ui` 전체 tarball이나 전체 저장소를 먼저 받지 않아요. 설치 도구 자체의 다운로드와 UI 소스의 다운로드를 구분해요.
- 기존 JSON은 ELI 규격이에요. 특정 외부 CLI와 호환된다고 단정하지 않아요. 설치 진입점과 현재 구현·공개 상태는 [패키지 매니저 지침](package-managers.md#소스-추가를-기본-소비-방식으로-사용해요)을 따라요.
- 선택한 소스는 전체 ELI UI 패키지를 다시 import하지 않아야 해요. 실제로 필요한 외부 의존성만 선언하고 UI·React를 설치 도구 자체의 실행 의존성으로 넣지 않아요.

## 원본과 생성물을 구분해요

- 컴포넌트 원본은 `packages/ui/src`, 공개 컴포넌트의 기준은 `packages/ui/package.json`의 `exports`예요.
- `packages/registry/catalog.json`은 규격 버전·공유 토큰 경로·예약된 항목 종류만 관리해요. 컴포넌트 명단과 의존 파일 목록을 수동 복제하지 않아요.
- `pnpm build:registry`가 `.artifacts/registry/registry.json`과 항목별 JSON을 생성해요. 생성물은 직접 고치거나 Git에 올리지 않아요.
- `packages/registry/schema.json`은 목록과 상세 JSON의 공개 JSON Schema예요. 규격을 호환되지 않게 바꾸면 `schemaVersion`을 올리고 CLI 담당자와 먼저 맞춰요.
- UI 원본과 개발 도구의 실행 의존성은 추가하지 않아요. 레지스트리 생성기는 기존 TypeScript 개발 의존성과 Node.js 기본 API를 사용해요.

## 항목을 작게 제공해요

공개 named export 하나를 하나의 `component` 항목으로 제공해요. ID는 공개 심벌의 PascalCase를 kebab-case로 바꿔요. 예를 들어 `TextField`는 `text-field`, `SnackBar`는 `snack-bar`예요. Button을 받았다고 같은 그룹의 IconButton을 받지 않아요.

토큰과 내부 파일은 `shared` 항목으로 제공해요. 내부 파일 ID는 `_file-` 접두사를 사용하고 CLI 선택 목록에는 `component`만 표시해요. 내부 항목 ID와 파일 경로를 직접 사용할 공개 API로 안내하지 않아요. 경로 변경도 설치 파일에 영향을 주므로 같은 릴리스의 데이터끼리 사용해야 해요.

TypeScript의 import·재수출·타입 참조와 CSS의 `@import`·`url()`을 따라 실제로 참조하는 파일만 수집해요. 타입·Hook·SVG도 포함하고, 같은 파일은 하나의 항목만 소유해요. 누락 참조, 소스 루트 밖의 참조, 개발 파일, 선언하지 않은 외부 의존성은 생성 오류예요. 새 참조 방식이나 파일 형식이 생기면 분석기와 소비 검사를 함께 보완해요.

원본의 그룹·컴포넌트 중첩을 설치 결과에 그대로 복사하지 않아요. 공개 구현은 설치 루트의 `{항목 ID}.tsx`로 제공하고 스타일·타입·Hook·에셋은 `{항목 ID}/`에 모아요. 예를 들어 원본 `button/Button/Button.tsx`는 `button.tsx`, `button/Button/Button.css`는 `button/Button.css`가 돼요. 공유 토큰과 내부 공유 파일은 별도로 재사용해요. 다른 컴포넌트를 함께 설치하는 그룹 barrel이나 단순 전달 파일은 만들지 않아요.

생성기에서 TS import·재수출·타입 참조·URL과 CSS의 `@import`·`url()`을 설치 위치에 맞춰 상대경로로 보정해요. 일반 TS 모듈 import의 `.js` 확장자는 제거하고 CSS·SVG 확장자와 URL의 query·fragment는 유지해요. JSDoc·한국어 주석·`'use client'`와 실제 컴포넌트 동작을 보존하고 변환한 UTF-8 바이트로 해시를 계산해요. 원본 소스는 수정하지 않으며 이 변환을 소비 프로젝트 설정으로 떠넘기지 않아요. 경로가 충돌하면 생성하지 않아요.

## CLI가 읽는 계약

목록 JSON에는 `schemaVersion`, `version`, `license`, `reservedKinds`, `items`가 있어요. 각 목록 항목은 `id`, `kind`, `name`, `description`, `filename`, `sha256`을 제공해요. 목록에는 실제 소스를 담지 않아요.

상세 JSON에는 같은 규격·릴리스 버전과 항목 정보에 더해 아래 값을 제공해요.

| 필드 | 의미 |
| --- | --- |
| `entry` | 공개 컴포넌트의 `{ path, export }`. 공유 항목은 `null`이에요 |
| `dependencies` | 함께 받아야 하는 항목 ID 배열이에요. 타입 참조 의존성도 포함해요 |
| `peerDependencies` | 해당 항목이 외부에서 요구하는 패키지와 버전 범위예요. 의존 항목의 값도 함께 확인해요 |
| `files` | `{ path, content, sha256 }` 배열이에요. 텍스트 TS·TSX·CSS·SVG만 제공해요 |

`packages/cli`는 다음 순서로 레지스트리에 연결해요. 실행 명령·결과·오류 코드는 [CLI 사용법](../packages/cli/README.md)을 기준으로 관리해요.

1. 신뢰하는 ELI GitHub Release의 `registry.json`을 읽고 규격 버전을 확인해요. 선택한 항목과 의존 항목 JSON만 재귀적으로 받아요. 전체 tarball이나 저장소를 먼저 받지 않아요.
2. 상세 JSON의 원본 UTF-8 바이트로 SHA-256을 확인해요. 파일의 해시는 **설치할 `content`의 UTF-8 바이트**를 기준으로 확인해요. 해시는 무결성 확인 수단이며 배포 출처 인증을 대신하지 않아요.
3. 모든 JSON의 `version`·`schemaVersion`이 목록과 같은지 확인해요. `peerDependencies`는 소비 프로젝트의 도구로 확인하며 React나 다른 UI를 임의로 추가하지 않아요.
4. `files.path`는 설정한 UI 설치 폴더를 기준으로 사용해요. 새 초기화의 기본 폴더는 `src`가 있으면 `src/components/ui`, 없으면 `components/ui`예요. 기존 `.eli/config.json`의 폴더는 유지해요. 절대 경로·`..`·역슬래시·심볼릭 링크를 통한 설치 폴더 밖 쓰기를 허용하지 않아요. `LICENSE`도 같은 폴더에 전달해요.
5. 전체 의존 항목을 먼저 검증하고 같은 경로는 한 번만 써요. 경로가 같은데 내용이나 해시가 다르면 중단해요. 그룹 barrel 파일은 추가하지 않고 `entry.path`의 로컬 모듈에서 `entry.export`를 가져오는 예시를 안내해요.
6. `.eli/config.json`에 레지스트리 주소·해시·버전·설치 폴더를 고정하고 `.eli/lock.json`에 소비 방식·요청/의존 항목·진입 경로·파일 소유 항목·해시를 기록해요. 같은 파일은 재사용하고 사용자 수정 파일은 덮어쓰지 않아요. 버전 변경·업데이트·강제 덮어쓰기는 아직 제공하지 않아요.

설치 위치는 초기화 시 `--dir`로 사용자가 정해요. FSD 같은 폴더 구조를 추측해 기본 경로를 바꾸거나 기존 파일을 이동하지 않아요. import 별칭은 소비 앱의 기존 설정을 재사용하고 CLI가 새 별칭이나 TypeScript·빌드 도구 설정을 자동으로 추가·변경하지 않아요. 실제 파일 경로와 앱의 import 별칭을 구분해요. 같은 모듈명을 쓰는 기존 `.ts`·`.tsx` 파일이나 폴더의 `index` 구현이 있으면 짧은 import가 다른 구현을 가리키지 않도록 추가 전에 중단해요. 사용 예시는 [CLI 사용법](../packages/cli/README.md)에서 관리해요.

설치 배치 변경은 UI 콘텐츠의 다음 MINOR 대상이에요. 기존 공개 JSON·태그와 설치 기록을 새 배치로 덮어쓰지 않아요. 기존 프로젝트는 고정된 콘텐츠와 기록의 경로를 계속 사용하며, 새 콘텐츠로 바꾸려면 수정 파일을 확인하는 별도 이전 작업이 필요해요. CLI 업데이트만으로 복사한 소스를 이동하거나 자동 이전하지 않아요.

일반 npm 패키지 방식은 전체 파일을 내려받아요. 선택 설치 예시와 npm 전체 설치의 import·다운로드 범위를 혼동하지 않아요. 두 방식을 자동으로 전환하거나 기존 `@eli-design/ui` 의존성을 제거하지 않아요.

## 하네스가 소비 방식을 구분하게 해요

UI·레지스트리와 설치 도구의 연동은 UI 담당 개발자가 맡고, MCP·하네스의 실제 동작은 해당 담당 개발자가 구현해요. UI 쪽은 아래 정보를 일관되게 제공하고, 실제 설치를 판단하거나 명령을 실행하는 하네스 로직은 담당자와 연결해요.

| 판단할 내용 | 기준 정보 |
| --- | --- |
| 어떤 UI가 있는지 | 레지스트리의 공개 항목 ID·이름·설명·릴리스 버전 |
| 무엇을 함께 받아야 하는지 | `dependencies`, `peerDependencies`, 공유 파일 소유 관계 |
| 어디에서 가져오는지 | 같은 릴리스의 목록·항목 JSON 위치와 해시 |
| 어떻게 사용하는지 | `entry.path`·`entry.export`, 소스의 JSDoc·타입, 별도로 제공할 사용 가이드 |
| 무엇이 이미 설치됐는지 | 소비 프로젝트의 설치 기록과 실제 파일·해시. 패키지 방식은 의존성 선언과 lockfile도 확인해요 |

설치 기록에는 앞 절차에서 정한 버전·항목 ID·설치 위치·파일 해시와 소비 방식(`source`)이 들어 있어요. `status --json`으로 실제 파일의 변경·누락도 조회할 수 있어요. 로컬 하네스의 훅·스킬은 설치 기록과 실제 파일을 통한 소스 인식을 지원해요. 원격 MCP는 레지스트리 항목의 `id`·`entry`만 알려주고 설치 상태는 판단하지 않아요. 레지스트리 JSON의 존재만으로 소비 프로젝트에 설치가 완료됐다고 판단하지 않아요.

파일의 `modified`는 설치 당시 해시와 다르다는 뜻이며 디자인·접근성 위반을 뜻하지 않아요. 사용자 수정에 대한 판단·보고·보존 절차는 [하네스 확인 기준](harness.md#사용자-커스터마이징을-확인해요)을 따르고, 실제 하네스 판단 로직은 담당자의 구현 범위로 남겨요.

소스 방식의 import 경로는 실제 설치 위치에 `entry.path`를 연결해 만들고, 패키지 방식의 import 경로는 `package.json`의 `exports`를 사용해요. 하네스가 npm 경로를 모든 프로젝트의 기본값으로 고정하거나 이미 설치한 UI를 전체 패키지로 다시 받게 하지 않아요. 컴포넌트의 의미·선택 기준을 파일 의존 관계만으로 추측하지 않아요.

[원격 MCP 규격](mcp-spec.md)은 npm 그룹 경로 대신 레지스트리 항목의 `id`와 `entry`를 돌려줘요. 서버는 로컬 import 경로를 만들지 않고, 하네스가 설치 기록으로 실제 경로를 확인해요. 이 응답으로 실제 에이전트의 스킬이 끝까지 동작하는지는 아직 확인하지 않았어요.

## 하네스가 설치 도구를 호출해요

아래는 설치 도구가 유지할 계약이에요. 저장소의 CLI는 목록·설치 상태·추가·미리보기·JSON 결과를 제공하지만, 하네스의 명령 호출과 공개 배포 환경은 별도 검증 대상이에요. 구체적인 명령과 기록 형식은 [CLI 사용법](../packages/cli/README.md)에서 관리해요.

- 목록·설치 상태를 파일 변경 없이 조회하고, 개별·다중·전체 추가와 쓰기 전 변경 미리보기를 지원해요.
- 필요한 인자를 주면 대화형 질문 없이 실행할 수 있어야 해요. 필수 설정이 빠졌거나 파일 충돌 판단이 필요하면 임의로 결정하지 않고 필요한 입력을 구조화된 오류로 돌려줘요.
- 결과는 성공 여부·콘텐츠 버전·요청/의존 항목·추가/재사용/건너뛴 파일·실제 진입 경로를 기계가 읽을 수 있게 제공해요. 사람이 읽는 메시지를 파싱해 성공 여부나 import 경로를 추측하게 하지 않아요.
- 구조화된 출력 모드에서는 표준 출력에 결과만 쓰고 진행 로그는 표준 오류로 분리해요. 오류 코드·종료 코드의 의미를 문서화하고, 실패를 성공 코드로 반환하지 않아요.
- 설치 기록을 실제 파일·해시와 대조해 누락과 사용자 수정을 구분해요. 같은 릴리스의 공통 파일은 재사용하고, 사용자 수정 파일은 일괄 확인 생략 옵션만으로 덮어쓰지 않아요.
- 설치 도구의 최신 버전으로 실행한 것과 UI 콘텐츠를 갱신한 것을 구분해요. 버전 기준은 [버전 지침](versioning.md#설치-도구와-콘텐츠-버전을-구분해요)을 따라요.

사용 목적·선택 기준·예시는 [문서 원본](docs.md#원본은-가이드-json과-레지스트리-json이에요)에서 제공하고, Props·토큰·파일 의존성은 실제 코드에서 가져와요. 레지스트리는 설치할 파일의 기준이고 MCP는 사용 의미의 조회 경로예요. 두 경로에서 같은 컴포넌트 식별자를 연결하되 사용 규칙을 레지스트리에 수동 복제하지 않아요.

## 하네스 담당자와 연결해요

UI 목록에는 `reservedKinds: ["harness"]`만 두고 하네스 항목이나 하네스 의존성을 추가하지 않아요. CLI의 별도 `harness` 명령이 UI 목록과 독립된 하네스 묶음을 설치해요. 규격·태그·기록은 [하네스 지침](harness.md#하네스-배포-데이터와-설치-기록)을 따라요.

하네스 데이터도 `schemaVersion`·독립 `version`·파일 목록과 해시로 식별해요. CLI는 에이전트 선택·복사·설정 병합을 맡고 사용자 신뢰는 해당 에이전트의 절차를 따라요. 원격 MCP 응답과 실제 에이전트가 스킬을 따르는지는 담당자가 별도로 검증해요.

저장소 주소 변경은 [공개 주소 기준](architecture.md#저장소와-공개-주소를-구분해요)을 따라 CLI의 목록 API·고정 버전 asset·하네스 조회를 함께 확인해요. 이전 GitHub API의 이동 응답에 기대어 새 설치가 계속 된다고 가정하지 않아요.

## 검증하고 배포해요

`pnpm test:registry`는 규격·해시·의존성·개별 선택 범위를 검사하고 생성 JSON만 복원한 소비 앱에서 모든 공개 컴포넌트의 타입·Vite CSS 연결과 대표 Next.js SSR·hydration·상호작용을 확인해요. 수행 범위는 [검증 기준](testing.md#선택-설치-데이터를-확인해요)을 따라요.

GitHub Release `v{콘텐츠 버전}`의 개별 asset으로 생성 폴더의 JSON 파일 전부를 제공하는 것을 배포 계약으로 정해요. `filename`은 같은 Release의 파일명이에요. 레지스트리와 그 UI 원본의 커밋을 고정하고, 같은 태그의 데이터를 덮어쓰지 않아요. npm에서 삭제된 전체 UI 패키지의 번호에 맞추려고 소스 콘텐츠를 다시 게시하지 않아요. 소스 배포를 위해 전체 UI 패키지의 npm 게시를 필수로 요구하지 않아요.

설치 도구의 릴리스는 콘텐츠 릴리스와 구분하고 지원 규격·콘텐츠 범위를 확인해요. 번호와 게시 순서는 [버전 기준](versioning.md#설치-도구와-콘텐츠-버전을-구분해요)과 [릴리스 절차](../handbook/releasing.md)를 따라요. 게시된 `0.0.0`에 뒤늦게 다른 소스를 붙이지 않고 다음 미게시 콘텐츠 버전의 릴리스에서 시작해요.

생성 결과의 버전 숫자만으로 공개 Release가 있다고 판단하지 않아요. GitHub Release 업로드·npm 게시·CLI 연동 완료 여부는 각각 확인해서 안내해요.

일반 사용자에게 제공할 목록과 항목은 저장소 권한이나 토큰 없이 받을 수 있어야 해요. 인증된 GitHub 도구의 업로드 성공과 익명 다운로드 성공을 구분해요. 사전 확인과 배포 위치 합의는 [릴리스 절차](../handbook/releasing.md#cli와-ui-소스-콘텐츠를-배포해요)를 따라요.

컴포넌트 추가 명령의 자동 초기화는 [확정된 후속 작업](../handbook/improvements.md#컴포넌트-추가-시-자동-초기화를-별도-브랜치에서-구현해요)이에요. 현재 `add`에는 먼저 만든 설정이 필요하며, 자동 초기화와 폰트 포함이 구현·검증되기 전에는 이미 지원하는 기능으로 안내하지 않아요.

## 조립 컴포넌트 설치 확장을 구분해요

현재 `dependencies`는 실제 소스 참조로 수집해요. 공식 조합의 기본 구성 요소까지 루트 항목 하나로 받도록 하는 변경은 [후속 설치 개선](../handbook/improvements.md#조립-컴포넌트의-기본-설치에-구성-요소를-포함해요)으로 합의했으며 아직 구현하지 않았어요. 문서 화면에서 한 그룹으로 소개한다는 이유로 설치가 자동 완료된다고 안내하지 않아요.
