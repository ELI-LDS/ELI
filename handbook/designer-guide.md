# 디자이너 협업 가이드

ELI는 동아리 개발자가 디자인을 다시 결정하지 않고 사용할 수 있는 React 컴포넌트 라이브러리예요. 이 문서는 디자인을 전달하고 실제 구현을 함께 확인할 때 사용해요.

해당하는 항목만 작성해요. 정해지지 않은 내용은 `미정`으로 표시하고, 기존 디자인과 같다면 해당 Figma 링크를 연결해요. 같은 명세를 여러 문서에 복사할 필요는 없어요.

## 디자인을 전달해요

| 항목 | 함께 알려주세요 |
| --- | --- |
| 목적과 선택 기준 | 어떤 상황에 쓰는지, 비슷한 컴포넌트와 어떻게 구분하는지 |
| 기준 디자인 | Figma 컴포넌트·Variables 링크, 전달 날짜, 확정·검토 중·미정 여부 |
| 형태와 상태 | 크기·형태별 차이, 기본·Hover·Pressed·Focus·Disabled 등 해당하는 상태 |
| 토큰 | 색상·타이포그래피·간격·모서리·그림자의 토큰 이름, 새로 필요한 토큰 |
| 콘텐츠 | 기본 문구, 최대 줄 수, 긴 문구의 줄바꿈·말줄임, 아이콘 유무와 위치 |
| 반응형 | 고정 크기와 유동 크기, 최소·최대 크기, 좁은 화면에서 달라지는 배치 |
| 입력 환경 | 마우스 Hover 없이 터치·키보드만으로 가능한 동작, 모바일 가상 키보드가 열렸을 때의 배치 |
| 동작 | 클릭·선택·닫기 결과, 적용할 애니메이션의 시간과 easing |
| 사용 규모와 성능 | 목록의 최대 항목 수, 동시에 움직이는 요소 수, 규모를 넘을 때 사용할 대체 패턴 |
| 변경 허용 범위 | 사용자가 바꿀 수 있는 문구·아이콘·색상·크기와 유지해야 할 기준 |

화면 예시에 표시된 너비가 고정값인지 예시값인지 구분해요. 특정 상태가 없거나 적용되지 않는다면 그 사실을 적어주세요. 미정인 디자인 값은 개발자가 임의로 확정하지 않고 관련 코드에 TODO와 기준 링크를 남겨요.

## 선택 기준을 합의해요

`color`, `variant`, `size`처럼 사용자가 골라야 하는 값이 있다면 모양뿐 아니라 선택 이유도 함께 정해요. 아래 항목 중 해당하는 내용을 합의하고, 아직 정하지 못한 항목은 `미정`으로 표시해요.

| 합의할 항목 | 확인할 질문 |
| --- | --- |
| 역할과 우선순위 | 각 선택지는 주 행동·보조 행동처럼 어떤 역할과 강조 수준을 나타내나요? |
| 선택지 구분 | 비슷해 보이는 선택지는 어떤 상황을 기준으로 구분하나요? |
| 권장 상황 | 이 선택지를 우선 사용해야 하는 대표적인 상황은 무엇인가요? |
| 피해야 하는 상황 | 잘못된 인상을 주거나 다른 선택지를 써야 하는 상황은 무엇인가요? |
| 조합과 제약 | 한 화면에서 함께 쓸 수 있는 조합, 개수나 배치 제한이 있나요? |
| 크기 기준 | 화면 크기, 콘텐츠 밀도와 사용 영역에 따라 어떤 크기를 고르나요? |
| 콘텐츠 영향 | 문구 길이, 아이콘 유무나 행동 종류에 따라 선택이 달라지나요? |
| 기본값의 의미 | 기본값은 가장 권장하는 선택인가요, 단순한 초기값인가요? |
| 예시와 반례 | 올바른 사용 예시와 혼동하기 쉬운 잘못된 예시는 무엇인가요? |

선택 기준은 개발 편의를 위한 임의 규칙이 아니라 디자인 시스템의 사용 원칙이에요. 합의한 결과의 개발 적용 방법과 완료 기준은 [컴포넌트 구현 규칙](../Agent/components.md#선택-기준을-함께-제공해요)에서 관리해요.

## 성능 범위를 합의해요

목록이나 반복 항목이 있는 컴포넌트는 일반적인 예시뿐 아니라 실제 서비스에서 예상하는 사용 규모를 함께 정해요. 아직 정하지 못한 내용은 `미정`으로 표시하고, 개발자가 임의의 최대값이나 최적화 방식을 확정하지 않아요.

| 합의할 항목 | 확인할 질문 |
| --- | --- |
| 최대 사용 규모 | 목록과 반복 항목은 최대 몇 개까지 기본 컴포넌트로 지원하나요? |
| 동시 모션 | 여러 항목이 함께 바뀔 때 어떤 요소까지 동시에 움직여야 하나요? |
| 초과 시 대안 | 권장 범위를 넘으면 검색, 페이지 나누기나 다른 컴포넌트 중 무엇을 사용하나요? |
| 가상화 | 화면에 보이는 항목만 렌더링해도 디자인·키보드·화면 낭독기 경험을 유지할 수 있나요? |
| 성능과 모션 조정 | 측정 결과가 느릴 때 유지해야 할 표현과 단순화할 수 있는 표현은 무엇인가요? |

측정 도구와 통과 기준은 개발 검증 영역이므로 [검증 기준](../Agent/testing.md#상호작용-성능을-별도로-확인해요)에서 관리해요. 합의한 범위는 Figma 설명이나 관련 PR에 남겨 이후 측정 시나리오와 연결해요.

## 역할을 나눠 함께 결정해요

- 디자이너는 시각적 명세와 사용 목적, 콘텐츠·반응형·상태 표현을 정리해요.
- 개발자는 공개 API, 기본 HTML 요소, 접근성 속성, 키보드·포커스 처리와 SSR 구현을 담당해요.
- 상태 전환, 포커스 표시, 긴 문구와 확대 화면의 처리처럼 사용 경험에 영향을 주는 내용은 함께 확인해요. Figma에 표시되지 않았다는 이유로 필요한 접근성 동작을 생략하지 않아요.

컴포넌트만으로 사용 의도가 전달되기 어렵다면 실제 사용 화면이나 짧은 흐름을 함께 전달해요. 예를 들어 입력 오류가 언제 나타나고, 제출 결과를 어디에서 알려주는지 보여줄 수 있어요.

## 반복되는 커스터마이징을 검토해요

소비 프로젝트에서 같은 스타일 변경이 반복되면 다음 질문을 함께 확인해요. 반복 적용할 개발 규칙과 설명 방법은 [컴포넌트 지침](../Agent/components.md#필요한-곳만-바꿀-수-있어요)에서 관리해요.

- 기본 디자인의 정렬·크기 같은 버그를 보정한 변경인가요?
- 해당 제품에만 필요한 변형인가요, 여러 제품에서 공통으로 필요한 선택지인가요?
- 공식 선택지로 제공한다면 어떤 상황에서 고르고, 어떤 조합은 피해야 하나요?
- 색상·크기를 바꾼 뒤에도 상태 구분·포커스·가독성과 반응형 배치가 유지되나요?

현재는 실제 소비 사례가 없으므로 임의의 빈도나 사용 요구를 만들어 선택지를 추가하지 않아요.

## 변경 사항을 전달해요

기존 디자인을 수정할 때는 아래 형식으로 바뀐 부분만 알려주세요. Figma 링크는 이후에도 바뀔 수 있으므로 검토에 사용한 날짜와 주요 변경 내용을 함께 남겨요.

현재는 외부 사용자가 없는 실험 단계라 기존 배포 구조를 보존해야 한다고 가정하지 않아요. 디자인·동작·공통 토큰이 바뀌는 영향과 문서의 선택 기준도 함께 확인해요. 배포 단계와 버전 판단은 [버전 규칙](../Agent/versioning.md)을 따라요.

```text
대상 / 사용 목적:
Figma 링크 / 전달 날짜:
상태: 확정 / 검토 중 / 미정
변경 내용: 이전 → 변경 후
영향 범위: 해당 형태·상태 또는 공통 토큰을 사용하는 전체 요소
선택 기준: 권장 상황 / 피해야 하는 상황 / 조합 제약
남은 결정:
```

## Storybook에서 함께 확인해요

[ELI Storybook](https://eli-storybook.jihong.dev)의 `한눈에 보기`에서 형태·크기·색상·상태를 함께 비교하고, `직접 바꿔보기`에서 문구와 공개 속성을 바꿔봐요. 변경할 공개 속성이 없는 컴포넌트는 `한눈에 보기`만 제공할 수 있어요. 개발 구현 규칙은 [컴포넌트 구현 규칙](../Agent/components.md#storybook을-함께-확인해요)에서 관리해요. 아직 배포되지 않은 작업은 개발자가 제공하는 미리보기에서 확인해요.

- 기본 모양뿐 아니라 실제 클릭·입력·선택과 키보드 이동을 확인해요.
- 긴 문구, 콘텐츠가 없는 경우, 좁은 화면과 글자가 확대된 경우도 확인해요.
- 데스크톱의 Hover뿐 아니라 Android·iOS의 터치 환경에서도 같은 작업을 완료할 수 있는지 확인해요.
- 수정 의견은 Story 이름, 재현 방법, 기대한 결과와 현재 결과를 함께 남겨요. 필요하면 Figma 링크나 캡처를 첨부해요.
- 남은 수정과 미정 사항을 구분하고, 디자인 검토 결과를 해당 PR에 기록해요. 디자인 확인과 개발 검증이 완료된 범위를 각각 표시해요.
