# ELI 개선 제안

초보 개발자가 ELI의 UI에 기능을 쉽게 연결하도록 돕기 위한 개선 후보와 남은 구현 범위를 관리해요. 각 항목의 상태를 구분하고, 방향을 합의했다는 사실을 구현 완료나 일정 확정으로 설명하지 않아요. 이 문서만으로 코드 변경이나 의존성 추가를 시작하지 않아요.

컴포넌트 선택 기준은 현재 적용할 규칙으로 승격했어요. 디자이너와 합의할 내용은 [디자이너 협업 가이드](designer-guide.md#선택-기준을-합의해요), 개발 적용 방법은 [컴포넌트 구현 규칙](../Agent/components.md#선택-기준을-함께-제공해요)에서 관리해요.

[FECONF 2026 「디자인 시스템, 더 나아가서」 발표 자료](https://junghyeonsu.github.io/feconf-2026-public/)의 맥락 전달·레퍼런스·사용 패턴 논의를 참고했어요. 아래 우선순위와 적용 방법은 ELI의 현재 규모에 맞춘 제안이며, 당근의 구현 방식을 그대로 도입한다는 뜻은 아니에요.

## 개선 후보

| --- | --- | --- | --- | --- |

| 승인된 화면 예시 | 디자인 변경 후 무엇을 기준으로 비교할지 불명확할 수 있어요. | 디자이너가 확인한 Story와 Figma 기준 링크, 검토 날짜를 PR에 남겨요. 자동 화면 비교는 반복 확인 비용이 커지면 검토해요. | 변경 전후 화면과 검토 당시의 기준을 추적할 수 있어요. | 중간 / 제안 |
| Docs·MCP의 자료 공유 | 사람용 설명과 AI용 설명을 따로 관리하면 내용이 달라질 수 있어요. | [JSON 검토 절차](component-guide-json.md)에 따른 승인본·사용 예시와 공통 조회 계층·MCP 연결을 구현했어요. 사용자용 문서 화면은 같은 자료를 읽도록 후속 작업에서 연결해요. [검토 기록](component-guide-review.md)과 [연동 인계](component-guide-handoff.md)에서 승인 상태와 실제 검증 범위를 확인해요. | 같은 컴포넌트의 공개 API·사용 예시·제약을 두 경로에서 일관되게 확인할 수 있어요. | MCP 연결 완료 / 문서 화면 예정 |

사용 패턴은 컴포넌트를 조합하는 예시예요. 서비스별 검증 규칙과 서버 요청은 소비 앱이 담당하고, 예제에서는 바꿔 넣을 위치를 보여줘요. 예시 하나를 만들기 위해 별도의 런타임 패키지를 추가하지 않아요.

새로운 디자인 언어나 전체 화면 자동 수집 시스템은 현재 우선 대상에 포함하지 않아요. 기존 Figma·React·CSS·Storybook으로 해결하기 어려운 구체적인 문제가 생기면 다시 검토해요.

선택 컴포넌트 설치의 배포 구조는 [프로젝트 구조](../Agent/architecture.md#소스-설치를-기본으로-사용해요), 패키지 매니저별 실행 명령은 [소비자 패키지 매니저 지원](../Agent/package-managers.md#소스-추가를-기본-소비-방식으로-사용해요)에서 관리해요. npm 하위 경로 import를 한 컴포넌트만 다운로드하는 기능으로 안내하지 않아요. 게시된 CLI·콘텐츠 버전과 원격 MCP가 설명하는 소스 버전을 구분해요. 현재 연결 상태와 남은 범위는 [연동 인계](component-guide-handoff.md)에서 확인해요.

## 배포 안정성 검사를 보완해요

현재 `pnpm check`는 실제 tarball의 구성·공개 경로·타입·Vite 빌드·일반 SSR·브라우저 상호작용·axe 접근성·Next.js App Router의 빌드와 hydration·용량을 확인해요. 아래 표는 완료된 기반과 아직 남은 확장 범위를 함께 관리해요. 현재 필수 검사와 결과 해석은 [검증 기준](../Agent/testing.md#소비자-입장에서-확인해요)에서 관리해요. 상호작용 성능 기준선은 [Design Systems Should Be Fast by Default](https://denodell.com/blog/design-systems-should-be-fast-by-default)의 측정 관점을 ELI 환경에 맞게 적용하는 제안이에요.

| 순서 | 개선 항목 | 확인할 문제 | 완료 기준 | 상태 |
| --- | --- | --- | --- | --- |
| 1 | 격리된 tarball 설치 | 저장소의 상위 `node_modules`에 우연히 의존하거나 peer dependency 충돌을 숨길 수 있어요. | 저장소 밖 임시 경로에서 React·React DOM을 명시한 소비 앱이 `--legacy-peer-deps` 없이 설치·타입 검사·빌드돼요. | 완료 |
| 2 | 패키지 매니저 호환성 | npm·pnpm·Yarn·Bun의 peer dependency와 설치 방식 차이로 특정 환경에서만 실패할 수 있어요. | [패키지 매니저 지원](../Agent/package-managers.md)의 행렬대로 같은 tarball을 격리 설치하고 타입 검사·소비 빌드를 통과해요. | 완료 |
| 3 | 브라우저 상호작용과 계산 스타일 | CSS가 번들에 존재해도 실제 우선순위가 다르거나 상태 동작이 깨질 수 있어요. | 클릭·입력·선택·키보드·포커스와 외부 클래스의 Default·Hover·Pressed·Disabled 계산 스타일을 실제 브라우저에서 검증해요. | 진행 중 |
| 4 | 상호작용 성능 기준선 | 패키지 용량만으로 긴 목록과 대량 상태 변경에서 UI가 멈추는 문제를 찾을 수 없어요. | [검증 기준](../Agent/testing.md#상호작용-성능을-별도로-확인해요)의 대표 시나리오를 프로덕션 빌드에서 반복 측정하고, 전체 처리 시간·최장 멈춤 시간·확장 비율을 PR에서 비교해요. | 진행 중 |
| 5 | Next.js 소비 예제 | 일반 SSR 검사만으로 RSC·`use client`·hydration 호환성을 보장할 수 없어요. | 실제 tarball의 App Router 프로덕션 빌드·서버 HTML·클라이언트 경계·CSS 연결을 확인하고, 브라우저 hydration과 콘솔 오류 검사까지 완료해요. | 완료 |
| 6 | 접근성 자동 검사 | Storybook 수동 확인만으로 화면 낭독기가 읽는 설명·역할·상태와 키보드 회귀를 놓칠 수 있어요. | 주요 컴포넌트의 접근성 속성·키보드 조작·포커스 이동을 자동 검사하고 예외를 기록해요. | 진행 중 |
| 7 | 시각 회귀 | 토큰이나 공통 CSS 변경으로 여러 컴포넌트의 화면이 함께 달라질 수 있어요. | 디자이너가 승인한 주요 Story의 모바일·데스크탑 기준 화면을 비교하고 의도한 차이만 승인해요. | 제안 |
| 8 | Node.js·React·브라우저 행렬 | 지원 범위를 넓힐 때 특정 버전이나 브라우저에서만 문제가 발생할 수 있어요. | 실제 Chrome·Edge와 Playwright의 Chromium·Firefox·WebKit, Android·iOS 기기 조건을 CI에서 검증하고 실제 Safari·모바일 실기기 결과를 릴리스에 기록해요. | 진행 중 |

도입 순서는 격리 설치, 패키지 매니저 호환성, 브라우저 상호작용과 계산 스타일, 상호작용 성능 기준선, Next.js 소비 예제, 접근성, 시각 회귀, Node.js·React·브라우저 행렬 순으로 잡아요. npm·pnpm·Yarn·Bun은 초기 배포 지원 범위로 합의했으므로 패키지 매니저 호환성 검사를 릴리스 전에 완료해요. 새 테스트 도구는 실행 의존성이 아니라 개발 의존성으로 검토하고, 해결하는 문제와 설치 용량·유지 비용을 PR에 기록해요.

2026년 10월 28일에는 SHA-256 `a171f469c0814211b71ed4a7fabefa14ff2aeed2bd1d6480c343b3812e69ae3e`인 같은 tarball을 저장소 밖 새 임시 소비 앱에 설치해 패키지 매니저 행렬을 수동으로 통과했어요. 2026년 11월 2일에는 같은 범위를 `.github/workflows/package-manager-compatibility.yml`과 `tests/package-managers/`로 자동화했어요. 강제 설치나 peer dependency 완화 옵션은 사용하지 않아요. Next.js 16.4.6 프로덕션 앱에서는 브라우저 hydration 후 Button·Select 상호작용과 콘솔 오류를 자동 확인해요. Storybook 기준 화면과 VoiceOver 수동 검토는 별도 항목으로 남겨요.

같은 날 `tests/performance/`에 Select 125개·250개와 Checkbox 100개를 프로덕션 빌드·4배 CPU 제한·3회 중앙값으로 측정하는 기준선 도구를 추가했어요. 아직 기기 간 비교 환경과 회귀 허용 범위를 확정하지 않았으므로 수치로 PR을 실패시키지 않고, 안정된 기준을 합의한 뒤 완료로 승격해요.

각 검사가 구현되면 이 문서의 상태를 `완료`로 바꾸는 데 그치지 않고 `pnpm check` 또는 릴리스 전용 명령에 연결해요. 반복 적용할 필수 기준은 [검증 기준](../Agent/testing.md)에 승격하고 이 문서에는 결정 이유와 결과 링크만 남겨요.

## 커스터마이징 현황 조회를 검토해요

상태는 `제안`이에요. 실제 소비 사례가 쌓이면 설치 기록과 로컬 import를 기준으로 반복되는 스타일 변경을 확인하는 선택형 도구를 검토해요. 클래스·인라인 스타일·직접 수정한 소스가 있다는 사실만으로 규칙 위반이나 PR 실패를 판정하지 않아요. 반복 요구를 검토하는 현재 기준은 [컴포넌트 지침](../Agent/components.md#필요한-곳만-바꿀-수-있어요)과 [디자이너 질문](designer-guide.md#반복되는-커스터마이징을-검토해요)에 있어요.

## Pretendard 기본 제공을 후속 작업으로 진행해요

2026-11-25에 방향을 합의했고 2026-11-27에 폰트 파일 포함도 별도 브랜치에서 진행하기로 재확인했어요. 상태는 `방향 확정 · 구현 보류`예요. 현재 웹사이트 작업과 분리하고 이후 별도 작업에서 진행해요.

- ELI 소스 설치 시 Pretendard 폰트 파일 제공과 로딩 연결을 기본으로 지원해요. 토큰의 글꼴 이름만 지정하고 실제 폰트 연결을 사용자가 알아서 해야 하는 부담을 줄여요.
- 기존 Pretendard 설치·로딩 설정을 먼저 확인하고 재사용해요. 기존 설정을 덮어쓰거나 같은 폰트를 중복 설치·로딩하지 않아요. 판별이 불확실한 경우의 처리 방식도 구현 전에 정해요.
- 여러 컴포넌트를 추가해도 공통 폰트는 한 번만 제공해요. 파일 제공 위치·설치 기록·연결 방식·라이선스와 다운로드량은 후속 작업에서 검토해요.
- 구현할 때 [현재 폰트 로딩 기준](../Agent/architecture.md#폰트-로딩을-분리해요), CLI·레지스트리·설치 안내와 관련 검증을 함께 갱신해요. 현재 CLI가 폰트를 자동 제공한다고 안내하지 않아요.

이번 합의로 현재 문서 앱의 폰트 의존성이나 로딩 코드를 바꾸지는 않아요.

단순 텍스트 검색만으로 별칭·공통 컴포넌트·동적 클래스를 모두 분석했다고 표현하지 않아요. 수집·분석 도구는 아직 구현하지 않았어요. [className Considered Harmful](https://mattrothenberg.com/notes/classname-considered-harmful/)의 변경 현황 관찰 관점을 참고하되, 소스를 직접 소유하는 ELI 사용자에게 스타일 제한을 강제하는 방식은 채택하지 않아요.

## 제안을 적용해요

상태는 `제안 → 합의 → 진행 중 → 완료`로 관리해요. 도입하지 않기로 하거나 미루면 `보류`와 이유를 남겨요. 작업을 합의할 때 담당자와 관련 이슈·PR 링크를 추가해요.

다음 개선 후보로 사용 패턴 하나를 구현해봐요. 그 과정에서 드러난 API·접근성 문제를 정리하고 필요한 검증을 추가한 뒤, Docs·MCP로 전달할 자료를 확장하는 순서를 제안해요.

반복 적용할 규칙이 확정되면 관련 `Agent/` 문서에 반영하고, 구현된 사용법은 JSDoc·Storybook·사용자 문서에 반영해요. 이 문서에는 결정 이유와 결과 링크를 남겨 같은 규칙을 중복 관리하지 않아요.

## 컴포넌트 추가 시 자동 초기화를 별도 브랜치에서 구현해요

2026-11-27에 방향을 합의했으며 상태는 `방향 확정 · 구현 보류`예요. 현재 CLI는 `.eli/config.json`이 없는 상태에서 `add`를 실행하면 `NOT_INITIALIZED`를 반환하고 먼저 `init`을 안내해요. 이번 독스 수정에서는 이 동작을 바꾸지 않아요.

후속 목표는 사용자가 `npx eli-design@latest add button`부터 실행해도 초기 설정과 선택 설치가 이어지는 것이에요.

- 설정이 없을 때만 기존 `init`과 같은 기본 설치 위치·레지스트리 버전 결정을 재사용해요. 기존 설정·설치 기록이 있으면 그대로 사용해요.
- 잘못된 설정이나 버전 충돌을 미초기화로 취급해 덮어쓰지 않아요. 사용자가 수정한 파일·프로젝트 별칭·패키지 매니저 설정도 유지해요.
- 잘못된 컴포넌트 ID·필수 의존성 오류·설치 충돌을 먼저 확인하고 실패 후 설정만 남는 부분 설치를 방지해요. `--dry-run`은 설정과 설치 파일을 쓰지 않아야 해요.
- 명시적인 `init`도 유지해 설치 위치를 먼저 지정할 수 있게 해요. [CLI·레지스트리 기준](../Agent/registry.md), 명령 도움말·README·독스의 설치 설명과 설치 기록·실패 복구 검증을 함께 갱신해요.
- 빈 프로젝트·기존 설정·손상된 설정·실패 복구·반복 실행·패키지 매니저 행렬에서 확인해요. 현재 CLI의 `init` 필요 여부는 CLI 도움말·README에서 유지해요. 사용자 요청으로 상세 페이지의 설치 영역은 `add` 코드만 표시하며, 이 화면 변경을 자동 초기화 구현 완료로 취급하지 않아요.

폰트 포함은 [Pretendard 후속 작업](#pretendard-기본-제공을-후속-작업으로-진행해요)과 함께 설치 흐름을 검토하되, 두 항목의 완료·배포 여부는 따로 기록해요.

## 독스 복사 버튼을 아이콘으로 변경해요

상태는 `방향 확정 · 디자인 전달 후 구현`이에요. 현재 `복사` 텍스트 버튼은 유지하고, 디자이너가 전달한 아이콘으로 후속 변경해요. 임의의 아이콘이나 새로운 의존성을 먼저 추가하지 않아요.

아이콘으로 바꿔도 동작 설명(`aria-label`), 키보드 조작, 복사 완료·실패 피드백을 유지해요. 복사하는 값은 줄 번호가 없는 원문이어야 해요. 실제 변경할 때 [독스 페이지 작성 기준](../Agent/docs-pages.md)에 반영해요.

## 조립 컴포넌트의 기본 설치에 구성 요소를 포함해요

2026-11-27 사용자 요청이며 상태는 `방향 확정 · 후속 브랜치에서 구현`이에요. 현재 생성된 레지스트리를 확인한 결과 NavigationBar는 Item을 자동으로 받지만 NavigationDrawer는 토큰만 의존하고 Category·Menu를 포함하지 않아요. Menu를 별도로 요청하면 Drawer와 Item이 따라오는 현재 관계와 구분해요.

- 목표는 `npx eli-design@latest add navigation-drawer` 하나로 공식 기본 조합에 쓰는 Category·Menu·Item까지 제공하는 것이에요. 기본 설치를 위해 조각 ID를 사용자가 모두 나열하게 하지 않아요.
- 파일 import 의존성과 공식 조합에 필요한 설치 의존성을 구분해 명시적인 조합 메타데이터를 검토해요. 단순 재수출이나 불필요한 소스 import로 의존성을 억지로 만들지 않아요.
- 현재 Menu → Drawer 참조가 있으므로 Drawer → Menu 추가 시 순환 의존성을 검토하고 생성기·CLI의 재귀 해석·중복 방지를 확인해요. 토큰·공유 파일은 한 번만 설치하고 무관한 UI·하네스는 포함하지 않아요.
- 구성 요소의 개별 설치는 유지해요. 구성 요소가 있거나 수정된 소비 프로젝트에서 파일 보호와 설치 기록·해시가 유지되어야 해요.
- 구현 시 [레지스트리 기준](../Agent/registry.md)·설치 예시·독스와 의존성 소비 검사를 함께 수정하고 콘텐츠 버전 영향은 별도로 판단해요. 실제 레지스트리·CLI·설치 기록은 후속 작업에서 변경해요. 사용자 요청으로 웹 문서는 목표 방식인 `add navigation-drawer`만 먼저 표시해요. 현재 설치 동작과 일치하지 않는 선반영 상태이며 실제 소비 검사는 미완료예요.

### FAB 구성의 기본 설치도 함께 정리해요

2026-11-27에 `add fab` 하나로 FabMenu·FabMenuSegment까지 받는 방향을 요청받았으며, 설치 구조 구현은 사용자의 결정으로 다음 작업에 남겼어요. 현재 실제 레지스트리는 FabMenu → Fab·FabMenuSegment이며 반대 방향은 없어요.

후속 작업에서 조립 메타데이터·순환 참조·공유 파일 중복 방지와 개별 설치 유지 여부를 함께 정하고 CLI·생성기·소비 검사를 확인해요. 이번에는 레지스트리를 바꾸지 않아요. 사용자 요청으로 웹 문서는 목표 방식인 `add fab`만 먼저 표시하고 `items` 예시에는 추가 설치 코드를 표시하지 않아요. 현재 `add fab`가 이미 메뉴를 포함하는 것은 아니며 실제 설치 구현·검증은 미완료예요.

두 웹 문서의 기본 예시에는 `installStatus: planned`를 남기고 설치 import 검사는 현재 누락되는 모듈을 정확히 기록해요. 실제 설치 동작을 검증한 것으로 처리하지 않으며 소비 검사 TODO 두 개를 유지해요. 다음 작업에서는 목표 의존성 구현·실제 소비 검사를 완료한 뒤 예정 표시·누락 기록·TODO를 해제해요. 이 상태로 사용자 문서나 설치 변경의 공개 배포 검증을 완료했다고 기록하지 않아요.
