# ELI 개선 제안

초보 개발자가 ELI의 UI에 기능을 쉽게 연결하도록 돕기 위한 개선 후보예요. 아래 항목은 모두 **제안 상태**이며 구현 완료나 일정 확정을 의미하지 않아요. 이 문서만으로 코드 변경이나 의존성 추가를 시작하지 않아요.

컴포넌트 선택 기준은 현재 적용할 규칙으로 승격했어요. 디자이너와 합의할 내용은 [디자이너 협업 가이드](designer-guide.md#선택-기준을-합의해요), 개발 적용 방법은 [컴포넌트 구현 규칙](../Agent/components.md#선택-기준을-함께-제공해요)에서 관리해요.

[FECONF 2026 「디자인 시스템, 더 나아가서」 발표 자료](https://junghyeonsu.github.io/feconf-2026-public/)의 맥락 전달·레퍼런스·사용 패턴 논의를 참고했어요. 아래 우선순위와 적용 방법은 ELI의 현재 규모에 맞춘 제안이며, 당근의 구현 방식을 그대로 도입한다는 뜻은 아니에요.

## 개선 후보

| 제안 | 해결하려는 문제 | 적용 방법 | 완료 기준 | 우선순위 / 상태 |
| --- | --- | --- | --- | --- |
| 선택 컴포넌트 설치 | Button 하나만 필요한 사용자가 관계없는 컴포넌트까지 내려받게 돼요. | shadcn/ui처럼 레지스트리와 CLI를 제공해 공통 `tokens/`와 요청한 컴포넌트 폴더, 실제 참조 파일만 소비 프로젝트에 추가해요. 선택 설치에서는 `@eli/ui` 전체 패키지를 설치하지 않고, 기존 전체 패키지 방식은 별도로 유지해요. | 네 패키지 매니저에서 Button 하나를 추가했을 때 토큰과 Button 관련 파일만 생성되고, 다른 컴포넌트가 포함되지 않아요. 의존 파일 누락·중복 추가·사용자 파일 무단 덮어쓰기 없이 타입 검사와 빌드를 통과해요. | 높음 / 합의 |
| 실제 사용 패턴 | 개별 컴포넌트 예시만으로 입력·검증·제출을 연결하기 어려워요. | 첫 후보로 Storybook에 회원가입 폼 예시를 만들고, 입력·오류·처리 중·결과 피드백을 연결해요. 필요한 디자인은 먼저 합의해요. | 개발자가 검증 함수와 요청 함수를 자신의 코드로 교체할 수 있고, 성공·실패 흐름을 직접 확인할 수 있어요. | 높음 / 제안 |
| 승인된 화면 예시 | 디자인 변경 후 무엇을 기준으로 비교할지 불명확할 수 있어요. | 디자이너가 확인한 Story와 Figma 기준 링크, 검토 날짜를 PR에 남겨요. 자동 화면 비교는 반복 확인 비용이 커지면 검토해요. | 변경 전후 화면과 검토 당시의 기준을 추적할 수 있어요. | 중간 / 제안 |
| Docs·MCP의 자료 공유 | 사람용 설명과 AI용 설명을 따로 관리하면 내용이 달라질 수 있어요. | 한국어 사용법과 예시의 기준 자료를 정한 뒤 Docs와 MCP가 같은 자료를 참조하도록 연결해요. | 같은 컴포넌트의 공개 API·사용 예시·제약을 두 경로에서 일관되게 확인할 수 있어요. | 후속 / 제안 |

사용 패턴은 컴포넌트를 조합하는 예시예요. 서비스별 검증 규칙과 서버 요청은 소비 앱이 담당하고, 예제에서는 바꿔 넣을 위치를 보여줘요. 예시 하나를 만들기 위해 별도의 런타임 패키지를 추가하지 않아요.

새로운 디자인 언어나 전체 화면 자동 수집 시스템은 현재 우선 대상에 포함하지 않아요. 기존 Figma·React·CSS·Storybook으로 해결하기 어려운 구체적인 문제가 생기면 다시 검토해요.

선택 컴포넌트 설치의 배포 구조는 [프로젝트 구조](../Agent/architecture.md#두-가지-소비-방식을-제공해요), 패키지 매니저별 실행 명령은 [소비자 패키지 매니저 지원](../Agent/package-managers.md#라이브러리는-프로젝트-의존성으로-설치해요)에서 관리해요. 레지스트리와 CLI가 구현되기 전에는 하위 경로 import를 한 컴포넌트만 다운로드하는 기능으로 안내하지 않아요.

## 배포 안정성 검사를 보완해요

현재 `pnpm check`는 실제 tarball의 구성·공개 경로·타입·Vite 빌드·일반 SSR·브라우저 상호작용·axe 접근성·Next.js App Router의 빌드와 hydration·용량을 확인해요. 아래 표는 완료된 기반과 아직 남은 확장 범위를 함께 관리해요. 현재 필수 검사와 결과 해석은 [검증 기준](../Agent/testing.md#소비자-입장에서-확인해요)에서 관리해요. 상호작용 성능 기준선은 [Design Systems Should Be Fast by Default](https://denodell.com/blog/design-systems-should-be-fast-by-default)의 측정 관점을 ELI 환경에 맞게 적용하는 제안이에요.

| 순서 | 개선 항목 | 확인할 문제 | 완료 기준 | 상태 |
| --- | --- | --- | --- | --- |
| 1 | 격리된 tarball 설치 | 저장소의 상위 `node_modules`에 우연히 의존하거나 peer dependency 충돌을 숨길 수 있어요. | 저장소 밖 임시 경로에서 React·React DOM을 명시한 소비 앱이 `--legacy-peer-deps` 없이 설치·타입 검사·빌드돼요. | 완료 |
| 2 | 패키지 매니저 호환성 | npm·pnpm·Yarn·Bun의 peer dependency와 설치 방식 차이로 특정 환경에서만 실패할 수 있어요. | [패키지 매니저 지원](../Agent/package-managers.md)의 행렬대로 같은 tarball을 격리 설치하고 타입 검사·소비 빌드를 통과해요. | 완료 |
| 3 | 브라우저 상호작용과 계산 스타일 | CSS가 번들에 존재해도 실제 우선순위가 다르거나 상태 동작이 깨질 수 있어요. | 클릭·입력·선택·키보드·포커스와 외부 클래스의 Default·Hover·Pressed·Disabled 계산 스타일을 실제 브라우저에서 검증해요. | 진행 중 |
| 4 | 상호작용 성능 기준선 | 패키지 용량만으로 긴 목록과 대량 상태 변경에서 UI가 멈추는 문제를 찾을 수 없어요. | [검증 기준](../Agent/testing.md#상호작용-성능을-별도로-확인해요)의 대표 시나리오를 프로덕션 빌드에서 반복 측정하고, 전체 처리 시간·최장 멈춤 시간·확장 비율을 PR에서 비교해요. | 제안 |
| 5 | Next.js 소비 예제 | 일반 SSR 검사만으로 RSC·`use client`·hydration 호환성을 보장할 수 없어요. | 실제 tarball의 App Router 프로덕션 빌드·서버 HTML·클라이언트 경계·CSS 연결을 확인하고, 브라우저 hydration과 콘솔 오류 검사까지 완료해요. | 완료 |
| 6 | 접근성 자동 검사 | Storybook 수동 확인만으로 화면 낭독기가 읽는 설명·역할·상태와 키보드 회귀를 놓칠 수 있어요. | 주요 컴포넌트의 접근성 속성·키보드 조작·포커스 이동을 자동 검사하고 예외를 기록해요. | 진행 중 |
| 7 | 시각 회귀 | 토큰이나 공통 CSS 변경으로 여러 컴포넌트의 화면이 함께 달라질 수 있어요. | 디자이너가 승인한 주요 Story의 모바일·데스크탑 기준 화면을 비교하고 의도한 차이만 승인해요. | 제안 |
| 8 | Node.js·React·브라우저 행렬 | 지원 범위를 넓힐 때 특정 버전이나 브라우저에서만 문제가 발생할 수 있어요. | README와 peer dependency에 약속한 Node.js·React·브라우저 조합을 CI에서 검증해요. | 제안 |

도입 순서는 격리 설치, 패키지 매니저 호환성, 브라우저 상호작용과 계산 스타일, 상호작용 성능 기준선, Next.js 소비 예제, 접근성, 시각 회귀, Node.js·React·브라우저 행렬 순으로 잡아요. npm·pnpm·Yarn·Bun은 초기 배포 지원 범위로 합의했으므로 패키지 매니저 호환성 검사를 릴리스 전에 완료해요. 새 테스트 도구는 실행 의존성이 아니라 개발 의존성으로 검토하고, 해결하는 문제와 설치 용량·유지 비용을 PR에 기록해요.

2026년 10월 28일에는 SHA-256 `a171f469c0814211b71ed4a7fabefa14ff2aeed2bd1d6480c343b3812e69ae3e`인 같은 tarball을 저장소 밖 새 임시 소비 앱에 설치해 패키지 매니저 행렬을 수동으로 통과했어요. 2026년 11월 2일에는 같은 범위를 `.github/workflows/package-manager-compatibility.yml`과 `tests/package-managers/`로 자동화했어요. 강제 설치나 peer dependency 완화 옵션은 사용하지 않아요. Next.js 16.4.3 프로덕션 앱에서는 브라우저 hydration 후 Button·Select 상호작용과 콘솔 오류를 자동 확인해요. Storybook 기준 화면과 VoiceOver 수동 검토는 별도 항목으로 남겨요.

각 검사가 구현되면 이 문서의 상태를 `완료`로 바꾸는 데 그치지 않고 `pnpm check` 또는 릴리스 전용 명령에 연결해요. 반복 적용할 필수 기준은 [검증 기준](../Agent/testing.md)에 승격하고 이 문서에는 결정 이유와 결과 링크만 남겨요.

## 제안을 적용해요

상태는 `제안 → 합의 → 진행 중 → 완료`로 관리해요. 도입하지 않기로 하거나 미루면 `보류`와 이유를 남겨요. 작업을 합의할 때 담당자와 관련 이슈·PR 링크를 추가해요.

다음 개선 후보로 사용 패턴 하나를 구현해봐요. 그 과정에서 드러난 API·접근성 문제를 정리하고 필요한 검증을 추가한 뒤, Docs·MCP로 전달할 자료를 확장하는 순서를 제안해요.

반복 적용할 규칙이 확정되면 관련 `Agent/` 문서에 반영하고, 구현된 사용법은 JSDoc·Storybook·사용자 문서에 반영해요. 이 문서에는 결정 이유와 결과 링크를 남겨 같은 규칙을 중복 관리하지 않아요.
