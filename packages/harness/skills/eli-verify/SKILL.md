# 디자인 시스템 점검하기

먼저 코드를 바꾸지 않고 보고해요. 고치는 것은 사용자가 승인한 뒤에 해요.

## 1. 기준을 가져와요

- `eli-docs`의 문서를 읽을 수 있어야 해요. 도구가 세션에 보이지 않으면 `eli` 스킬의 "원격 MCP에 연결해요"대로 등록하고 조회 스크립트로 이어서 진행해요. 스크립트로도 읽지 못할 때만 멈춰요. 기준 없이 점검하지 않아요.
- `get_guide`로 `verify` 가이드를 읽어요. 점검 규칙과 예외가 여기에 있어요. `not_found`이면 가이드가 아직 없는 거예요. 멈추지 않고 이 스킬의 기준으로 점검하고, 원격 점검 규칙 없이 봤다고 보고 맨 위에 적어요.
- `get_tokens`로 네 분류의 토큰을, `list_components`로 컴포넌트 목록을 가져와요. 점검에는 전체 값이 필요하므로 분류마다 한 번씩만 부르고 다시 부르지 않아요.
- `DESIGN.md`가 있으면 읽고, `## 토큰`에 적힌 프로젝트의 토큰 파일을 읽어요. 토큰 파일이 없으면 가장 먼저 보고하고 `/eli-design-system`으로 토큰부터 만들자고 안내해요.

## 2. 범위를 정해요

- 사용자가 폴더나 파일을 말했으면 그 범위만 봐요. 말하지 않았으면 프론트엔드 소스 전체를 봐요.
- `node_modules`, 빌드 결과물, 생성된 파일, 외부에서 가져온 코드는 보지 않아요.
- 스타일 방식을 먼저 확인해요. CSS 파일, CSS Modules, Tailwind, CSS-in-JS에 따라 찾는 방법이 달라요.

## 3. 찾아요

| 종류 | 찾는 것 |
| --- | --- |
| 값 직접 쓰기 | 토큰 파일 밖에서 직접 쓴 색상, 간격, 글자, 모서리, 그림자 값 |
| 단위 기준과 다름 | `DESIGN.md`의 `## 단위` 표와 다른 단위. 예: `px`로 쓴 글자 크기, `px`로 고정한 너비 |
| 글꼴 | 전역 `body` 밖에서 직접 쓴 `font-family`, Pretendard가 아닌 글꼴, 다시 정한 `--eli-font-family-sans`, 타이포그래피 토큰 없이 따로 쓴 `letter-spacing` |
| 토큰 건너뛰기 | 토큰 파일 밖의 화면 코드에서 직접 쓴 `--eli-` 변수 |
| 쓰지 않는 토큰 | 토큰 파일에 있지만 어디에서도 쓰지 않는 토큰 |
| 컴포넌트 직접 만들기 | ELI에 맞는 컴포넌트가 있는데 네이티브 요소나 자체 구현을 쓴 곳 |
| 잘못된 사용 | 문서에 없는 props, 없는 import 경로, 문서의 `when-to-use`와 다른 용도 |
| 스타일 덮어쓰기 | ELI 컴포넌트의 내부 클래스나 구조에 의존해 덮어쓴 스타일 |
| 권장과 다름 | 컴포넌트 문서의 `do-dont`에서 하지 말라고 한 사용법 |
| 방향과 다름 | `DESIGN.md`에 적힌 방향과 분명히 어긋나는 화면 |
| 문구 규칙과 다름 | `UX-WRITING.md`의 말투, 용어, 문구 형식과 다른 화면 문구 |

- 검색으로 후보를 넓게 찾은 뒤 파일을 읽고 확인해요. 검색 결과만으로 위반이라고 적지 않아요.
- 맞는 토큰이 없는 값도 위반이에요. 다만 비슷한 토큰으로 바꾸면 디자인이 달라지므로, 제안에는 "토큰 추가"라고 적고 어떤 역할 이름으로 추가할지 사용자에게 확인받아요.
- 컴포넌트를 바꾸자고 제안하기 전에 `get_component`로 그 컴포넌트가 이 용도에 맞는지 확인해요.
- "문구 규칙과 다름"은 `UX-WRITING.md`가 있을 때만 봐요. 없으면 가장 먼저 보고하고 `/eli-ux-writing`을 안내해요. 문구가 많으면 건수만 적고 자세한 수정은 `/eli-ux-writing`에 맡겨요.
- "권장과 다름"은 프로젝트가 실제로 쓰는 컴포넌트의 `do-dont` 섹션을 읽고 판단해요. 섹션이 없는 컴포넌트는 "확인하지 못한 것"에 적어요.

### 화면 품질도 봐요

디자인 시스템을 지켜도 실제 화면에서 깨지는 곳을 찾아요. 기준은 `eli` 스킬 폴더의 `references/css.md`와 `references/code.md`를 따르고, `verify` 가이드에 더 엄격한 값이 있으면 그 값을 따라요. 두 곳에 없는 기준을 지어내지 않아요. 종류는 "품질"로 적어 디자인 시스템 위반과 구분해요.

| 종류 | 찾는 것 |
| --- | --- |
| 상태 누락 | 데이터를 불러오는 화면에 로딩, 빈 화면, 오류 상태가 없는 곳 |
| 내용 넘침 | 긴 글자, 긴 이름, 큰 숫자가 들어오면 잘리거나 밀리는 곳 |
| 입력 | 라벨이 없는 입력창, 맞는 `type`·`inputmode`·`autocomplete`가 없는 입력창 |
| 터치 | 누르는 영역이 너무 작거나 서로 붙어 있는 요소, hover에서만 보이는 기능 |
| 포커스 | 키보드 포커스 표시를 지운 곳, 누를 수 있는데 `div`로 만든 요소 |
| 좁은 화면 | 고정 너비 때문에 모바일 너비에서 가로로 넘치는 곳 |
| 움직임 | 움직임 줄이기 설정을 따르지 않는 애니메이션, `width`·`top` 같은 배치 속성을 움직이는 애니메이션 |
| 우선순위 | `!important`, ID 선택자, 큰 `z-index`로 덮어쓴 스타일 |
| React | `useEffect`로 맞춘 상태, 순번으로 쓴 `key`, 컴포넌트 안에서 정의한 컴포넌트 |

브라우저 도구가 있으면 모바일 너비로 화면을 열어 가로 넘침과 콘솔 오류를 확인해요. 도구가 없으면 코드로 판단한 것임을 보고에 적어요.

## 4. 보고해요

```markdown
## 요약
위반 N건, 확인 필요 N건, 확인하지 못한 것 N건 (점검한 파일 N개)

## 위반
| 위치 | 종류 | 현재 코드 | 근거 | 제안 |

## 확인 필요
| 위치 | 이유 |

## 확인하지 못한 것
```

- 위치는 `파일:줄`로 적어요. 같은 문제가 여러 곳에 있으면 묶어서 건수와 함께 적어요.
- 근거에는 토큰 이름이나 문서의 어느 섹션인지 적어요.
- 원격에서 기준을 확인하지 못한 항목은 통과로 적지 않고 "확인하지 못한 것"에 적어요.
- 위반이 없으면 없다고 짧게 말해요.

보고한 뒤 무엇을 고칠지 물어요. 전부, 종류별, 파일별로 고를 수 있게 해요.

## 5. 고쳐요

- 승인받은 항목만 고쳐요. "확인 필요" 항목은 사용자가 방법을 정해 준 것만 고쳐요.
- 화면의 모양과 동작이 달라지는 수정은 미리 알려요.
- 기능 코드, 로직, 테스트를 함께 정리하지 않아요.
- 고친 뒤 프로젝트의 타입 검사와 린트를 실행해요. 브라우저 도구가 있으면 바뀐 화면을 확인해요.
- 고친 것, 남은 것, 확인하지 못한 것을 보고해요.
