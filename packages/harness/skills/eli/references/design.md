# 화면을 디자인하는 기준

새 화면을 만들거나 화면의 구성을 바꿀 때 읽어요. 디자이너의 시안이 있으면 시안을 따라요. 시안이 없을 때 이 기준으로 판단해요. 서비스의 방향은 `DESIGN.md`가 먼저예요. 이 문서와 `DESIGN.md`가 다르면 `DESIGN.md`를 따라요.

값은 모두 프로젝트 토큰에서 골라요. 이 문서의 기준을 맞추려고 값을 새로 만들지 않아요.

## 무엇이 중요한지 먼저 정해요

화면을 그리기 전에 답해요.

1. 사용자가 이 화면에서 하려는 일 하나는 무엇인가요?
2. 그 일을 하려면 무엇을 먼저 봐야 하나요?
3. 없어도 그 일을 할 수 있는 것은 무엇인가요?

3번에 해당하는 것은 빼거나 덜 눈에 띄게 해요.

## 위계

- **중요한 것 하나만 강조해요.** 모든 것을 강조하면 아무것도 강조되지 않아요.
- **덜 중요한 것을 약하게 해서 강조해요.** 중요한 것을 더 키우기 전에 나머지를 옅게, 작게 해요.
- **굵기와 색을 크기보다 먼저 써요.** 글자 크기를 여러 단계로 늘리지 않아요. 한 화면에서 제목, 본문, 보조 설명 세 단계면 충분해요.
- **라벨은 값보다 약하게 해요.** "가격 12,000원"에서 사용자가 보려는 것은 숫자예요.
- **주요 버튼은 화면에 하나예요.** 나머지 버튼은 브랜드 색을 빼고 중립색으로 낮춰요. 브랜드 색의 테두리 버튼이나 글자 버튼을 주요 버튼 옆에 나란히 두지 않아요. 어떤 변형이 어떤 중요도인지는 버튼 문서의 `variants`에서 확인해요.
- **위험한 동작이 가장 눈에 띄면 안 돼요.** 삭제 버튼을 주요 버튼으로 두지 않아요.

## 간격

- **관련 있는 것은 가깝게, 관련 없는 것은 멀게 둬요.** 묶음 안의 간격이 묶음 사이의 간격보다 작아야 해요. 간격이 모두 같으면 무엇이 한 묶음인지 알 수 없어요.
- **넉넉하게 시작해서 줄여요.** 좁게 시작하면 답답한 화면이 돼요.
- **토큰의 단계에서만 골라요.** 중간 값을 만들지 않아요.
- **선보다 여백으로 나눠요.** 아래 "테두리"의 순서를 따라요.
- **가장자리를 맞춰요.** 요소들의 왼쪽 끝이 한 줄에 놓이게 해요. 정렬이 어긋나면 정돈되지 않아 보여요.

## 색

기본은 중립색이에요. 색은 뜻이 있을 때만 써요. 토큰에 있는 색이라고 해서 어디에나 써도 되는 것은 아니에요.

- **화면의 대부분은 중립색이에요.** 배경, 표면, 글자, 아이콘은 중립색 토큰으로 써요. 색을 넣을지 망설여지면 넣지 않아요.
- **브랜드 색으로 채운 요소는 한 화면에 하나예요.** 그 하나가 주요 버튼이에요. 스크롤 없이 보이는 범위를 한 화면으로 세요.
- **브랜드 색을 쓸 수 있는 자리는 정해져 있어요.**

| 써요 | 쓰지 않아요 |
| --- | --- |
| 주요 버튼 하나 | 보조 버튼, 취소 버튼 |
| 지금 선택된 항목의 표시(탭, 내비게이션, 체크) | 제목, 본문, 가격 같은 글자 |
| 글 안의 링크 | 장식용 아이콘, 구역 제목 옆의 아이콘 |
| 진행 표시, 포커스 표시 | 카드·구역·머리글의 배경과 테두리 |
| | 배지, 태그, 구분선 꾸미기 |

- **ELI 컴포넌트가 스스로 쓰는 브랜드 색은 그대로 둬요.** 위 기준은 프로젝트가 직접 쓰는 화면 코드와, 컴포넌트의 변형을 고를 때 적용해요. 변형은 가장 덜 눈에 띄는 것부터 골라요.
- **상태 색은 그 상태가 실제로 있을 때만 써요.** 오류가 없는데 빨간색을, 성공을 알릴 일이 없는데 초록색을 쓰지 않아요. 분류나 꾸밈에 상태 색을 쓰지 않아요.
- **색이 있는 배경은 한 화면에 한 곳까지예요.** 안내 상자나 강조 구역을 여러 개 색으로 깔지 않아요.
- **색만으로 뜻을 전달하지 않아요.** 오류는 빨간색과 함께 문구나 아이콘으로도 알려요.
- **색이 있는 배경 위에 회색 글자를 쓰지 않아요.** 탁해 보이고 대비가 떨어져요. 같은 계열의 토큰을 써요.
- **강조는 색보다 굵기와 크기로 먼저 해요.** 글자를 눈에 띄게 하려고 브랜드 색을 입히지 않아요.

## 테두리

기본은 테두리가 없는 거예요. 상자마다 테두리를 두르면 화면이 격자로 보이고 내용보다 선이 먼저 보여요.

나눠야 할 때는 아래 순서로 해요. 앞 단계로 충분하면 다음 단계를 쓰지 않아요.

| 순서 | 방법 | 쓰는 때 |
| --- | --- | --- |
| 1 | 간격 | 항상 먼저 해 봐요. 묶음 사이를 묶음 안보다 넓게 띄워요 |
| 2 | 옅은 배경 | 간격만으로 묶음이 드러나지 않을 때. 표면 토큰 한 단계 차이로 해요 |
| 3 | 구분선 | 같은 종류의 항목이 길게 이어지는 목록에서만. 항목 사이에 한 줄만 그어요 |
| 4 | 테두리 | 배경과 같은 색의 면이라 경계가 보이지 않는데, 그 면 전체를 눌러야 할 때 |

- **한 요소에는 한 가지만 써요.** 테두리, 그림자, 배경색 차이 중 하나로 면을 구분해요. 카드에 테두리와 그림자를 함께 주지 않아요.
- **테두리 안에 테두리를 넣지 않아요.** 테두리가 있는 상자 안에 다시 테두리가 있는 상자나 구분선을 넣지 않아요.
- **구역을 상자로 감싸지 않아요.** 페이지의 구역은 제목과 간격으로 나눠요. 구역마다 테두리 상자를 만들지 않아요.
- **입력창과 버튼의 테두리는 ELI 컴포넌트가 이미 갖고 있어요.** 그 위에 테두리를 더하거나 감싸는 상자를 두르지 않아요.
- **테두리 색은 가장 옅은 토큰을 써요.** 브랜드 색이나 상태 색의 테두리는 선택됨, 오류 같은 상태를 알릴 때만 써요.
- **표는 가로줄만 그어요.** 칸마다 사방에 선을 긋지 않아요.

## 글자

- **글자 크기와 굵기의 종류를 줄여요.** 토큰에 있는 단계에서만 골라요.
- **한 줄이 너무 길지 않게 해요.** 넓은 화면에서도 본문의 너비를 제한해요.
- **가운데 정렬은 짧은 글에만 써요.** 두세 줄이 넘는 글은 왼쪽으로 맞춰요.
- **문구는 `UX-WRITING.md`대로 써요.**

## 모양

- **안쪽 모서리는 바깥 모서리보다 작게 해요.** 카드 안의 버튼이 카드보다 둥글면 어색해요.
- **그림자는 떠 있는 요소에만 써요.** 모달, 팝오버, 떠 있는 버튼처럼 다른 내용 위에 있는 요소에 써요. 꾸미려고 모든 카드에 넣지 않아요.
- **아이콘은 뜻을 전달할 때만 넣어요.** 커스텀 아이콘은 `eli-icon` 스킬의 판단표를 통과한 자리에만 써요.

## 모바일 웹

- **엄지가 닿는 곳에 주요 동작을 둬요.** 화면 아래쪽이 누르기 쉬워요.
- **한 화면에 한 가지 일을 해요.** 긴 폼은 단계로 나눠요.
- **누르는 요소는 충분히 크고 서로 떨어져 있어야 해요.** 기준은 `code.md`의 표를 따라요.
- **한 손으로 쓸 수 있게 해요.** 끌기 같은 동작에만 기능을 두지 않고 누르는 방법도 함께 둬요.
- **입력을 줄여요.** 고를 수 있으면 고르게 하고, 자동 완성을 켜요.

## 내용이 달라져도 버텨야 해요

실제 데이터는 시안처럼 가지런하지 않아요. 아래 경우를 모두 넣어 봐요.

| 경우 | 확인하는 것 |
| --- | --- |
| 아주 짧을 때 | 한 글자짜리 이름, 항목 하나뿐인 목록에서 화면이 휑하지 않나요? |
| 아주 길 때 | 긴 이름, 긴 제목, 큰 숫자에서 넘치거나 다른 요소를 밀지 않나요? |
| 없을 때 | 빈 화면이 왜 비었는지와 다음에 할 일을 알려주나요? |
| 많을 때 | 항목이 백 개여도 쓸 수 있나요? |
| 느릴 때 | 불러오는 동안 무엇을 보여주나요? |
| 실패했을 때 | 무슨 일이 생겼는지와 다시 해 볼 방법을 알려주나요? |

빈 화면도 하나의 화면으로 공들여 만들어요. 처음 쓰는 사용자가 가장 먼저 보는 화면이에요.

## 만든 뒤에 확인해요

- 화면을 흐리게 보거나 멀리서 봤을 때 가장 중요한 것이 먼저 보이나요?
- 주요 버튼이 하나인가요?
- 브랜드 색으로 채운 요소가 한 화면에 하나뿐인가요? 브랜드 색 글자와 아이콘이 선택 상태나 링크가 아닌 곳에 있지 않나요?
- 테두리를 모두 지워도 무엇이 한 묶음인지 알 수 있나요? 알 수 있다면 테두리를 지워요.
- 테두리와 그림자를 함께 쓴 요소, 테두리 안의 테두리가 없나요?
- 무엇이 한 묶음인지 간격만으로 알 수 있나요?
- 뺄 수 있는 선, 색, 아이콘, 그림자가 남아 있나요?
- 같은 역할의 요소가 다른 화면과 같은 모양인가요?
- 가장 좁은 화면과 긴 내용에서도 깨지지 않나요?

## 출처

Refactoring UI의 원칙(다른 글의 요약으로 확인했어요), Every Layout, Vercel 디자인 가이드라인, Apple 휴먼 인터페이스 가이드라인. 이 문서의 내용은 표준이 아니라 실무에서 널리 쓰는 판단 기준이에요.
