# ELI 처음 셋업하기

먼저 `../eli/references/installation.md`를 읽고 UI 소비 방식과 하네스 설치 상태를 확인해요. 소스로 설치된 UI에 전체 npm 패키지를 다시 추가하지 않아요. 아래의 컴포넌트 표기는 실제 설치 방식의 ELI를 뜻하고 소스 방식의 import는 설치 기록을 따라요.

새 프로젝트는 세 단계, 이미 화면 코드가 있는 프로젝트는 네 단계로 진행해요. 사용자에게는 짧게 묻고, 초안을 빨리 보여주고, 피드백으로 고쳐요.

| 단계 | 하는 일 | 끝나는 조건 |
| --- | --- | --- |
| 1. 묻기 | 서비스 기획과 디자인 레퍼런스를 물어요 | 두 가지 답을 받았어요 |
| 2. 만들기 | 문서 세 개를 만들고, Pretendard를 연결하고, 토큰과 디자인 시스템 페이지를 만들어 로컬에서 띄워요 | 사용자가 페이지를 볼 수 있어요 |
| 3. 다듬기 | 피드백을 받아 문서와 디자인 시스템을 고쳐요 | 사용자가 됐다고 말해요 |
| 4. 옮기기 | 기존 화면 전체를 새 기준으로 리팩토링해요. 화면 코드가 이미 있을 때만 해요 | 남은 위반을 모두 보고했어요 |

## 시작하기 전에

- `eli-docs` MCP가 연결되어 있는지 확인해요. 연결되지 않았으면 `eli` 스킬의 연결 방법을 안내해요. 그래도 연결할 수 없으면 멈추지 않고, 원격 없이 할 수 있는 1단계와 문서 세 개까지만 진행해요. ELI 설치, 토큰 파일, 디자인 시스템 페이지, 4단계는 연결한 뒤에 이어서 한다고 사용자에게 알려요. ELI의 토큰과 컴포넌트를 추측해서 만들지 않아요.
- `DESIGN.md`, `ICON.md`, `UX-WRITING.md` 중 이미 있는 문서는 덮어쓰지 않아요. 있는 문서는 읽어서 그대로 쓰고, 없는 문서만 만들어요. 세 문서와 토큰 파일이 모두 있으면 3단계부터 시작할지 물어요.
- README, 라우트 구조, 기존 화면에서 알 수 있는 내용은 미리 읽어 둬요.

## 1. 묻기

두 가지만 물어요. 이 단계에서 더 묻지 않아요. 자세한 내용은 3단계에서 실제 화면을 보면서 정해요.

| 질문 | 받아야 할 것 |
| --- | --- |
| 서비스 기획 | 어떤 서비스인가요? 누가 쓰나요? 핵심 기능은 무엇인가요? |
| 디자인 레퍼런스 | 당근, 토스처럼 닮고 싶은 제품은 무엇인가요? 그 제품의 어떤 점을 닮고 싶나요? |

- 레퍼런스는 이름만 받지 않아요. "어떤 점"을 답하지 않았으면 한 번만 더 물어요.
- 레퍼런스가 없다고 하면 원하는 분위기를 두세 낱말로 물어요.
- 프레임워크는 코드에서 확인해요. 코드로 알 수 없을 때만 물어요.

## 2. 만들기

답을 바탕으로 아래 순서로 만들어요. 글꼴 연결을 빼지 않아요. Pretendard를 불러오지 않으면 자간이 맞지 않아요. 중간에 확인을 받으려고 멈추지 않아요. 확인은 3단계에서 한 번에 받아요.

| 순서 | 만드는 것 | 따르는 스킬 |
| --- | --- | --- |
| 1 | `DESIGN.md` | `eli-design-md` 스킬 폴더의 `template.md`와 맞추는 규칙 |
| 2 | `UX-WRITING.md` | `eli-ux-writing` 스킬 폴더의 `template.md`와 맞추는 규칙 |
| 3 | `ICON.md` | `eli-icon` 스킬 폴더의 `template.md`와 맞추는 규칙 |
| 4 | ELI 설치, 글꼴, 프로젝트 토큰 파일, 디자인 시스템 페이지 | `eli-design-system`의 2~6번 |

문서는 처음부터 새로 쓰지 않아요. 각 스킬의 `template.md`를 가져와 이 서비스에 맞게 고쳐요. 각 스킬의 맞추는 규칙은 그대로 따르고, 질문 단계만 건너뛰어요. 이미 있는 화면 코드와 문구가 있으면 거기서 읽은 내용을 먼저 써요.

### 초안은 초안이라고 표시해요

사용자가 직접 답하지 않은 내용은 레퍼런스 제품과 기획에서 추정해 채워요. 추정한 항목에는 끝에 `(초안)`을 붙여요. 각 스킬은 답이 없는 항목을 비워 두라고 하지만, 셋업에서는 근거가 있으면 추정해서 채우고 표시해요. 3단계에서 사용자가 화면을 보고 확인하기 때문이에요.

- 추정할 근거가 없는 항목은 채우지 않고 "정하지 않은 것"에 적어요.
- 레퍼런스 제품의 색상 값, 로고, 고유한 그림을 베끼지 않아요. 닮고 싶다고 한 점만 따라요. 예: 한 화면에 한 가지 일, 큰 글씨, 넓은 여백.
- 값은 ELI 토큰에서만 골라요. 레퍼런스에 맞추려고 ELI에 없는 값을 만들지 않아요.

### 쓰는 버전을 기록해요

`DESIGN.md`의 `## 버전`에 소비 방식과 UI 콘텐츠·하네스·설치 도구 버전을 구분해 적어요. 실제 패키지 방식은 설치된 패키지와 그 하네스 버전을 적어요. `eli-docs`가 해당 소비 방식의 최신 버전을 확인해 줄 때만 오늘 날짜를 적고, 연결·응답 계약이 준비되지 않았으면 "확인 전"으로 둬요.

### 글꼴은 Pretendard로 고정해요

`eli-design-system` 스킬 폴더의 `fonts.md`대로 Pretendard를 전역 글꼴로 연결해요. 글꼴 후보를 보여주거나 고르게 하지 않아요. 레퍼런스 제품이 다른 글꼴을 쓰더라도 따라가지 않아요.

### 디자인 시스템 페이지에 세 문서를 모두 보여줘요

사용자가 페이지 하나만 보고 피드백할 수 있어야 해요. `eli-design-system`의 페이지 구성에 아래를 더해요.

| 구역 | 보여주는 것 |
| --- | --- |
| 방향 | `DESIGN.md`의 서비스, 레퍼런스, 톤을 요약한 글 |
| 토큰 | 프로젝트 토큰의 이름·역할·실제 모습 |
| 컴포넌트 | 이 서비스에서 주로 쓸 설치된 ELI 컴포넌트와 변형. 직접 새로 만들지 않아요. 버튼과 안내 문구는 `UX-WRITING.md`의 말투로 써요 |
| 문구 | 버튼, 오류, 빈 화면, 확인 창의 문구 예시 |
| 아이콘 | `ICON.md`의 스타일 요약과, 빈 화면 예시에 넣은 커스텀 아이콘 하나 |
| 예시 화면 | 이 서비스의 핵심 화면 하나를 프로젝트 토큰, 설치된 ELI 컴포넌트, 문구로 조립한 것 |

- 커스텀 아이콘은 스타일을 보여주기 위한 하나만 만들어요. 더 만들지 않아요.
- `(초안)`으로 추정한 내용은 페이지에서도 초안이라고 보이게 해요.

로컬에서 띄운 뒤 주소를 알려주고 3단계로 넘어가요. 배포하지 않아요.

## 3. 다듬기

페이지를 보여주고 피드백을 받아요. 사용자가 됐다고 말할 때까지 반복해요.

1. 무엇을 만들었는지 짧게 알리고, `(초안)`으로 추정한 항목을 모아서 보여줘요.
2. 영역별로 피드백을 물어요: 색과 분위기, 글자와 간격, 문구의 말투, 아이콘, 컴포넌트 구성.
3. 피드백을 아래 표대로 문서부터 고쳐요.

| 피드백 | 먼저 고치는 곳 | 이어서 고치는 곳 |
| --- | --- | --- |
| 서비스, 사용자, 방향이 달라요 | `DESIGN.md` | 영향받는 다른 문서와 페이지 |
| 글꼴을 바꾸고 싶어요 | 바꾸지 않아요. Pretendard로 고정인 이유를 알리고 굵기, 크기, 색, 여백으로 조절하자고 제안해요 | |
| 색, 글자, 간격, 모서리 | 토큰 파일 | 페이지 |
| 말투, 용어, 문구 | `UX-WRITING.md` | 페이지의 문구 |
| 아이콘의 느낌 | `ICON.md` | 예시 아이콘 |
| 컴포넌트 선택과 구성 | 페이지 | |

4. 고친 것을 알리고 페이지를 다시 보여줘요.

지켜요.

- 페이지만 고치지 않아요. 문서나 토큰 파일을 먼저 고치고 페이지가 그것을 따르게 해요. 페이지만 고치면 다음 작업에서 원래대로 돌아가요.
- 사용자가 확인한 항목은 `(초안)` 표시를 지워요.
- ELI 토큰이나 컴포넌트로 할 수 없는 요청은 할 수 없다고 말하고, 가장 가까운 방법을 제안해요. 값을 지어내지 않아요.
- 피드백이 서로 어긋나면 어느 쪽을 따를지 물어요.

## 4. 옮기기

이미 화면 코드가 있는 프로젝트에서만 해요. 3단계에서 사용자가 됐다고 하면 이어서 시작해요. 문서와 토큰만 만들고 기존 화면을 그대로 두면 새 화면과 옛 화면이 따로 놀아요. 그래서 기존 화면 전체를 새 기준으로 옮겨요.

### 시작하기 전에

- 저장하지 않은 변경이 있으면 먼저 알리고 어떻게 할지 물어요. 사용자의 작업을 덮어쓰지 않아요.
- 새 브랜치를 만들어 그 위에서 작업해요. Git을 쓰지 않는 프로젝트면 되돌릴 방법이 없다고 알리고 계속할지 물어요.
- 묶음마다 커밋할지 처음에 한 번만 물어요.
- 프로젝트의 타입 검사, 린트, 테스트, 빌드 명령을 찾아 지금 통과하는지 먼저 실행해요. 이미 실패하는 검사는 기록해 두고, 리팩토링 때문에 생긴 실패와 구분해요.

### 전체를 조사해요

`eli-verify` 스킬의 1~4번대로 프론트엔드 전체를 조사해 보고해요. `eli-ux-writing` 스킬의 2~3번대로 문구도 함께 조사해요. 보고에는 종류별 건수와 묶음 계획을 적어요.

보고한 뒤 사용자의 승인을 기다리지 않고 이어서 고쳐요. 전체를 옮기는 것이 이 단계의 목적이고, 새 브랜치에서 작업하므로 되돌릴 수 있어요. 다만 아래는 고치지 않고 모아서 물어요.

- 화면의 모양이나 동작이 눈에 띄게 달라지는 변경
- 맞는 토큰이 없어서 새 토큰이 필요한 값
- 뜻이 바뀔 수 있는 문구
- 어느 ELI 컴포넌트로 바꿀지 판단이 갈리는 자체 구현

### 묶음으로 나눠 고쳐요

한 번에 다 고치지 않아요. 아래 순서로 묶음을 나누고, 묶음 하나를 끝낼 때마다 검사를 실행해요.

| 순서 | 묶음 | 하는 일 |
| --- | --- | --- |
| 1 | 토큰 | 직접 쓴 색, 간격, 글자, 모서리 값을 프로젝트 토큰으로 바꿔요 |
| 2 | 단위 | `DESIGN.md`의 단위 기준과 다른 단위를 고쳐요 |
| 3 | 컴포넌트 | 자체 구현과 네이티브 요소를 맞는 ELI 컴포넌트로 바꿔요 |
| 4 | 문구 | 화면의 문구를 `UX-WRITING.md`에 맞게 고쳐요 |
| 5 | 화면 품질 | 상태 누락, 넘침, 입력창 설정, 포커스, 좁은 화면 문제를 고쳐요 |

- 묶음이 크면 화면이나 폴더 단위로 더 나눠요.
- 묶음을 끝낼 때마다 타입 검사, 린트, 테스트, 빌드를 실행해요. 실패하면 다음 묶음으로 넘어가지 않고 그 묶음에서 고쳐요.
- 검사를 통과시키려고 테스트를 지우거나 건너뛰지 않아요.
- 브라우저 도구가 있으면 묶음마다 바뀐 화면을 열어 확인해요.

### 지켜요

- 화면의 모양과 문구의 표현만 옮겨요. 기능, 데이터 처리, 라우팅, 상태 관리의 로직을 바꾸지 않아요.
- 쓰지 않는 코드를 정리하거나 구조를 바꾸는 일을 함께 하지 않아요. 리팩토링의 범위는 디자인 기준이에요.
- 생성된 파일, 외부에서 가져온 코드, `node_modules`는 고치지 않아요.
- 고칠 수 없거나 고치지 않은 곳은 숨기지 않고 보고에 남겨요.

### 끝나면 다시 조사해요

모든 묶음을 끝낸 뒤 `eli-verify`의 조사를 한 번 더 실행해요. 남은 위반이 0이 아니면 무엇이 왜 남았는지 적어요.

## 마무리해요

사용자가 됐다고 하면 아래를 보고해요. 4단계를 했으면 4단계가 끝난 뒤에 보고해요.

- 만든 파일과 디자인 시스템 페이지의 주소
- 아직 `(초안)`으로 남은 항목과 "정하지 않은 것"
- 확인하지 못한 것
- 4단계를 했으면: 묶음별로 고친 건수, 사용자에게 물어야 해서 고치지 않은 것, 남은 위반, 실행한 검사와 결과, 작업한 브랜치
- 다음에 할 일: 만들 화면을 말해 달라고 해요
