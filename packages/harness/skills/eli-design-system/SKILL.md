# 디자인 시스템 구축하기

ELI를 설치하고, 프로젝트의 디자인 토큰을 만들고, 디자인 시스템 페이지를 만들어 로컬에서 띄워요. 토큰을 만드는 단계는 건너뛰지 않아요. 외부에 배포하지 않아요.

## 1. 준비해요

- `eli-docs` MCP가 연결되어 있어야 해요. 연결되지 않았으면 `eli` 스킬의 연결 방법을 안내하고 멈춰요.
- `DESIGN.md`를 읽어요. 없으면 `/eli-design-md`를 먼저 실행할지 사용자에게 물어요. 사용자가 건너뛰면 그대로 진행해요.
- 프로젝트의 상태를 확인해요.

| 확인할 것 | 방법 |
| --- | --- |
| 프레임워크 | `package.json`의 의존성과 설정 파일 (`next.config.*`, `vite.config.*` 등) |
| 패키지 매니저 | lockfile 종류 |
| 라우팅 방식 | 기존 라우트 폴더와 라우터 설정 |
| ELI 설치 여부 | `package.json`의 `@eli/ui` |

프레임워크가 여러 개로 보이거나 판단할 수 없으면 추측하지 않고 사용자에게 물어요.

## 2. ELI를 설정해요

프레임워크가 정해진 프로젝트에서만 해요. 정해지지 않았으면 3번으로 넘어가요.

1. `get_guide`로 `install` 가이드를 읽어요.
2. 가이드대로 프로젝트의 패키지 매니저로 설치해요. 이미 되어 있는 설정은 다시 추가하지 않아요.
3. 가이드에 없는 설정 파일이나 플러그인을 추가하지 않아요.

## 3. 글꼴을 골라요

반드시 해요. 프레임워크가 정해지지 않은 프로젝트에서도 해요. 이 스킬 폴더의 `fonts.md`를 읽고 그 순서대로 진행해요.

- 브라우저 기본 글꼴이나 시스템 글꼴을 주 글꼴로 두지 않아요. Pretendard, Inter, Noto Sans KR처럼 `fonts.md`의 "쓰지 않는 글꼴"에 있는 글꼴을 제안하지 않아요.
- `DESIGN.md`의 톤에 맞는 후보를 두세 개 추려서 같은 내용을 각 글꼴로 보여주는 비교 화면을 띄우고, 사용자가 고르게 해요.
- 고른 글꼴을 전역 진입점에서 한 번 불러오고, `DESIGN.md`의 `## 글꼴`에 이름, 라이선스, 불러오는 방법을 적어요.
- 프로젝트가 이미 글꼴을 정해 쓰고 있으면 그 글꼴을 유지할지 물어요. 그 글꼴이 "쓰지 않는 글꼴"이면 흔한 글꼴이라는 점을 알리고 후보를 함께 보여줘요.
- 글꼴은 4번에서 토큰으로 연결해요.

## 4. 디자인 토큰을 만들어요

반드시 해요. 사용자가 급하다고 해도, 화면이 하나뿐이어도 건너뛰지 않아요. 토큰 없이 화면부터 만들면 값이 흩어지고 나중에 한 번에 바꿀 수 없어요.

프로젝트의 토큰은 "이 서비스에서 이 값을 어디에 쓰는지"를 이름으로 정한 것이에요. 값은 ELI 토큰에서 가져와요.

1. `get_tokens`로 `color`, `semantic-color`, `typography`, `layout`을 모두 읽어요. 이미 화면 코드가 있으면 반복해서 쓰인 색·간격·글자 값을 검색해 토큰 후보로 모아요.
2. `DESIGN.md`의 방향에 맞춰 역할별로 토큰을 정해요. 최소한 아래 역할을 다뤄요.

| 분류 | 역할 |
| --- | --- |
| 색 | 브랜드, 배경, 표면, 글자, 테두리, 상태(성공·경고·오류) |
| 글꼴 | 본문 글꼴, 필요하면 제목 글꼴. 3번에서 고른 글꼴이에요 |
| 글자 | 제목, 본문, 보조 설명 |
| 간격 | 화면 여백, 구역 사이, 요소 사이 |
| 모양 | 모서리 반경 |

3. 토큰 파일 하나에 CSS 변수로 정의해요. 위치와 이름은 프로젝트의 기존 스타일 구조를 따라요. 이미 토큰 파일이 있으면 새로 만들지 않고 그 파일을 채워요.
4. 전역 진입점에서 토큰 파일을 한 번 불러와요. Tailwind처럼 테마 설정이 있는 스타일 방식이면 테마가 이 변수를 가리키게 연결해요.
5. `DESIGN.md`의 `## 토큰`에 토큰 파일의 경로와 분류별 이름 규칙을 적어요. `DESIGN.md`가 없으면 이 섹션만 담아 만들어요. 값은 적지 않아요.

토큰을 정할 때 지켜요.

- 글꼴 토큰은 `fonts.md`의 "토큰에 연결해요"대로 정해요. ELI 컴포넌트도 같은 글꼴을 쓰도록 `--eli-font-family-sans`를 함께 바꿔요.
- 이름은 값이 아니라 역할로 지어요. `blue-500`이 아니라 `color-brand`처럼 지어요.
- 접두사 `--eli-`는 ELI의 것이에요. 프로젝트 토큰에는 쓰지 않아요.
- 값은 `var(--eli-...)`로 ELI 토큰을 가리켜요. 프레임워크가 정해지지 않아 ELI를 설치하지 못했으면 `get_tokens`의 값을 적고, 어느 ELI 토큰의 값인지 주석으로 남겨요.
- ELI에 맞는 토큰이 없는 값은 지어내지 않아요. 사용자에게 값을 확인받아 토큰 파일에만 적어요.
- 색, 간격, 글자 크기 같은 값을 직접 쓰는 곳은 프로젝트 전체에서 토큰 파일 하나뿐이어야 해요.
- 이미 화면 코드가 있는 프로젝트면 토큰을 만든 뒤 `/eli-verify`로 기존 코드를 토큰으로 옮기라고 안내해요.

## 5. 디자인 시스템 페이지를 만들어요

`get_guide`로 `design-system-page` 가이드를 읽고 그 구성을 따라요. 내용은 4번에서 만든 프로젝트 토큰과 `list_components`, `get_component`의 `examples`·`variants` 섹션에서 가져와요.

| 프로젝트 상태 | 만드는 것 |
| --- | --- |
| 프레임워크가 정해져 있어요 | 그 프레임워크의 라우트로 `/design-system` 페이지를 만들어요. 실제 `@eli/ui` 컴포넌트를 가져와 렌더링해요. |
| 라이브러리가 아직 정해지지 않았어요 | `design-system.html` 파일 하나로 만들어요. 토큰과 디자인 방향을 보여줘요. |

- 기존 프로젝트의 폴더 구조, 스타일 방식, 코드 규칙을 따라요.
- 페이지에는 프로젝트 토큰의 이름·역할·실제 모습과 컴포넌트별 변형을 담아요. 페이지의 스타일도 프로젝트 토큰만 써요. `DESIGN.md`가 있으면 이 서비스에서 주로 쓸 컴포넌트를 먼저 보여줘요.
- HTML 파일에서는 React 컴포넌트를 실행할 수 없어요. 컴포넌트는 문서의 설명으로 소개하고, 실제 컴포넌트가 아니라고 페이지에 적어요.
- 문서에 없는 토큰이나 변형을 지어내지 않아요.

## 6. 로컬에서 띄워요

- 프레임워크 프로젝트: 프로젝트의 개발 서버 명령을 백그라운드로 실행하고 `/design-system` 주소를 알려줘요. 이미 실행 중이면 그 서버를 써요.
- HTML 파일: 로컬 정적 서버로 띄우거나 파일을 브라우저로 열어요.
- 서버는 `localhost`에만 띄워요.
- 배포 명령을 실행하지 않아요. 배포 설정 파일을 추가하지 않아요. 터널링 도구로 외부에 공개하지 않아요.

## 7. 확인하고 보고해요

- 화면이 실제로 고른 글꼴로 보이는지 확인해요. 브라우저 도구가 있으면 계산된 글꼴을 확인해요.

- 토큰 파일 밖에 직접 쓴 색·간격·글자 값이 남아 있지 않은지 이번에 만든 파일을 검색해 확인해요.
- 페이지가 실제로 열리는지 확인해요. 브라우저 도구가 있으면 화면과 콘솔 오류를 확인해요.
- 프로젝트의 타입 검사와 린트가 있으면 실행해요.
- 보고에는 주소, 추가하거나 바꾼 파일, 확인하지 못한 것을 적어요. 확인하지 않은 것을 확인했다고 적지 않아요.
