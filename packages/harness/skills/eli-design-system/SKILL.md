# 디자인 시스템 구축하기

디자인 시스템은 설치된 ELI 컴포넌트와 토큰 위에 만들어요. 먼저 `../eli/references/installation.md`로 소비 방식을 구분해요. 소스 방식은 필요한 UI만 추가하고 기록된 로컬 경로에서 가져와요. 프로젝트의 디자인 토큰과 디자인 시스템 페이지를 만들어 로컬에서 띄워요. 토큰을 만드는 단계는 건너뛰지 않아요. 외부에 배포하지 않아요.

## 1. 준비해요

- `eli-docs`의 문서를 읽을 수 있어야 해요. 도구가 세션에 보이지 않으면 `eli` 스킬의 "원격 MCP에 연결해요"대로 등록하고 조회 스크립트로 이어서 진행해요. 스크립트로도 읽지 못할 때만 멈춰요.
- `DESIGN.md`를 읽어요. 없으면 `/eli-design-md`를 먼저 실행할지 사용자에게 물어요. 사용자가 건너뛰면 그대로 진행해요.
- 프로젝트의 상태를 확인해요.

| 확인할 것 | 방법 |
| --- | --- |
| 프레임워크 | `package.json`의 의존성과 설정 파일 (`next.config.*`, `vite.config.*` 등) |
| 패키지 매니저 | lockfile 종류 |
| 라우팅 방식 | 기존 라우트 폴더와 라우터 설정 |
| ELI 설치 여부 | 소스 방식의 설치 기록·실제 파일 또는 기존 npm 패키지 |

프레임워크가 여러 개로 보이거나 판단할 수 없으면 추측하지 않고 사용자에게 물어요.

## 2. ELI를 설정해요

프레임워크가 정해진 프로젝트에서만 해요. 정해지지 않았으면 3번으로 넘어가요.

1. `get_guide`로 `install` 가이드를 읽어요. `not_found`이면 `../eli/references/installation.md`만 따라요.
2. 소스 방식은 CLI로 필요한 항목만 추가해요. 실제 npm 패키지 방식을 선택한 경우에만 패키지 매니저로 UI 패키지를 설치해요. 이미 되어 있는 설정은 다시 추가하지 않아요.
3. 가이드에 없는 설정 파일이나 플러그인을 추가하지 않아요.
4. 설치한 버전을 `DESIGN.md`의 `## 버전`에 적어요.

## 3. 글꼴을 연결해요

반드시 해요. 프레임워크가 정해지지 않은 프로젝트에서도 해요. 이 스킬 폴더의 `fonts.md`를 읽고 그대로 진행해요.

- 전역 글꼴은 Pretendard로 고정이에요. 다른 글꼴을 제안하거나 고르게 하지 않아요.
- ELI의 타이포그래피 토큰은 자간과 줄 높이가 Pretendard에 맞춰져 있어요. 글꼴을 바꾸면 자간과 정렬이 깨져요.
- Pretendard 공식 안내의 가변 다이나믹 서브셋을 전역 진입점에서 한 번 불러오고, 전역 스타일의 `body`에 `font-family: var(--eli-font-family-sans)`를 둬요. 이미 되어 있으면 다시 추가하지 않아요.
- Next.js에서도 `next/font/local`을 쓰지 않아요. 글꼴이 다른 이름으로 등록돼서 ELI 컴포넌트에 적용되지 않아요.
- `--eli-font-family-sans`를 다시 정하지 않아요.
- 프로젝트에 이미 다른 글꼴이 연결되어 있으면 사용자에게 알리고, Pretendard로 바꿀지 확인받은 뒤 지워요.
- `DESIGN.md`의 `## 글꼴`에 불러오는 방법을 적어요.

## 4. 디자인 토큰을 만들어요

반드시 해요. 사용자가 급하다고 해도, 화면이 하나뿐이어도 건너뛰지 않아요. 토큰 없이 화면부터 만들면 값이 흩어지고 나중에 한 번에 바꿀 수 없어요.

프로젝트의 토큰은 "이 서비스에서 이 값을 어디에 쓰는지"를 이름으로 정한 것이에요. 값은 ELI 토큰에서 가져와요.

1. `get_tokens`로 `color`, `semantic-color`, `typography`, `layout`을 모두 읽어요. 이미 화면 코드가 있으면 반복해서 쓰인 색·간격·글자 값을 검색해 토큰 후보로 모아요.
2. `DESIGN.md`의 방향에 맞춰 역할별로 토큰을 정해요. 최소한 아래 역할을 다뤄요.

| 분류 | 역할 |
| --- | --- |
| 색 | 브랜드, 배경, 표면, 글자, 테두리, 상태(성공·경고·오류) |
| 글자 | 제목, 본문, 보조 설명 |
| 간격 | 화면 여백, 구역 사이, 요소 사이 |
| 모양 | 모서리 반경 |

3. 토큰 파일 하나에 CSS 변수로 정의해요. 위치와 이름은 프로젝트의 기존 스타일 구조를 따라요. 이미 토큰 파일이 있으면 새로 만들지 않고 그 파일을 채워요.
4. 전역 진입점에서 토큰 파일을 한 번 불러와요. Tailwind처럼 테마 설정이 있는 스타일 방식이면 테마가 이 변수를 가리키게 연결해요.
5. `DESIGN.md`의 `## 토큰`에 토큰 파일의 경로와 분류별 이름 규칙을 적어요. `DESIGN.md`가 없으면 이 섹션만 담아 만들어요. 값은 적지 않아요.

### 브랜드 컬러를 만들어요

사용자가 브랜드 컬러를 정했으면 그 색으로 만들어요. ELI에 없는 색이어도 돼요. 사용자가 직접 정한 값이라 "값을 지어내지 않아요"에 어긋나지 않아요. 정하지 않았으면 이 절을 건너뛰고 ELI의 기본 브랜드 색을 그대로 써요.

1. **기준 색을 정해요.** 색상 코드를 받았으면 그대로 써요. 색 이름만 받았으면 ELI의 색 토큰(`get_tokens`의 `color`)에서 가장 가까운 색을 먼저 찾고, 맞는 색이 없으면 색상 코드를 하나 골라 사용자에게 확인받아요.
2. **토큰 파일에만 적어요.** 기준 색을 프로젝트의 브랜드 토큰으로 정의하고 "사용자가 정한 브랜드 컬러"라고 주석을 남겨요. 색상 값을 직접 쓰는 곳은 여기 한 곳뿐이에요.
3. **상태별 색을 기준 색에서 만들어요.** hover, pressed, disabled, 반투명 배경은 값을 새로 지어내지 않고 기준 색에서 CSS로 계산해요(`color-mix()`나 상대 색상 문법). ELI의 기본 브랜드 색이 상태별로 어떻게 달라지는지 `get_tokens`로 읽고 같은 방식과 비율을 따라요.
4. **ELI 컴포넌트가 따라오게 해요.** `get_tokens`에 `category: "semantic-color"`, `q: "brand"`로 ELI의 브랜드 시맨틱 토큰을 모두 찾아요. 토큰 파일에서 그 변수들이 프로젝트의 브랜드 토큰을 가리키도록 다시 정의해요. 이름을 기억으로 쓰지 않고 응답에 있는 변수만, 빠짐없이 다시 정의해요. 하나라도 빠지면 버튼의 일부 상태만 옛 색으로 남아요.
5. **읽을 수 있는지 확인해요.** 브랜드 색 배경 위의 글자, 흰 배경 위의 브랜드 색 글자가 명암비 4.5:1 이상인지 계산해요. 모자라면 색을 몰래 바꾸지 않고 사용자에게 알리고, 더 어둡거나 밝은 대안을 색상 코드와 함께 제안해요.
6. 디자인 시스템 페이지의 색 구역에 브랜드 컬러와 상태별 색을 먼저 보여줘요. 설치된 ELI 버튼이 실제로 그 색으로 보이는지 확인해요.

브랜드 컬러 밖의 색(배경, 글자, 테두리, 상태 색)은 그대로 ELI 토큰을 가리켜요. 브랜드 컬러에 맞추려고 다른 색까지 새로 만들지 않아요.

토큰을 정할 때 지켜요.

- 글꼴 토큰을 따로 만들지 않아요. 글꼴은 Pretendard로 고정이고 `--eli-font-family-sans`를 그대로 써요.
- 글자 크기, 굵기, 줄 높이, 자간은 ELI의 타이포그래피 토큰을 한 묶음으로 가리켜요. 자간만 따로 정하지 않아요.
- 이름은 값이 아니라 역할로 지어요. `blue-500`이 아니라 `color-brand`처럼 지어요.
- 접두사 `--eli-`는 ELI의 것이에요. 프로젝트 토큰에는 쓰지 않아요. 브랜드 시맨틱 토큰을 프로젝트 브랜드 토큰으로 다시 가리키게 하는 것만 예외이고, 토큰 파일 안에서만 해요.
- 값은 `var(--eli-...)`로 ELI 토큰을 가리켜요. 프레임워크가 정해지지 않아 ELI를 설치하지 못했으면 `get_tokens`의 값을 적고, 어느 ELI 토큰의 값인지 주석으로 남겨요.
- ELI에 맞는 토큰이 없는 값은 지어내지 않아요. 사용자에게 값을 확인받아 토큰 파일에만 적어요. 브랜드 컬러는 위 절대로 사용자가 정한 색을 써요.
- 색, 간격, 글자 크기 같은 값을 직접 쓰는 곳은 프로젝트 전체에서 토큰 파일 하나뿐이어야 해요.
- 이미 화면 코드가 있는 프로젝트면 토큰을 만든 뒤 `/eli-verify`로 기존 코드를 토큰으로 옮기라고 안내해요.

## 5. 디자인 시스템 페이지를 만들어요

`get_guide`로 `design-system-page` 가이드를 읽고 그 구성을 따라요. `not_found`이면 토큰, 타이포그래피, 컴포넌트 순서의 기본 구성으로 만들고 원격 가이드 없이 구성했다고 알려요. 내용은 4번에서 만든 프로젝트 토큰과 `list_components`, `get_component`의 `examples`·`variants` 섹션에서 가져와요.

| 프로젝트 상태 | 만드는 것 |
| --- | --- |
| 프레임워크가 정해져 있어요 | 그 프레임워크의 라우트로 `/design-system` 페이지를 만들어요. 설치 기록의 실제 ELI 컴포넌트를 가져와 렌더링해요. |
| 라이브러리가 아직 정해지지 않았어요 | `design-system.html` 파일 하나로 만들어요. 토큰과 디자인 방향을 보여줘요. |

- **설치된 ELI 컴포넌트를 사용해요.** 버튼, 입력창, 모달 같은 컴포넌트를 직접 새로 만들지 않아요. `list_components`로 있는 컴포넌트를 확인하고 소스 방식의 실제 로컬 경로에서 가져와요.
- 다른 UI 라이브러리를 추가하지 않아요. 프로젝트에 이미 다른 UI 라이브러리가 있으면 알리고, ELI로 옮길지 물어요.
- 이 서비스에 필요한데 ELI에 없는 컴포넌트만 직접 만들어요. ELI 컴포넌트와 프로젝트 토큰을 조합해서 만들고, 페이지에서 "직접 만든 컴포넌트"로 구분해서 보여줘요.
- 기존 프로젝트의 폴더 구조, 스타일 방식, 코드 규칙을 따라요.
- 페이지에는 프로젝트 토큰의 이름·역할·실제 모습과 컴포넌트별 변형을 담아요. 페이지의 스타일도 프로젝트 토큰만 써요. `DESIGN.md`가 있으면 이 서비스에서 주로 쓸 컴포넌트를 먼저 보여줘요.
- HTML 파일에서는 React 컴포넌트를 실행할 수 없어요. 컴포넌트는 문서의 설명으로 소개하고, 실제 컴포넌트가 아니라고 페이지에 적어요.
- 문서에 없는 토큰이나 변형을 지어내지 않아요.

### 데스크톱에서 읽기 좋게 배치해요

이 페이지는 개발자와 디자이너가 데스크톱 브라우저로 보는 문서예요. 서비스가 모바일 앱이어도 페이지 전체를 모바일 폭으로 만들지 않아요. 좁은 열 양옆에 큰 빈 여백이 남으면 토큰과 컴포넌트를 한눈에 비교할 수 없어요.

| 항목 | 데스크톱 (기본) | 좁은 화면 |
| --- | --- | --- |
| 본문 폭 | 화면 폭을 넓게 써요. 최대 폭은 넓은 데스크톱 기준으로 한 번만 정하고 가운데에 둬요. 휴대폰 폭이나 글 한 단 폭으로 제한하지 않아요 | 화면 폭 전체 |
| 좌우 여백 | 프로젝트의 화면 여백 토큰만큼만 둬요. 여백으로 본문을 좁히지 않아요 | 같은 토큰의 좁은 화면 값 |
| 구역 이동 | 구역 목록을 옆에 고정해 두고 본문만 스크롤해요 | 목록을 본문 위로 올려요 |
| 색·간격·모서리 토큰 | 여러 열의 격자로 나란히 보여줘요 | 한두 열 |
| 타이포그래피 | 이름, 값, 실제 글자를 한 줄에 나란히 보여줘요 | 세로로 쌓아요 |
| 컴포넌트 변형 | 같은 컴포넌트의 변형을 가로로 나란히 놓아 비교해요 | 줄바꿈해요 |

- 격자는 `repeat(auto-fill, minmax(...))`처럼 폭에 따라 열 수가 바뀌게 해요. 폭을 `px`로 고정하지 않아요. 긴 설명 문단만 읽기 좋은 길이로 제한해요.
- 최대 폭, 격자 칸의 최소 폭, 화면 폭 기준점도 프로젝트 토큰으로 써요. 없으면 토큰 파일에 먼저 추가해요. 단위는 `DESIGN.md`의 `## 단위`를 따라요.
- 이 서비스의 화면이 모바일용이면 예시 화면만 휴대폰 폭의 틀 안에 넣어 보여줘요. 페이지 자체는 넓게 둬요.
- 좁은 화면에서도 가로로 넘치지 않아야 해요. 너비 320px에서 확인해요.
- `design-system-page` 가이드가 구역과 순서를 정해도 이 배치 기준은 그대로 지켜요.

## 6. 로컬에서 띄워요

- 프레임워크 프로젝트: 프로젝트의 개발 서버 명령을 백그라운드로 실행하고 `/design-system` 주소를 알려줘요. 이미 실행 중이면 그 서버를 써요.
- HTML 파일: 로컬 정적 서버로 띄우거나 파일을 브라우저로 열어요.
- 서버는 `localhost`에만 띄워요.
- 배포 명령을 실행하지 않아요. 배포 설정 파일을 추가하지 않아요. 터널링 도구로 외부에 공개하지 않아요.

## 7. 확인하고 보고해요

- 화면이 실제로 Pretendard로 보이는지 확인해요. 브라우저 도구가 있으면 계산된 글꼴을 확인해요.

- 토큰 파일 밖에 직접 쓴 색·간격·글자 값이 남아 있지 않은지 이번에 만든 파일을 검색해 확인해요.
- 페이지가 실제로 열리는지 확인해요. 브라우저 도구가 있으면 화면과 콘솔 오류를 확인해요.
- 데스크톱 폭(1440px 안팎)에서 본문이 좁은 열로 몰리거나 양옆이 크게 비지 않는지, 320px에서 가로로 넘치지 않는지 확인해요. 브라우저 도구가 없으면 확인하지 못했다고 적어요.
- 프로젝트의 타입 검사와 린트가 있으면 실행해요.
- 보고에는 주소, 추가하거나 바꾼 파일, 확인하지 못한 것을 적어요. 확인하지 않은 것을 확인했다고 적지 않아요.
