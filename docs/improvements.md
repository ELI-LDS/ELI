# ELI 개선 제안

초보 개발자가 ELI의 UI에 기능을 쉽게 연결하도록 돕기 위한 개선 후보예요. 아래 항목은 모두 **제안 상태**이며 구현 완료나 일정 확정을 의미하지 않아요. 이 문서만으로 코드 변경이나 의존성 추가를 시작하지 않아요.

[FECONF 2026 「디자인 시스템, 더 나아가서」 발표 자료](https://junghyeonsu.github.io/feconf-2026-public/)의 맥락 전달·레퍼런스·사용 패턴 논의를 참고했어요. 아래 우선순위와 적용 방법은 ELI의 현재 규모에 맞춘 제안이며, 당근의 구현 방식을 그대로 도입한다는 뜻은 아니에요.

## 개선 후보

| 제안 | 해결하려는 문제 | 적용 방법 | 완료 기준 | 우선순위 / 상태 |
| --- | --- | --- | --- | --- |
| 컴포넌트 선택 기준 | 허용되는 props를 알아도 어떤 조합을 선택할지 어려워요. | 디자이너와 사용 목적·권장 상황을 합의해 짧은 기준은 JSDoc, 비교 예시는 Storybook에 담아요. | 검토 대상의 선택 이유와 피해야 할 사용 사례를 확인할 수 있어요. | 높음 / 제안 |
| 실제 사용 패턴 | 개별 컴포넌트 예시만으로 입력·검증·제출을 연결하기 어려워요. | 첫 후보로 Storybook에 회원가입 폼 예시를 만들고, 입력·오류·처리 중·결과 피드백을 연결해요. 필요한 디자인은 먼저 합의해요. | 개발자가 검증 함수와 요청 함수를 자신의 코드로 교체할 수 있고, 성공·실패 흐름을 직접 확인할 수 있어요. | 높음 / 제안 |
| 상호작용 검증 | 현재 패키징·SSR 검사만으로 키보드와 포커스 동작을 확인하기 어려워요. | 복잡한 입력·선택·오버레이부터 실제 사용 흐름을 점검하고, 반복 확인이 필요한 동작에 자동 검사를 추가해요. | 선택한 흐름의 키보드 조작·포커스 이동·상태 변경을 검증하고 지원 범위를 기록해요. | 높음 / 제안 |
| 승인된 화면 예시 | 디자인 변경 후 무엇을 기준으로 비교할지 불명확할 수 있어요. | 디자이너가 확인한 Story와 Figma 기준 링크, 검토 날짜를 PR에 남겨요. 자동 화면 비교는 반복 확인 비용이 커지면 검토해요. | 변경 전후 화면과 검토 당시의 기준을 추적할 수 있어요. | 중간 / 제안 |
| Docs·MCP의 자료 공유 | 사람용 설명과 AI용 설명을 따로 관리하면 내용이 달라질 수 있어요. | 한국어 사용법과 예시의 기준 자료를 정한 뒤 Docs와 MCP가 같은 자료를 참조하도록 연결해요. | 같은 컴포넌트의 공개 API·사용 예시·제약을 두 경로에서 일관되게 확인할 수 있어요. | 후속 / 제안 |

사용 패턴은 컴포넌트를 조합하는 예시예요. 서비스별 검증 규칙과 서버 요청은 소비 앱이 담당하고, 예제에서는 바꿔 넣을 위치를 보여줘요. 예시 하나를 만들기 위해 별도의 런타임 패키지를 추가하지 않아요.

새로운 디자인 언어나 전체 화면 자동 수집 시스템은 현재 우선 대상에 포함하지 않아요. 기존 Figma·React·CSS·Storybook으로 해결하기 어려운 구체적인 문제가 생기면 다시 검토해요.

## 제안을 적용해요

상태는 `제안 → 합의 → 진행 중 → 완료`로 관리해요. 도입하지 않기로 하거나 미루면 `보류`와 이유를 남겨요. 작업을 합의할 때 담당자와 관련 이슈·PR 링크를 추가해요.

먼저 선택 기준을 합의하고 사용 패턴 하나를 구현해봐요. 그 과정에서 드러난 API·접근성 문제를 정리하고 필요한 검증을 추가한 뒤, Docs·MCP로 전달할 자료를 확장하는 순서를 제안해요.

반복 적용할 규칙이 확정되면 관련 `Agent/` 문서에 반영하고, 구현된 사용법은 JSDoc·Storybook·사용자 문서에 반영해요. 이 문서에는 결정 이유와 결과 링크를 남겨 같은 규칙을 중복 관리하지 않아요.
